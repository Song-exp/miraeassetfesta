## 0. 한 줄

**"사람 말 → SQL → 데이터 → 사람 말"** 로 바꾸는 8단계 파이프라인이고,
그 사이에 **사람이 판단해 쌓은 규칙(yaml)** 이 끼어들어 LLM 이 지어내지 못하게 막는다.

LLM 에 통째로 맡기면 없는 상품을 만들어낸다. 그래서 **단계를 쪼개고 LLM 은 두 곳에서만** 쓴다.

| | 쓰는 것 | 왜 |
| :-- | :-- | :-- |
| ⑤ Plan | 🤖 HCX | 자연어 → SQL. 조건 조합은 규칙으로 다 적을 수 없다 |
| ⑧ Answer | 🤖 HCX | 조회 결과 → 문장 |
| 나머지 6단계 | 결정적 코드 | 재현 가능하고, 비용이 0이며, 틀리면 고칠 자리가 있다 |

## 1. 전체 흐름

```
질문
 │
 ├─① Normalize  문장 다듬기 (따옴표·공백)
 │
 ├─② Route      어느 상품군인가          ← 단어 목록 없이. 문장 구조 + DB 어휘
 │
 ├─③ Ground     이름 → DB 값             ← 지식그래프(KG). 별칭·자회사·해외티커까지 폄
 │
 ├─④ Gate       답할 수 없는 것 끊기      ← 🤖 호출 전. 비용 0
 │
 ├─⑤ Plan       근거문서 조립 → SQL 생성  ← 🤖 HCX ①
 │
 ├─⑥ Guard      SQL 검사 (+1회 재생성)    ← 안전·정합
 │
 ├─⑦ Execute    읽기 전용 조회 (≤30행)
 │
 └─⑧ Answer     문장 만들기               ← 🤖 HCX ② + 말하기 규칙
```

모든 단계는 `think_trace` 에 남는다. **어디서 틀렸는지 눈으로 보고 고칠 수 있다**는 것이 이 구조의 이유다.

## 2. 예문 하나로 끝까지 — `"채권형 국내 ETF 중 총보수 낮은 것 3개 알려줘"`

### ② Route — 어느 상품인가 (LLM 안 씀)

`채권형` 이 들어 있다고 채권으로 보내면 틀린다.

> **한국어는 맨 뒤 상품 명사가 머리다.** *"채권형 ETF"* 는 ETF, *"ETF형 채권"* 이면 채권이다.

```
채권형  국내  ETF  중 총보수 …
        └수식┘ └머리┘        → domestic_etfs
```

세 겹으로 판정하고, **어느 겹에도 사람이 쓴 단어 목록이 없다.**

| 겹 | 방법 | 예 |
| :-: | :-- | :-- |
| ① | 문장 구조 — 마지막 상품 명사가 머리, 그 앞 국내/해외/미국이 테이블을 가름 | `채권형 국내 ETF` → 국내ETF |
| ② | 온톨로지 값 — 질문에 어느 테이블의 **실제 값**(발행사·지수·종목명)이 나오나 | `KOSPI200 추종 상품` → 국내ETF |
| ③ | 동의어 — DB 에 글자가 없는 통칭 | `곱버스` → `인버스2X` → 국내ETF |
| ④ | 못 정하면 4테이블 전부 넘겨 HCX 가 FROM 으로 결정 | |

> 🔴 예전엔 단어 11개 목록으로 판정해 `국고채` 를 못 알아듣고 `채권형 ETF` 를 채권으로 끌고 갔다.

### ③ Ground — 이름을 DB 값으로 (지식그래프)

사람이 부르는 이름과 DB 글자가 다르다. 그 사이를 KG 가 잇는다.

```
"에코프로"  →  Sec_m_ecopro  (정본 노드 · 별칭 0개)
                 ├─ Sec_kr_086520   에코프로비엠   ┐ kg_closure
                 ├─ Sec_kr_247540   에코프로       ┘ 후손
                 └─ (자회사 질의면) subsidiaryOf 엣지로 1단 더
               → ext_etf_holdings.ticker IN ('086520','247540', …)
```

**정본 노드는 값이 0개**고 실물이 후손으로 매달려 있다. 후손을 펴지 않으면 *정본에 정확히 매칭될수록 답이 빈다.*
이 결함(㉡)을 8/30 에 고쳤고, 주최 공식 예시 2개(캠브리콘·에코프로)가 그때 풀렸다.

이 예문에선 `국내` 가 걸리는데 — **여기에 함정이 있다.**

> `국내 ETF` 의 "국내" 는 **상장 시장**이지 투자 지역이 아니다.
> KG 가 `Region_Korea` 로 잡아 `wu_inv_rgn='국내'` 필터를 붙이면 **해외채권형 ETF 가 통째로 빠진다.**
> → `국내 (상장)? (ETF|ETN|상품)` 자리면 건너뛴다. `국내에 투자하는`·`국내 주식형` 은 그대로 둔다. (2026-08-31)

### ④ Gate — 답할 수 없는 것을 HCX 호출 전에 끊기

| 유형 | 예 | 근거 |
| :-- | :-- | :-- |
| 속성 부재 | *"위험등급 낮은 해외 ETF"* | 해외ETF 에 위험등급 컬럼이 없음 |
| 등급 오류 | *"AAAA 등급 채권"* | 신용등급 표준표에 없는 등급 |
| 기준일 이후 | *"2027년 시점 수익률"* | 데이터 기준일 2026-08-22 |

**비용이 0이고 즉답이다.** 평가의 *답변불가 5문항* 을 여기서 잡는다.

> ⚠️ 단, 연도만 보고 막지 않는다. *"2027년 만기 채권"* 은 정상 질의라 사후 검사로 옮겼다.

### ⑤ Plan — 근거문서 조립 → SQL 생성 🤖

질문만 주지 않는다. **약 8,700자의 근거 뭉치**를 함께 넘긴다.

| 구성 | 출처 |
| :-- | :-- |
| KG 개체 매핑 | ③ 결과 |
| **도메인 규칙** (`query_rules`) | `ontology/enums/<도메인>.yaml` ← **사람이 판단해 쌓은 것** |
| 되묻기 규칙 (`clarify`) | 같음 |
| 답변불가 규칙 | `enums/_refusal.yaml` |
| 범주형 컬럼의 실제 값 | DB 에서 자동 |
| 스키마 | DB |

이 예문에 실리는 규칙:

```
채권형질의 : wu_inv_ast_type LIKE '%채권%' AND NOT (인버스…)
보수유효   : cu_charge_rt > 0      # 0 은 무료가 아니라 미입력. 안 걸면 미입력이 상위를 도배한다
ETF만      : pd_grp_no = 'ETF'     # 국내ETF 테이블에 ETN 545건이 섞여 있다
```

> 🔴 **규칙은 문서가 아니라 프롬프트다.** 판정을 문서에 적으면 챗봇은 모른다. yaml 에 적어야 프롬프트가 바뀐다.
> 서버 실측(8/31)에서 인버스 질의의 SQL 이 yaml 원문과 글자까지 같았다.

### ⑥ Guard — SQL 검사

| 검사 | 막는 것 |
| :-- | :-- |
| SELECT 한 문장인가 | DELETE·DROP·다중문 |
| 허용 테이블만 쓰나 | 화이트리스트 밖 |
| **FROM 에 없는 테이블을 참조하나** | 실행 시 OperationalError (2026-08-31 신설) |
| LIMIT 있나 | 결과 폭주 — 없으면 **기각이 아니라 보정** |
| WHERE 값이 DB 에 있나 | 존재하지 않는 값으로 0행 |
| 날짜 리터럴 | SQLite 는 `2029-08-22` 를 뺄셈(=1999)으로 읽는다 |

문제가 있으면 **사유를 붙여 1회 재생성**한다. 정답 조건식을 형식 때문에 버리지 않는 것이 원칙이다.

### ⑦ Execute — 읽기 전용, 최대 30행

### ⑧ Answer — 문장 만들기 🤖 + 말하기 규칙

`answer_rules` 를 함께 넘긴다. **`query_rules` 는 SQL 생성기만 보고, 말하기 규칙은 여기서 따로 싣는다.**

```
- 조회 결과에 없는 상품명·수치·날짜를 만들지 않는다 (환각 = 최대 감점)
- 총보수가 0이면 "0%" 가 아니라 "수록되어 있지 않습니다"
- 인버스는 배수를 그대로 말하지 않는다 — 부호가 88% 소실됐다
- 레버리지가 목록에 있으면 장기보유 주의 문구를 붙인다 (발동 조건일 때만)
- 투자 권유로 읽히는 표현을 쓰지 않는다
```

## 3. 도메인이 다르면 무엇이 달라지나

**뼈대는 같다. ③⑤⑧ 이 참조하는 yaml 만 갈린다.**

### `"안전한 채권 추천해줘"` vs `"안전한 ETF 추천해줘"`

| 단계 | 국내ETF | 국내채권 |
| :-- | :-- | :-- |
| ② Route | `domestic_etfs` | `domestic_bonds` |
| ③ Ground | 종목·지수·운용사 | **신용등급 계층** — `투자등급` → `AAA~BBB-` 10종으로 펴짐 |
| ⑤ 규칙 | `ETF만` · `보수유효` · `구매가능` | `고위험제외` · `신용보강 층 주입` |
| ⑧ 말하기 | 레버리지·인버스 주의 | *"국공채는 신용등급 미부여"* · *"수익률 6% 초과면 원금 주의"* |

> 🔴 **같은 말이 도메인마다 뜻이 다르다.**
> 채권 위험등급은 **6등급이 가장 안전**, 펀드는 **1등급이 가장 위험**. 각 도메인 `answer_rules` 에 방향을 못박아 뒀다.

### 국내ETF ↔ 해외ETF — 같은 "ETF" 인데 성격이 반대다

| | 국내ETF (1,780) | 해외ETF (6,037) |
| :-- | --: | --: |
| 상품명 언어 | 한글 1,779 / 지수명은 영문 | **영문 6,037 · 한글 0** |
| 총보수 유효 | **67건** (ETF 기준 5.4%) | **5,618건** (93%) |
| 위험등급 | 전건 있음 | **컬럼 없음** |
| 기간수익률 | 6종(1d·1m·3m·6m·ytd·1y) | **1일치 하나뿐** |
| 인버스 판정 | 이름 (배수 부호 88% 소실) | 플래그 컬럼 정상 |
| `cu_strtegy` | 범주값 4개 | **자유서술 5,943종** |

> 국내 규칙을 해외에 그대로 옮기면 대부분 틀린다. 그래서 yaml 을 따로 쓴다.
> 예 — 국내에서 *"총보수 수록되지 않음"* 은 맞는 말이지만 해외에선 93%가 유효해 틀린 말이 된다.

### 교차 질의 — 한 호출에서 여러 상품군

*"삼성전자를 보유한 국내/해외 ETF와 공모펀드"* 처럼 `보유한·편입·구성종목` 이 있으면
마스터 4테이블 + 외부 `ext_*` 를 **함께** 대상으로 잡고 조인 키를 프롬프트에 넣는다.

> 🔴 조인 키를 안 주면 모델이 마스터에 없는 컬럼을 WHERE 에 써서 실행이 깨진다.

## 4. 규칙은 어디서 와서 어디로 가나

```
사람의 판단 (실측 근거 + 회의 결정 + 주최 답변)
        │
        ▼
ontology/enums/*.yaml        ← 도메인 4개. 손으로 쓰는 유일한 곳
ontology/shared/*.yaml       ← 지역·통화·등급·지수·종목 (일부 자동 생성)
ontology/codebooks/*.csv     ← 코드 ↔ 이름
        │  scripts/build_ontology.py   (V1~V6 검증 통과해야 산출)
        ▼
ontology/*.ttl  5개          +  kg_node / kg_alias / kg_edge / kg_closure
        │  src/runtime/loader.py
        ▼
HCX 프롬프트 (Plan · Answer 단계)
```

**`.ttl` 과 KG 는 손으로 쓰지 않는다.** 전부 yaml 에서 기계가 만든다.
규칙 하나를 고치고 재생성하면 챗봇 행동이 바뀐다 — 그게 이 2층 구조의 목적이다.

### 지금 규모 (2026-09-01)

| | 국내ETF | 해외ETF | 국내채권 | 공모펀드 |
| :-- | --: | --: | --: | --: |
| `query_rules` | 39 | 21 | 31 | 31 |
| `answer_rules` | 25 | 21 | 17 | 21 |
| `synonyms` | 57 | 32 | 30 | — |

ETF 몫 query_rules 60개 중 24개는 **트리거식** — 질문에 관련 단어가 있을 때만 프롬프트에 실린다
(항상 실으면 11,760자 → 트리거식으로 5,800~6,300자. 단, 오답을 만드는 규칙 12개는 바꿔 말해도
빠지면 안 되므로 항상 싣는다 — "돈 제일 조금 떼가는" 이 '보수' 규칙을 놓치는 사고를 실측 후 복귀).

## 5. 규칙은 어떻게 만들어지나 — 실제 사례

규칙은 상상으로 쓰지 않는다. **결함을 먼저 관측하고, 실측으로 크기를 재고, 그 근거를 규칙 본문에 적는다.**

### 사례 — *"인버스 ETF 3개 알려줘"* (서버 실측 2026-08-31)

| 단계 | 내용 |
| :-- | :-- |
| **관측** | 1번 답이 ETN 이었다 — *KB 블룸버그 인버스 2X 천연가스 선물 **상장지수증권*** |
| **실측** | 인버스 조건 235건 중 **ETN 189건(80%)** · ETF 46건. 앞에서 3건 자르면 ETN 이 나오는 것이 구조적 |
| **규칙** | `query_rules.인버스` 본문에 *"질문이 인버스 **ETF** 면 `AND pd_grp_no='ETF'` 를 반드시 함께 건다"* 삽입 |
| **회귀** | `eval/questions_domestic_etfs.jsonl` 에 `ETF-D-025` 로 승격 (gold 3행) |

이 사이클이 문서 → yaml → 재생성 → 배포 → 재검증으로 돈다.
**규칙 본문에 실측 수치를 적어 두는 이유**는, 나중에 누가 규칙을 지우려 할 때 근거를 다시 재지 않아도 되게 하기 위해서다.

## 6. 왜 이렇게 만들었나 — 설계 판단 3가지

**① LLM 을 두 곳으로 제한했다.**
자연어→SQL 과 결과→문장만 맡긴다. 라우팅·개체매핑·거절 판정을 맡기면 재현이 안 되고, 틀렸을 때 고칠 자리가 없다.

**② 규칙을 코드가 아니라 데이터(yaml)로 뒀다.**
규칙이 코드에 있으면 도메인 담당이 못 고친다. yaml 이면 3명이 각자 자기 도메인을 고치고, 생성기가 검증한다.

**③ 문자열 매칭을 쓰되 실측으로 검증한다.**
컬럼이 있으면 컬럼을 쓴다. 이름을 쓰는 것은 **대응 컬럼이 없거나 값이 소실된 경우**뿐이고,
그때는 오탐·누락을 전수로 세어 규칙 본문에 적는다.

> 예 — 국내 인버스 235건은 배수 부호가 88% 소실돼 이름이 유일한 근거다.
> 전수 검토 결과 오탐 0·누락 0 을 확인했고, 그 표를 [`docs/rule_audit/`](rule_audit/README.md) 에 CSV 로 남겼다.
>
> 반대 사례 — 해외 영문 약어는 부분일치로 쓰면 안 된다.
> `AI` 는 865건 중 **811건(94%)이 오탐**(Ch**ai**nlink · D**ai**ly), `TR` 은 1,593건 중 14건만 진짜다.
> SQLite 에 단어경계 문법이 없어 구분자를 공백으로 바꿔 감싸는 형식을 쓰고,
> 정규식 단어경계와 **누락 0·오탐 0** 으로 일치함을 확인했다.
