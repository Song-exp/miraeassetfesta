```
        │                       = 4테이블 사이에 없는 조인 키 (A-Box)
        │
        └─ 워크샵 후 ────────▶  holdings 테이블 (as_of ≤ 2026-07-11)
```

| 산출물 | 무엇 | 왜 필요 |
| :--- | :--- | :--- |
| **`<domain>.yaml`** | 이 데이터셋의 품질 사실 | 0값·센티넬을 걸러야 Top-N이 안 오염됨 |

| **`kg_*` 테이블** | 정규명 ↔ 원본값 매핑 | **4테이블에 조인 키가 하나도 없음.** 교차 질의의 유일한 수단 |

```
                   ┌──────────▼──────────┐
  ontology.ttl ───▶│ 3. Route       코드 │   이 클래스에 이 속성이 있나?
                   └──┬────────┬───────┬─┘
              없음 ───┘        │       └─── 애매
                   │           │             │
        ┌──────────▼──┐        │      ┌──────▼──────┐
        │ 9. Deny     │        │      │ 8. Clarify  │  HCX 1회

                   │  ┌────────▼─────────┐   │
   .ttl + yaml ───▶│  │ 4. PlanSQL   HCX │   │  스키마 요약을 프롬프트에
                   │  └────────┬─────────┘   │
                   │  ┌────────▼─────────┐   │
      SQLite ─────▶│  │ 5. Execute   코드 │   │  ← 여기서 처음 수치가 나옴
                   │  └────────┬─────────┘   │
                   │  ┌────────▼─────────┐   │
        yaml ─────▶│  │ 6. Validate  코드 │   │  모수 · 화이트리스트 · 0건
                   │  └────────┬─────────┘   │
                   │  ┌────────▼─────────┐   │
        yaml ─────▶│  │ 7. Answer    HCX │   │  answer_policy
                   │  └────────┬─────────┘   │
                   └───────────┼─────────────┘
                               ▼
              { question_id, question, retrieved_context,
                think_trace, answer }
```

> 🔑 **HCX 호출은 경로당 최대 2회**(PlanSQL + Answer)이고, **기각 경로는 0회**입니다.
> 🔑 **판단은 전부 코드가 합니다.** LLM은 SQL 문자열을 만들고 문장을 쓸 뿐, **DB 커넥션도 없습니다.**
> 🔑 각 노드가 남긴 기록이 그대로 `think_trace` 가 됩니다 — **근거를 따로 지어낼 필요가 없습니다.**

> *"KODEX 200의 총보수 알려줘"*

```sql
SELECT cu_charge_rt FROM domestic_etfs WHERE TRIM(pd_abrv_nm)='KODEX 200';
-- ▶ 0.0        ← SQL은 정상적으로 값을 반환했습니다
```

| | 응답 |
| :--- | :--- |
| **yaml 없이** | ❌ *"KODEX 200의 총보수는 0%입니다."* — **환각.** 순자산 28조짜리 대표 ETF가 무보수일 리 없습니다 |
| **yaml 있으면** | ✅ *"데이터에 `0`으로 기록되어 있으나 이는 미입력값입니다. 국내 ETF 1,202종 중 총보수가 실제로 수록된 것은 **67종**뿐입니다."* |

```yaml
cu_charge_rt:
  missing_reason: missing
  answerable_n: 67                    # >0 67 / =0 150(미입력) / NULL 985
  answer_policy: "'보수 낮은 ETF' 질의는 cu_charge_rt > 0 로 한정하고 유효 모수 67건 명시."
  note: 배당형 상품명 113건도 보수 0 → 0=미입력 확증
```

> 🔴 **A·B·C는 조회가 실패해서 드러나지만, D는 조회가 성공합니다.**
> **같은 SQL 결과에서 정반대 답이 나오고, 차이는 전부 여러분이 지금 만드는 yaml에 있습니다.**

## 3. 🧩 구조 이해 — `yaml` / KG / `ttl` 이 각각 무엇을 하나

**이번 단계에 우리가 직접 만드는 건 `yaml` 하나뿐입니다.** 나머지 둘은 워크샵 이후에 만들지만,
**yaml을 채울 때 "이건 나중에 KG로 갈 값이구나"를 알고 적어야** 워크샵에서 바로 이어집니다.

### 3.1 판별 기준 — 세 줄

| 파일 | 담는 것 | 판별 질문 |
| :--- | :--- | :--- |
| **`ontology.ttl`** | 스키마 — *어떤 것이 존재할 수 있나* | **"데이터가 완벽했어도 참인가?"** → 예 |
| **KG** (SQLite 테이블) | 인스턴스 — *무엇이 실제로 있나* | **"이 값으로 다른 테이블을 찾아가나?"** → 예 |
| **`<domain>.yaml`** | 이 데이터셋의 품질 사실 | 위 둘이 **아니오** → 전부 여기 |

```
"ETF와 ETN은 다른 상품이다"              → 데이터 무관하게 참        → .ttl
"위험등급은 낮을수록 위험하다"             → 데이터 무관하게 참        → .ttl
"삼성자산운용이 KODEX 200을 운용한다"      → 사실, 테이블을 이어줌     → KG
"cu_charge_rt 의 0은 미입력이다"          → 이 데이터셋에서만 참      → yaml
"국내ETF 총보수 유효 모수는 67건이다"       → 이 데이터셋에서만 참      → yaml
```

> 🔴 **"범주형이면 KG"가 아닙니다.** 범주형 컬럼 대부분은 한 테이블 전용이라 SQL이 바로 처리합니다.
> KG로 가는 건 **여러 테이블에 걸치면서 표기가 다른 값**뿐입니다 (운용사·지수·지역·자산군·위험등급·통화 6종).
> 펀드 `or_attr_desc`(11종)는 범주형이지만 펀드에만 있어서 **KG에 안 갑니다.**

### 3.2 같은 개념이 셋으로 나뉘는 모습 — **위험등급 예시**

한 개념을 셋이 나눠 갖는 게 어떤 모양인지 보시면 감이 잡힙니다.

**① `ontology.ttl` — 스키마 (워크샵 후 작성)**

```turtle
:riskGrade a owl:DatatypeProperty ;
    rdfs:domain :FinancialProduct ;
    rdfs:range  xsd:integer ;
    :minValue 0 ; :maxValue 6 ;
    rdfs:comment "낮을수록 위험. 1=매우높은위험, 6=매우낮은위험" .

:OverseasETF rdfs:subClassOf [
    a owl:Restriction ;
    owl:onProperty :riskGrade ;
    owl:cardinality 0                # 🔴 해외ETF엔 위험등급이 없다
] .
```

→ *"위험등급 낮은 해외 ETF 알려줘"* 가 **HCX 호출 0회로 즉시 기각**되는 근거.

**② KG — 인스턴스 매핑 (워크샵 후 작성, SQLite 테이블)**

```
kg_riskgrade
┌────────┬─────────────────┬───────────────────────┬──────────────────┐
│ 정규값 │ table_name      │ column_name           │ raw_value        │
├────────┼─────────────────┼───────────────────────┼──────────────────┤
│   3    │ domestic_bonds  │ PD_RISK_GCD           │ 3                │
│   3    │ domestic_etfs   │ pd_risk_cd            │ PD_RISK_GCD_13   │
│   3    │ public_funds    │ zrin_fd_ivst_risk_gcd │ 3.0              │
└────────┴─────────────────┴───────────────────────┴──────────────────┘
```

### 3.3 한 질의에서 셋이 도는 순서

```

③ yaml  query_rules.ETF만      → AND pd_grp_no='ETF'
        query_rules.수익률정상 → AND du_er_1y > -100
④ SQL   SELECT ... ORDER BY du_er_1y DESC LIMIT 3       ← 여기서 처음 수치가 나옴
⑤ HCX   결과 3행 + 근거로 문장 생성
```

### 5.1 `ontology/enums/<domain>.yaml` — 이번 단계의 주 산출물

**완료 판정 기준입니다.** *"EDA 마무리"* 는 판정이 안 되지만 **파일 4개**는 됩니다.

#### 필드별 의미 — 무슨 값을 넣나

| 키 | 필수 | 값 | 뜻 |
| :--- | :-: | :--- | :--- |
| `domain` | ✅ | 테이블명 | |
| `columns.<col>.korean_name` | ✅ | 문자열 | `schema_metadata` 또는 원본 `Sheet1_Schema` |
| `columns.<col>.missing_reason` | ✅ | `not_applicable` / `missing` / `mixed` / `none` | **① 결측 판정** |
| `columns.<col>.missing_semantics` | 센티넬 있으면 | `{값: 판정}` | `NULL` 아닌 위장 결측 |
| `columns.<col>.answerable_n` | 결측 있으면 | 정수 | **유효 모수.** 답변에 명시할 숫자 |
| `columns.<col>.answer_policy` | ✅ | 문장 | **결측일 때 뭐라고 답할지** |
| `columns.<col>.unit` | 수치형 ✅ | `percent` `krw` `usd` `days` `grade` `count` | **③ 층위** |
| `columns.<col>.layer` | 교차축이면 | `{scale, direction, note}` | **③ 층위** — 다른 테이블과 비교 가능한가 |
| `columns.<col>.value_semantics` | 범주형 ✅ | `{값: 뜻}` | **② 범주형 해독** |
| `columns.<col>.kg_entity` | 해당되면 | 개체명 | 이 컬럼 값이 KG 개체가 됨 (6종만) |
| `columns.<col>.note` | ✅ | 근거 + **건수** | 판정 근거 |
| `query_rules.<이름>` | ✅ | SQL 조건 | 모든 질의에 항상 붙는 필터 |
| `axis_derivation` | 축 있으면 | `confirmed` / `pending_workshop` | 파생 컬럼이 아니라 **규칙으로** |

## 6. 🔍 추가 데이터 발굴 — **채권·펀드도 반드시**

### 6.1 발굴 방법 — yaml을 채우다 자연히 나옵니다

```
① 컬럼을 채우다 "이 코드가 무슨 뜻인지 모르겠다"          → 코드북 후보

④ 층위를 적으려는데 "단위를 모르겠다"                     → 원본 schema 확인
```
