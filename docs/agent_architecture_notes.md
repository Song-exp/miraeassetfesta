# 🧩 Agent 아키텍처 참고 노트 — 그래프 엔지니어링 적용 검토

> **성격: 참고용 설계 노트입니다. 확정된 규칙이 아닙니다.**
> 3단계(에이전트 핵심 로직 개발)에 착수할 때 이 문서를 출발점으로 삼되,
> 실측치(특히 HCX 레이턴시)에 따라 얼마든지 바뀔 수 있습니다.
> 확정 규칙은 `.agents/rules/miraeasset-rules.md`에 있습니다.

---

## 1. 왜 이 검토를 남기나

에이전트를 **단일 프롬프트 1회 호출**로 만들지, **여러 노드로 쪼갠 그래프**로 만들지는
개발 착수 시점에 되돌리기 어려운 결정입니다. 그래프 엔지니어링(Node / Edge / State / Condition)
관점에서 우리 과제 조건에 맞는 것과 안 맞는 것을 미리 갈라둡니다.

**우리 과제의 제약 조건 4가지**가 판단 기준입니다:

| 제약 | 출처 | 함의 |
| :--- | :--- | :--- |
| 응답 15초 목표 / 60초 초과 감점 | 배점·SLA | 노드가 늘수록 레이턴시 증가 — LLM 호출 노드 수가 상한을 가짐 |
| `think_trace` · `retrieved_context` 응답 필수 | API 스키마 | 실행 과정을 **기록**할 구조가 필요 |
| 환각 시 대형 감점 | 멘토 경고 | 검증을 LLM에 맡기면 안 됨 |
| Single-turn Q&A (cURL 단발) | 평가 방식 | 런타임에 사람이 개입할 수 없음 |

## 2. 4대 패턴 채택 판단

| 패턴 | 판단 | 이유 |
| :--- | :---: | :--- |
| **Router** | ✅ **채택** | 상품군 5분기 × 의도 8분기가 이미 필요. 규정상 인텐트 분석은 LLM 없이 코드로 가능 → 레이턴시 0, 결정론적 |
| **결정론적 검증 레이어** | ✅ **채택** | 환각 방지가 최대 감점 요인. 규칙 문서의 *"조회 결과 없으면 HCX 호출 건너뛰고 즉시 반환"* 이 곧 이 패턴 |
| **Generator-Evaluator Loop** | ⚠️ **범위 한정** | SQL 생성 단계에만. 최종 답변 재생성 루프는 레이턴시 예산 초과 (§5) |
| **Parallel Execution** | ❌ **보류** | 병목이 HCX 호출이고 SQLite 조회는 0.001초 — 병렬화해도 절약 없음 (§6) |
| **Human-in-the-Loop** | ❌ **런타임 불가** | Single-turn 평가. 단 개발 시점 활용은 유효 (§7) |

## 3. 가장 큰 이득: State 로깅이 곧 `think_trace`

**단일 프롬프트 구조의 문제** — `think_trace`를 채우려면 LLM에게 "생각한 과정을 써줘"라고 시켜야 하는데,
그건 **사후 합리화**입니다. 실제 실행 경로와 무관한 그럴듯한 서사가 나오고, 그 자체가 환각입니다.

**그래프 구조에서는 지어낼 필요가 없습니다.** State에 각 노드가 누적한 기록이 그대로 근거가 됩니다.

```
state.trace.append(NodeTrace(node, decision, sql, row_count, elapsed_ms))

→ think_trace        = render_trace(state.trace)
→ retrieved_context  = render_evidence(state.evidence)
```

> ⚠️ `think_trace`는 **사람이 읽는 필드**입니다. raw 로그를 그대로 덤프하면 오히려 감점 요인이므로
> 렌더링 계층을 따로 둡니다. 로그 원본은 서버 로그로, 응답에는 정제된 서술을 넣습니다.

State는 **API 응답 4필드와 1:1로 대응하도록** 설계하면 응답 조립이 공짜가 됩니다.

## 4. 역할 분담: 무엇을 코드가, 무엇을 HCX가

이 표가 이 문서에서 가장 실무적으로 쓰일 부분입니다.

### 코드가 결정론적으로 판단 (LLM 호출 없음)

| 검증 항목 | 판정 근거 | 비고 |
| :--- | :--- | :--- |
| 종목 존재 여부 | 정규화 종목명 인덱스 | ⚠️ `TRIM` 필수 — `PD_NM` 패딩 1,396건 |
| 등급 화이트리스트 | `CRD_GRD` 20종 / `risk_grade` 0~6 | `AAAA` 즉시 기각 |
| 결측 모수 임계 | `enums.yaml`의 `answerable_n` | 국내ETF 총보수 **67건**(non-null 217 중 150건이 0), 채권 매수수익률 881건 |
| 기준일 위반 | 질의 내 2026-07-11 이후 시점 언급 | |
| SQL 안전성 | `SELECT`만 허용 · 컬럼 화이트리스트 · `LIMIT` 강제 | |
| 결과 0건 | 실행 후 row count | → LLM 호출 없이 `unanswerable` 종료 |
| 응답 스키마 | 4필드 존재·타입 | |

### HCX가 판단 (추론·맥락 필요)

| 항목 | 비고 |
| :--- | :--- |
| 질의의 애매성 → `clarify` 분기 여부 | 코드로는 어려움. "안전한 ETF 추천해줘" 류 |
| SQL 계획 수립 | 조건이 복합적일 때 |
| 최종 답변 문장 생성 | 규정상 **HCX 고정** |
| 비교·설명 서술 | |

> **원칙: LLM에게 자가검증을 시키지 않습니다.** 환각을 환각으로 잡을 수 없습니다.
> 검증은 전부 코드로 내리고, LLM은 검증을 통과한 데이터로 문장만 만듭니다.

## 5. 노드 그래프 스케치 (초안)

```
                 [질의 입력]
                      │
              ┌───────▼────────┐
              │ 1. Normalize   │  코드  ─ TRIM / 전각·자모 정규화
              └───────┬────────┘
              ┌───────▼────────┐
              │ 2. Ground      │  코드  ─ ontology/axes 사전으로 축 그라운딩
              └───────┬────────┘         (운용사·자산군·지역·등급·통화·지수)
              ┌───────▼────────┐
              │ 3. Route       │  코드  ─ 상품군 × qtype 판정
              └───────┬────────┘
        ┌─────────────┼──────────────┐
        │             │              │
   [존재검증 실패]  [정상]      [애매·조건부족]
        │             │              │
        ▼             ▼              ▼
  ┌──────────┐  ┌──────────┐   ┌──────────┐
  │ 9. Deny  │  │4. PlanSQL│HCX│8. Clarify│ HCX
  │(LLM 우회)│  └────┬─────┘   └────┬─────┘
  └────┬─────┘       │              │
       │        ┌────▼─────┐        │
       │        │5. Execute│  코드   │
       │        └────┬─────┘        │
       │             │  ◄──┐        │
       │        ┌────▼─────┴──┐     │   재시도 ≤2 & 누적 ≤12s
       │        │6. Validate  │ 코드│   ─ 0건? 스키마? 모수?
       │        └────┬────────┘     │
       │             │              │
       │        ┌────▼─────┐        │
       │        │7. Answer │  HCX   │
       │        └────┬─────┘        │
       └─────────────┼──────────────┘
                     ▼
          [State → JSON 4필드 조립]
```

**설계 의도**

- **HCX 호출은 경로당 최대 2회** (PlanSQL + Answer). 존재검증 실패 경로는 **0회**.
- 노드 9개 — 과분할하면 노드 경계마다 정보가 손실되므로 이 정도가 상한입니다.
- `9. Deny`(확인할 수 없음)와 `8. Clarify`(역질문)를 **별도 종료 노드**로 분리합니다.
  과제 명세는 *"확인할 수 없음 명시"* 와 *"필요한 조건을 역질문"* 을 다른 요구사항으로 적고 있습니다.

### 루프와 종료 조건 (반드시 코드로 강제)

자료에서는 DAG라고 표현하지만 **Generator-Evaluator는 사이클입니다.** 사이클이 생기는 순간
종료 보장이 공짜가 아니게 되므로, 두 가지를 코드로 못박습니다:

| 가드 | 값 | 이유 |
| :--- | :--- | :--- |
| 최대 재시도 | **2회** | 무한 루프 방지 |
| 누적 시간 예산 | **12초** 초과 시 루프 중단, 현재 최선으로 응답 | 60초 초과가 감점이므로 절대 방어선 |

**루프를 어디에 두느냐가 핵심입니다:**

| 루프 위치 | 재시도 1회 비용 | 판정 |
| :--- | :--- | :---: |
| SQL 생성 후 (`5→6→4`) | 실행이 0.001초 — 문법 오류·컬럼 없음·0건이 즉시 드러남 | ✅ |
| 최종 답변 생성 후 | 평가 LLM 1회 + 재생성 1회 = **+2회 호출** | ❌ |

## 6. Parallel Execution을 보류하는 이유

우리 병목은 **HCX 호출(수 초)** 이고 SQLite 조회는 0.001초입니다. 4개 테이블을 병렬로 쳐도
절약되는 시간이 사실상 0이고, 복잡도만 늘어납니다.

**다만 병렬화가 값어치를 갖는 지점이 하나 있습니다 — 레이턴시가 아니라 리콜입니다.**

엔티티 링킹을 `정확일치 / FTS5 / 유사도` 3가지로 동시에 시도해 결과를 합치는 구조는 실제로 필요합니다.
패딩(§ EDA_GUIDE 6-①)과 표기 흔들림 때문에 정확일치 하나로는 종목을 자주 놓치고,
놓치면 **잘못된 `확인할 수 없음`** 이 나갑니다. 목적이 "빠르게"가 아니라 "놓치지 않게"로 바뀝니다.

---

## 7. Human-in-the-Loop — 런타임 불가, 개발 시점엔 유효

평가는 cURL 단발 호출이므로 승인 노드에서 사람을 기다리면 타임아웃입니다.
그러나 두 가지 형태로 살아남습니다:

1. **`clarify` 분기 = HITL의 단일턴 버전.** 되묻고 그 응답으로 끝나는 **종료 노드**이지 대기 노드가 아닙니다.
2. **개발 시점 HITL — 지금 우리에게 특히 중요합니다.**
   주최 측 예시 질의셋이 **제공되지 않는 것으로 확정**되어, 자체 80문항이 유일한 기준입니다.
   80문항을 돌리고 사람이 답변을 채점 → 통과한 답변을 **few-shot 예시로 승격**하는 루프가
   사실상 우리의 유일한 품질 개선 수단입니다.

## 8. 프레임워크는 얹지 않는 방향 (LangGraph 등)

| | 프레임워크 도입 | 순수 Python |
| :--- | :---: | :---: |
| 노드 / State / 조건부 엣지 | ✅ | ✅ (함수 + dataclass + 디스패치 테이블) |
| 체크포인팅 · 재개 · 스트리밍 · 멀티턴 | ✅ | ❌ |
| **우리가 그 기능이 필요한가** | — | **아니오 — 단일턴 15초** |
| Dockerfile 재현성 (배점 항목) | 생태계 버전 깨짐 잦음 | 의존성 최소 |
| HCX 연동 | 커스텀 래퍼 필요 (기본 통합은 타사 전제) | `httpx` 직접 호출 |

프레임워크의 진짜 값어치는 **체크포인팅·재개·스트리밍·멀티턴**인데 우리는 전부 안 씁니다.
노드 9개짜리 그래프에 얹어서 얻는 건 다이어그램 자동 생성 정도이고, 잃는 건 의존성 리스크입니다.

> **규정 확인:** LangGraph는 LLM이 아니라 오케스트레이션 라이브러리이므로 *"HCX만 사용"* 규정 위반은 아닙니다.
> 보류 사유는 순전히 **재현성과 구현 비용**입니다.

## 9. 개발 착수 전에 반드시 측정할 것

### 🔢 HCX-005 호출 1회의 p95 레이턴시

**이 숫자 하나가 위 그래프의 모양을 결정합니다.** API 키를 받는 즉시 측정하세요.

| 실측 p95 | 가능한 구조 |
| :--- | :--- |
| ~2초 | 호출 2회 + 재시도 여유까지 가능 (위 스케치 그대로) |
| ~5초 | 호출 2회가 상한. 재시도는 SQL 단계에만 |
| 8초 이상 | **호출 1회 구조로 재설계.** PlanSQL을 룰 기반으로 내려야 함 |

같이 측정할 것: 입력 토큰 길이에 따른 레이턴시 변화 (→ `retrieved_context` 크기 상한 결정),
동시 호출 시 rate limit.

## 10. 요약

- **채택**: Router / 결정론적 검증 레이어 / State 로깅 → `think_trace`
- **범위 한정**: Generator-Evaluator 루프는 **SQL 단계에만**, 재시도 2회 + 12초 예산
- **보류**: Parallel (레이턴시 이득 없음 — 단 엔티티 링킹 리콜 목적은 별개)
- **런타임 불가**: HITL (단 개발 시점 few-shot 구축용으로는 채택)
- **프레임워크**: 얹지 않고 개념만 차용
- **선행 측정**: HCX p95 레이턴시
