# HCX 레이턴시·처리량 실측 — 지시서 §4.3 ① (워크샵 제출물)

> **측정 2026-08-14 · 담당 Song-exp · 테스트 API 키 · temperature=0 · 순차 호출**
>
> 원시 데이터
> - `hcx_latency_full3x3.json` — 전체 매트릭스 (설정 3종 × 입력 3종 × 10회 = 90콜, 90/90 성공)
> - `hcx_latency_tail_n40.json` — 꼬리 특성 (설정 2종 × 입력 2종 × 40회 = 160콜, 160/160 성공)
>
> 재현: `python scripts/bench_hcx.py --n 10 --concurrency 8 --tag full3x3`

---

## 결론 3줄

1. **`HCX-005` · `HCX-007(none)` 모두 p95 ~2초** → 지시서 분기표 최상단. **PlanSQL을 LLM으로 두는 설계 유지 가능. 전면 재설계 불필요.**
2. **`HCX-007(low)` 탈락** — 단일 호출 7.5~17.6초. 게다가 지연이 입력 크기에 단조롭지 않아 **예산 자체를 세울 수 없음.**
3. **병목은 레이턴시가 아니라 rate limit** — 입력 8,159토큰에서도 1.9초지만, 토큰 한도 때문에 **분당 질의 3.6개**가 천장.

| 설정 | 입력 | 입력토큰 | p50 | **p95** | max | 생성 | 사고 |

| `HCX-005` | small | 51 | 1.39 | **7.94** ⚠️ | 11.27 | 45 | — |
| `HCX-005` | medium | 2,735 | 1.37 | **1.79** | 1.83 | 42 | — |
| `HCX-005` | large | 8,159 | 1.94 | **2.15** | 2.28 | 60 | — |
| `HCX-007(none)` | small | 51 | 0.71 | **0.89** | 1.02 | 30 | — |
| `HCX-007(none)` | medium | 2,735 | 1.41 | **1.68** | 1.80 | 64 | — |
| `HCX-007(none)` | large | 8,159 | 1.60 | **2.17** | 2.18 | 74 | — |
| `HCX-007(low)` | small | 51 | 7.80 | **9.90** | 10.02 | 467 | 403 |

⚠️ `005/small` p95 7.94는 **11.27초 단발 이상치 1건** 때문입니다. §2에서 재측정했습니다.

### 🔴 007(low) 의 비단조성

```
medium (2,735토큰)  →  17.49초   사고토큰 816
large  (8,159토큰)  →   7.55초   사고토큰 335
                          ↑ 입력이 3배인데 2배 빠름
```

컨텍스트가 충분하면 덜 생각합니다. **입력 크기로 지연을 예측할 수 없다**는 뜻이고,
15초 예산을 관리해야 하는 구조에서는 느린 것보다 이쪽이 더 결격입니다.

## 2. 꼬리 특성 (n=40, 160/160 성공)

| 설정 | 입력 | p50 | **p95** | p99 | max | 3초 초과 |
| :--- | :--- | ---: | ---: | ---: | ---: | ---: |
| `HCX-005` | small | 1.27 | **2.17** | 3.44 | 3.48 | 2건 (3.5 · 3.4) |
| `HCX-005` | medium | 1.32 | **1.85** | 2.05 | 2.47 | 0건 |
| `HCX-007(none)` | small | 0.78 | **0.95** | 0.96 | 1.03 | 0건 |
| `HCX-007(none)` | medium | 1.25 | **1.58** | 1.61 | 1.79 | 0건 |

**11초는 재현되지 않았습니다** (추가 40회). 누적 50회 중 1건이므로 **~2% 확률의 서버측 단발 스파이크**로 봅니다.
최악의 경우(11초 + 2초 = 13초)에도 15초 안이지만 **여유가 없습니다** → 재시도 예산을 여기에 쓰면 안 됩니다.

### 🔑 005 vs 007(none) — 꼬리가 가릅니다

```
누적 80표본 max      005 → 3.48초        007(none) → 1.79초
누적 50표본 이상치   005 → 11.27초 1건    007(none) → 없음
```

중앙값·p95는 사실상 동률이지만 **007(none) 의 분산이 일관되게 작습니다.**
15초 예산은 평균이 아니라 꼬리로 깨지므로 이 차이는 실질적입니다.

## 4. 🔴 테스트 API 키 한도 — 응답 헤더 실측

```
x-ratelimit-limit-requests:     60  / 60s
x-ratelimit-limit-tokens:   60,000  / 60s      ← 이쪽이 먼저 걸립니다
```

요청 수는 넉넉한데 토큰이 병목입니다. **컨텍스트 크기가 곧 처리량 상한**입니다.

| `retrieved_context` | 호출당 토큰 | 분당 호출 | **분당 질의**(경로당 2회) | 30문항 소요 |
| :--- | ---: | ---: | ---: | ---: |
| 질의만 (51) | ~91 | 60 (요청한도) | 30 | 1분 |
| ETF yaml (2,735) | ~2,777 | 21 | **10.8** | ~3분 |
| ETF+펀드 yaml (8,159) | ~8,219 | 7 | **3.6** | 🔴 8분+ |

> 📌 지시서 §4.3 ①은 이 항목을 *"입력 토큰 길이별 레이턴시 변화 → `retrieved_context` 상한"* 으로 잡았습니다.
> **실측 결과 레이턴시로는 상한이 정해지지 않습니다** (51→8,159토큰에 1.4→1.9초).
> 상한을 정하는 것은 rate limit입니다. → **"레이턴시 예산" 이 아니라 "처리량 예산" 문제로 프레이밍을 바꿔야 합니다.**

### ⚠️ 미확인 — 서비스 API 키 한도

위 수치는 **전부 테스트 키 기준**입니다. 주최측 오토배치가 30문항을 어떤 간격으로 호출하는지 모르는 상태이므로,
서비스 키 한도 확인이 필요합니다. 서비스 키가 더 높다면 **서비스 앱 등록이 선택이 아니라 필수**가 됩니다.

## 5. 판정

```
p95 ~2초   호출 2회 + 재시도 여유          ← ✅ 005 · 007(none) 둘 다 여기
p95 ~5초   호출 2회가 상한
p95 8초+   🔴 PlanSQL 룰 기반 전면 재설계   ← 007(low) 를 골랐다면 여기
```
