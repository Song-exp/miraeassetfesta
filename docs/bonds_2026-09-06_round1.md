## ④ 구조적 관찰

### 응답 시간 분해 — 파이프라인이 아니라 HCX 호출 대기다

- 50초 이상 26문항의 think_trace 에는 **재생성·값 검사 실패·HCX 답변 생성 같은 추가 단계가 없다**: 26건 중 22건이 `[Plan] SQL 생성` 1회 + 기계 조립(HCX 0회) 경로이고, 나머지 4건(D-037·D-045·D-052·U-035)의 재생성 시작 시점 `누적` 은 1.1~3.4s 다. 즉 1차 HCX 호출이 1~3초에 끝났고 나머지 50초대는 **두 번째 호출(또는 유일한 호출) 안에서** 났다.
- 느린 문항의 위치가 주기적이다: 실측 순번 4·7·10·13·16·20·24·27·30·33·35·37·40·43·45·47·51·55·58·61·64·68·71·74·83·87 — 빠른 문항 2~3개(각 1~3초) 뒤에 55초대 하나가 반복된다. 배포 코드 `src/hcx/client.py` 는 HTTP 429 에 `max(reset_tokens_s, reset_requests_s, retry_wait_s=20.0)` 만큼 잠들고 최대 3회 재시도한다. 28.4k자 근거문서 × 분당 토큰 한도에 걸려 **분 창(60s) 잔여 시간만큼 대기**하는 모양과 일치한다. 이 가설을 확정할 마커가 trace 에 없다(HCXResult.retries·rate_limit 이 기록되지 않음) — BP ④.
- 재생성이 붙은 문항은 60초를 넘길 확률이 높다(D-037 60.4·D-052 62.1·S-004 76.7·UT-091 75.1). 재생성 절약(F1·BD·BP②③)이 곧 타임아웃 회피다.
- 재생성이 **같은 문장을 되풀이한** 사례(#87 유형) 6건: D-010·D-027·A-043·S-004·UT-094(글자 하나 안 바뀜) · U-035('삼성전자'→'(주)삼성전자', 같은 부재값). 전부 HCX 호출 1회를 그냥 버렸다.

### 결정층이 잡지 못한 HCX 자유도

- ❌ 17건 중 13건의 1차 원인은 HCX 가 규칙과 다른 SQL 을 낸 것이다. 규칙은 전부 yaml 에 선언돼 있다(코코본드 판정식·통안채 동의어·등급 다의어·고위험제외·할인채). "선언만 있고 가드가 없으면 안 지켜진다"가 다시 확인됐다 — §③(가)는 전부 강제 부착이다.
- HCX 가 **컬럼과 값의 소속을 자주 틀린다**: `std_pd_mcls_nm='국고채'`(D-027·A-043) · `bd_knd='회사채'`(D-052·UT-094) · `bd_knd='일반회사채'`(UT-091) · `bd_knd IN ('전환사채')`(D-019) · `mtco_itm_no`(S-004) · `bd_nm`(D-019). F1 은 '주인 있는 값' 만 고친다 — 나머지 셋(주인 없는 값·환각 컬럼·GROUP BY)은 BC·BD.
- S-009 '원금 잃기 싫은데' 는 가드 사각인데 HCX 가 '16' 단독을 냈다 — 정답이지만 가드 없이 맞은 것이라 다음 실측에서 뒤집힐 수 있다.
- D-003 은 조회 질의인데 조립기 머리줄이 '수익률 높은 순 상위 5개' 로 나간다 — HCX 가 ORDER BY/LIMIT 5 를 임의로 넣었고 기본 TOP-N 가드는 그대로 통과시켰다(값은 맞음).
