## 2. 원인 — 분당 토큰 한도(429) 대기

`src/hcx/client.py` 의 실측 주석: **60 requests/60s · 60,000 tokens/60s**(테스트 키 2026-08-14). 재시도 정책: 429 이면 `max(reset_tokens, reset_requests, 20초)` 만큼 `time.sleep` 후 재호출, 최대 3회. 요청 timeout 60초.

근거문서 크기(로컬 재조립, 채권 단일 테이블):

| 블록 | 글자 수 |

| 도메인 규칙 (`ontology/enums/domestic_bonds.yaml` 61개 항목) | **24,069** |

한글 11,700자 + 영문·기호 16,700자. 한도 60,000토큰/분에서 "3번 빠르고 1번 막힘" 이 나오려면 **호출당 15,000~20,000토큰**이어야 하고, 이 문서 크기와 맞는다. 순차 호출이라도 답이 1.7초에 끝나면 분당 30문항 이상이 들어오므로 3~4번째 호출마다 토큰 창이 바닥나고, 창이 리셋되는 시각까지(최대 60초) 잠든다. 그 뒤 재호출 1.5초 → 총 53~77초.

**주최 평가도 같은 조건이다.** 주최는 순차 1건씩 호출한다고 했고, 우리 답이 빠를수록 호출 간격이 짧아져 같은 벽에 부딪힌다. 정답률을 올려도 3~4문항마다 하나가 60초 근처로 가면 시간 감점이 남는다.

확정되지 않은 것: 서버가 실제로 받은 `x-ratelimit-limit-tokens` 값(운영 키 등급). trace 에 429 재시도 횟수가 기록되지 않아 헤더값을 못 봤다 — 라운드1 수리 BP④(429 대기·재시도 횟수 `[Plan]` 마커 기록)가 붙으면 다음 실측에서 확정된다.

## 3. 줄이는 방법 — 네 층, 효과와 비용

토큰 예산 식: `분당 호출 가능 수 = 60,000 / 호출당 토큰`. 지금 약 3회. 목표는 "주최가 어떤 간격으로 던져도 60초를 넘기지 않는 것" 이며, 이는 **① 호출당 토큰을 줄이고 ② 그래도 막히면 기다리지 않고 다른 길로 답하는 것** 두 가지를 같이 해야 한다.

### 3.1 [즉시 · 코드만 · 리드 결정] 429 대기 정책 — 기다리지 말고 예산 안에서 끝낸다 (`src/hcx/client.py`)

| 항목 | 지금 | 제안 | 효과 |
| :-- | :-- | :-- | :-- |
| 대기 하한 20초 | `max(reset, 20)` | 헤더 `reset` 값 그대로(하한 0) | reset 이 5초인데 20초 자는 낭비 제거 |
| 문항 예산 | 없음(60초 timeout × 최대 3회 재시도 = 이론상 180초) | **문항 시작 후 45초 예산**. `reset` 이 남은 예산을 넘으면 자지 않고 즉시 폴백 | 60초 초과 0건 보장(폴백이 있을 때) |
| 사전 판단 | 429 를 받아야 안다 | 직전 응답 헤더 `remaining_tokens` < 예상 토큰이면 호출 전에 폴백 결정 | 429 왕복 1회 절약 |

폴백이 없으면 이 층만으로는 "빨리 틀리는" 것이라 3.3 과 짝이다.

### 3.2 [프롬프트 절감 · 선언 필요 · 리드 결정] 규칙 24k자를 질문 유형별로 싣는다

- 이미 있는 기계: R-2 `triggered` 규칙(질문에 트리거 낱말이 있을 때만 싣는다). 채권 61개 규칙 중 **triggered 는 2개**(만기구간·투기등급)뿐이고 59개는 항상 실린다. 문서 머리에도 "일부는 이 질문과 무관할 수 있다" 고 적혀 있다.
- 제안: 규칙을 두 층으로 나눈다. **항상 층**(대표행·기본모수·구매가능·위험등급방향·등급서열·고위험제외·범주형 실제 값·동의어 — 어떤 채권 질문에도 걸리는 것, 약 6~8k자) + **트리거 층**(만기윈도우·신용보강·종류비교·가격축·시장집계금지·판매행·구조표시·ESG·발행 시점 … 질문 낱말이 있을 때만). 트리거 낱말은 규칙마다 `triggers:` 로 yaml 에 선언한다 — **온톨로지 선언 변경이라 리드 결정**이다(4도메인 영향 없음, `domestic_bonds.yaml` 전용. 단 이 문서가 바뀌면 SQL 생성 결과가 바뀌므로 정답률 재검이 필수).
- 기대: 28k → 약 10~12k자(호출당 6~8k토큰) → 분당 **7~10회**. 60초 초과는 크게 줄지만 주최가 분당 10문항 이상 던지면 여전히 막힌다. 그래서 3.3 없이는 완결이 아니다.
- 검증 도구가 이미 있다: `eval/run_paired.py` (RULES_MODE=full vs layered, McNemar). 평가 기간 밖에 채권 54문항으로 돌려 정답률 손실 0 을 확인하고 넣는다.
- 부수 절감: 플래너 system 2.5k자 · 스키마 블록의 컬럼 설명 압축 · 규칙 문장 안의 실측 사연("2026-09-02 실측 …") 은 HCX 에겐 근거가 아니라 잡음 — 이 문서에서만 빼고 yaml 주석에 남기면 2~3k자 더 준다.

### 3.3 [근본 · 설계 변경 · 리드 결정] HCX 0회 경로 확대 — 자주 나오는 문형은 결정층이 SQL 을 조립한다

- 지금도 답변은 기계 조립(HCX 0회)이고, HCX 는 **SQL 초안 한 번**에만 쓴다. 그런데 그 초안은 가드 10여 개가 거의 다시 쓴다(trace 의 [Guard] 줄: 종류 교정·창 확정·대표행·정렬·고위험제외·SELECT 보강…). 즉 채권 문형 다수에서 HCX 가 기여하는 것은 "어떤 컬럼을 어느 방향으로" 정도다.
- 제안: 라우터·Ground·게이트가 이미 뽑는 슬롯(종류 확정식 · 등급 서열 · 위험등급 · 만기/발행 창 · 정렬축·방향 · TOP-N · 집계/목록 여부)이 **전부 채워지는 문형**은 템플릿으로 SQL 을 조립하고 HCX 를 건너뛴다. 슬롯이 비거나 모르는 낱말이 있으면 종전처럼 HCX 로 간다(폴백 방향이 반대인 점이 핵심 — 3.1 의 폴백으로도 쓴다).
- 대상 문형(87문항 기준 대략): 종류·등급·위험등급별 **개수**(A-008·042~044·059·D-029·D-039~041 …) · 조건 **목록/TOP-N**(D-001·003·004·007·012·025~028·033·034·S-001~004 …) · **사실확인**(D-021·030·031). 게이트 즉답 13건을 합치면 **60% 안팎이 HCX 0회**가 될 수 있고, 그 문항들은 1초대에 끝나며 429 노출도 없다.
- 비용: 템플릿 조립기 모듈 + 슬롯 완결성 판정 + 회귀 테스트. 이번 라운드 수리(BA·BB·BE 종류 확정식, BI 안전 등급, BL 창) 가 그 슬롯을 더 확정해 주므로 다음 단계로 자연스럽다. 정답률 위험은 낮다(가드가 이미 같은 확정식을 강제하고 있다) — 오히려 HCX 자유도가 사라져 재생성·환각 사고가 줄어든다.
