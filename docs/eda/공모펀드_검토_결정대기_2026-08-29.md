## 1. 결정 §7-1 — 외부 조인 키 교체 (`ext_fund_holdings.grp` → `itm_no`) · 대응 ❌3 (A-3-03)

### 상황
현재 런타임과 gold가 `ext_fund_holdings`를 **`grp = mtco_itm_no`로 조인**한다. `grp`가 전역 유일이 아니어서 **103개 grp가 복수 운용사에 오부착**된다고 문서가 보고한다(최악 `grp='00'`이 34개 운용사·138클래스). 이대로면 "삼성전자 담은 펀드" 류 **교차 질의에 다른 운용사 펀드가 섞여 오답**이 난다. HANDOFF §1-1에서 교차질의 조인 키 오류가 실제 런타임 버그(`OperationalError`, 오답)로 잡혔던 계열과 같은 위험이다.

### 검증된 사실 (이 세션)
- `src/runtime/pipeline.py`의 `JOIN_KEYS`에 `("ext_fund_holdings", "ext_fund_holdings.grp = public_funds.mtco_itm_no")`가 실재함을 코드로 확인.

### 미검증 → 재현됨 (2026-08-29 DB 실측)
- "103개 grp 복수 운용사" → **103 재현 확인**. ("grp=mtco raw 조인 2,898/2,902"는 미재현 — 실행 시 확인)

### 무엇을 정해야 하나
`ext_fund_holdings` 조인을 `grp=mtco_itm_no` → **대표 클래스 `itm_no` 경유**로 바꿀지. 바꾸면 안전하지만, "형제 클래스 비중 확장"을 어떻게 재현할지(`(or_co, zfill한 mtco)` 정규화 경로)를 함께 정해야 한다.

### 정해지면 실행할 조치 (2곳 — 런타임 + gold)
- `src/runtime/pipeline.py` JOIN_KEYS:
  - `ext_fund_holdings.grp = public_funds.mtco_itm_no` → `ext_fund_holdings.itm_no = public_funds.itm_no`
- `eval/questions_cross_and_unanswerable.jsonl`의 `CROSS-001.gold_sql`:
  - `JOIN ext_fund_holdings h ON h.grp=p.mtco_itm_no` → `JOIN ext_fund_holdings h ON h.itm_no=p.itm_no`
- `grp` 컬럼은 삭제하지 않고 **검증용으로 유지**.

### 실행 전 검증
1. DB 확보 후 검토기록 §5의 "103개 grp" SQL 재현.
2. 변경 후 `python eval/run_gold_check.py`로 `CROSS-001` 재현 확인(현재 `gold_verified=false` — HANDOFF §2-2에서도 미해소).

## 2. 결정 §7-2 — `rptt` 센티넬 수정 후 KG 재생성 시점 · 대응 ❌2 (E-3-03, C-2-09, E-5-01)

### 상황
`rptt_ksd_itm_no`(대표예탁원종목번호)는 실제 KG에서 `Fund` 노드의 키다. 두 문제가 겹쳐 있다:
- **(a) 수치 오류** — yaml `evidence`가 "NULL+더미 1,761행(7.4%)"인데 문서 실측은 7,086행(29.9%). 1차 수치가 남은 것으로 추정. (이 부분은 아래 §2 조치에서 yaml만 고치면 되며, 실측 재현 후 값 확정 필요.)
- **(b) 생성기 결함** — `gen_fund_structure_auto.py`가 **공백 제거 전에** 정규식 `(KR)?0+`를 적용해 `'0'`·`'00'`·`'00000'`·`'0000000'`·`'KR'`·`'KR000000000'` 6종 센티넬을 **가짜 Fund 노드**로 만든다고 문서가 보고.

### 검증된 사실 (이 세션)
- `gen_fund_structure_auto.py`에서 `sentinel = p.rp.str.fullmatch(r"(KR)?0+")`이고, 그 앞에 `p = p[p.rp.notna() & (p.rp.str.strip() != "")]`로 빈값만 거를 뿐 **`.strip()`을 센티넬 판정 전에 적용하지 않음**을 코드로 확인. 즉 공백이 섞인 0계열은 정규식을 통과할 수 있다 — 문서 지적과 정합.

### 미검증 → 재현됨 (2026-08-29 DB 실측)
- 더미 **7,086(29.9%)** · 물리 NULL **116** · 판매중 더미 **116** 모두 재현 확인. 빌드 커버리지 리포트도 0계열 `KR0000000000`(5,308) · `000000000000`(1,645) 미매핑을 보고.
- 미재현: 가짜 노드 6종(`Fund_ca71a0054d` 등)의 `kg_alias` 개별 존재 — 큰 두 값 외 6종 세부는 KG 조회로 실행 시 확인.

### 무엇을 정해야 하나
생성기를 고친 뒤 **KG를 언제 재생성할지**. 재생성하면 `kg_*` 테이블이 전부 갈리므로 `pytest`·`run_gold_check`를 함께 재확인해야 하고, 서버 반영(`deploy.sh --db-only` 등)까지 파급된다. 9/6 코드 프리즈 일정과의 관계도 고려 대상.

### 정해지면 실행할 조치 (yaml 2 + 생성기 1)
- `public_funds.yaml` `columns.rptt_ksd_itm_no.evidence`:
  - `NULL+더미 1,761행(7.4%)` → `NULL 116 + 더미 6,970 = 7,086행(29.9%·판매중 116행 1.1%)` *(수치는 재현 후 확정)*
- `public_funds.yaml` `missing_profile.…rptt_ksd_itm_no`:
  - `[null, null, 7.4, unresolved]` → `[116, 1.1, 29.9, unresolved]` *(수치는 재현 후 확정)*
- `scripts/gen_fund_structure_auto.py` 센티넬(공백 제거 선행):
  - `sentinel = p.rp.str.fullmatch(r"(KR)?0+")`
  - → `rp = p.rp.str.strip()` 후 `sentinel = rp.str.fullmatch(r"(KR)?0*")` + 빈문자열 제외 `p = p[~sentinel & (rp != "")]`
- `missing_reason: unresolved`는 **유지**(판정 아님, 숫자·노드만 고침).

### 실행 전 검증
1. DB 확보 후 검토기록 §5의 "KG 가짜 Fund 노드" SQL로 6종 존재 재현.
2. 생성기 수정 → `python scripts/gen_fund_structure_auto.py` 재실행 → 가짜 노드 6종 제거 확인.
3. `kg_*` 변동 → `pytest tests -q` · `python eval/run_gold_check.py` 재확인.

## 3. 결정 §7-3 — `Fund` 개념 분리 여부 · 대응 ❌4 / 부수발견 F-2 (E-3-03)

### 상황
`Fund`라는 **한 이름이 두 개념에 겹친다**:
- 도메인 yaml의 `Fund` 키 = `(or_co_xtn_itt_cd, mtco_itm_no)` — 14,522
- 실제 KG의 `Fund` 키 = `rptt_ksd_itm_no` — 6,883

같은 이름이 서로 다른 키를 가리켜, KG 별칭→노드 매핑(E-3-03)이 개념적으로 어긋난다. §2(생성기 수정)로 가짜 노드는 제거되지만, **이름 충돌 자체는 설계 결정 사안**이라 코드 수정만으로 닫히지 않는다.

### 검증된 사실 / 미검증
- 생성기가 `rptt`를 키로 `Fund_` 노드를 만드는 로직은 코드로 확인(`sid("Fund_", rp)`).
- 도메인 yaml의 `(or_co,mtco)` 14,522, KG `rptt` 6,883 수치는 문서 값 — 미검증.

### 무엇을 정해야 하나
`Fund`를 개념별로 **분리할지**(`ManagementFund`(or_co,mtco) / `KsdFund`(rptt) / `FundClass`(itm_no)), 아니면 **이름을 유지하고 note로만 충돌을 명시할지**.

### 정해지면 실행할 조치
- **분리 선택 시**: `public_funds.yaml`의 `entities` 블록 재정의 + 엔티티맵·생성기 라벨 동반 수정. `kg_*` 재생성 → 테스트·gold 재확인 필수.
- **유지 선택 시**: 이름 충돌을 `note`로만 명시(코드 무변경).
- 연관 부수발견: F-1(`FundClass` 노드 부재, `belongsToFund` edge 0), F-3(`MotherFund` 정책 충돌)도 이 결정과 함께 검토하면 일관성 확보.

### 실행 전 검증
- 분리 후 `belongsToFund`/`feedsInto` 등 edge 재생성 결과를 KG 탐색기·`run_gold_check`로 확인.
