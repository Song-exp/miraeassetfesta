## 0. 이 회차가 무슨 작업인가 (쉬운 말)

이름 컬럼은 결측이 0 이라 "볼 게 없다"고 넘기기 쉽다. 그런데 이름은 **두 가지 일을 동시에** 한다 —

```
① 이름 6컬럼 결측·의미 판정 (B-1-56~59 · E-3-12)             ← 검토표가 물은 것
        ↓
② "괄호 안 (채권혼합) 은 검토됐나?"  → 아니다. D-1-07 이 ☐ 였고 yaml 도 '판정률 미산출'
        ↓
③ 괄호 말고 또 있나? → 전수 스캔: 문자열 규약 24종 (§3.6)
        ↓
④ 각 규약에 구조 컬럼·태그가 있나? → 셋으로 갈린다: 태그가 완전히 덮음 / 서로 보완 / 이름이 유일 출처
        ↓
⑤ "피처로 없으면 이름에서 뽑아 규칙을 만든다" → 그런데 LIKE 규칙을 흩어 놓으면 실체가 두 곳

```

⑤→⑥ 이 이번 회차의 설계 결정이다. **규칙의 원천은 yaml 한 곳, 실체는 DB 컬럼 한 곳** — 플래너가 `itm_nm LIKE` 를 즉흥으로 쓰지 않게 한다.

## 4. 설계 — 왜 전부 파생 컬럼인가

리드의 세 질문이 결정을 만들었다.

1. *"괄호 외에 이름에 규칙이 더 있나"* → 24종 (§3.6).
2. *"피처로 없으면 이름에서 뽑아 규칙을 만들어야 하지 않나"* → 맞다. 그런데 `query_rules` 에 `itm_nm LIKE` 를 개념마다 적으면 **규칙의 실체가 yaml 문장 속에 흩어지고**, KG 는 `(테이블, 컬럼, raw값)` alias 라 **걸 값이 없다**.
3. *"그러면 전부 데이터로 파생해야 하는 것 아닌가"* → 그렇다. 태그·구조 컬럼이 있는 축도 파생해 두면 "이름 vs 구조 컬럼 불일치" 가 데이터로 남는다(QA 축).

```
ontology/enums/public_funds.yaml  name_features  ─── 규칙의 원천 (kind·pattern·실측·cross_check·함정)
        │  실행 (규칙을 다시 짜지 않는다 — HANDOFF 08-30 §2-3 '규칙 재작성' 함정)
        ▼
src/name_features.py  parse_name()  ← 4 kind 실행기: flag · extract · map · family
        │
scripts/derive_name_features.py    ← 멱등: ALTER TABLE(없으면) → 전행 UPDATE → schema_metadata 등록
        ▼
public_funds.nm_* 27컬럼  ──▶  플래너 스키마(한글명 "(종목명 파생)")  ·  query_rules 가 nm_* 를 가리킴
                          ──▶  (2단, 미착수) KG alias 를 걸 raw 값이 생김 → FundSeries · 레버리지 배수 노드
```

**왜 별도 테이블이 아니라 마스터 컬럼인가** — 별도 테이블이면 이름 특성 질의마다 플래너가 JOIN 을 써야 한다(HCX SQL 오류 증가). 마스터에 `nm_` 접두로 얹으면 런타임 코드 무수정(`schema_metadata` 로 노출). 원본/파생 경계는 접두어 + yaml + 사전 헤더("주최 원본 75 + 파생 27")로 명시했다.

**3단 로드맵** — 1단 `query_rules` 어휘 매핑(즉시) · **2단 파생 컬럼(이번 회차)** · 3단 Fund 노드 속성 edge + 런타임 edge 필터(프리즈 전 무리).

**답변 우선순위**(`query_rules.이름표기_우선순위`) — 구조 컬럼 > 태그 > `nm_*`. 자산군은 `zrin_btyp_nm`(실질) 우선, 괄호는 "약관 분류 기준" 병기. `배당·인컴` 은 전략이지 분배 방식이 아니다(`분배식`/`nm_monthly_payout` + `fd_last_dstb_r`).

**파생 결과(전체 · 판매중공모)** — `nm_series_no` 11,665·2,647 · `nm_hedge` H 1,448/UH 922 · `nm_asset_bracket` 13,252·8,550 · `nm_class_token` 10,865·7,532 · `nm_tdf_vintage` 624 · `nm_target_conversion` 432·211 · `nm_umbrella_conversion` 219·170 · `nm_is_leverage` 161·44 · `nm_leverage_multiple` 79 · `nm_is_index` 682·479 · `nm_maturity` 142 · `nm_status_memo` 6 · `nm_is_mother` 1.
