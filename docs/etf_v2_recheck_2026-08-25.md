## 2. 🔴 회의 안건 제안 ① — "레버리지 ETF" 질의에 인버스가 섞임

### 사실

2차에서 `cu_lev_fector` **부호가 소실**됨(형이 회귀로 기록). 실측:

```
'인버스' 상품의 cu_lev_fector 부호 →  양수(부호소실) 163 · 음수(정상) 23 · 0/NULL 49
현행 규칙  레버리지: ABS(cu_lev_fector) > 1  →  308건
   그중 상품명에 '인버스' 포함           →   98건 (32%)
```

1차에서는 인버스가 음수라 `>1` 에 안 걸렸는데, 2차는 `ABS()` 라 **인버스2X 가 레버리지로 함께 잡힘.**

### 쟁점

*"레버리지 ETF 추천해줘"* 에 `KODEX 미국달러선물인버스2X` 가 나오는 게 맞나?

| 선택지 | 근거 |
| :-- | :-- |
| ⓐ 현행 유지 (배수>1 전부) | 도메인 통설상 인버스2X 도 레버리지 상품이 맞음 |
| ⓑ 정방향만 (`ABS>1 AND NOT 인버스`) | 사용자 의도는 보통 정방향. 1차 동작과 동일(210건) |
| ⓒ 질의어로 분기 | "레버리지"→정방향 · "인버스 레버리지"→포함 |

**권고 ⓑ 또는 ⓒ.** E1 검토 때 "축과 규칙 경계 정리 필요"로 남겨둔 것이 2차에서 32% 규모로 커진 것임.
`leverageType` **축은 이미 방향+배수 조합으로 정확**하므로(형 개정), 어긋나는 건 `query_rules.레버리지` 하나뿐.

## 3. 🔴 회의 안건 제안 ② — LLM 제약 범위가 미반영

> 🔧 **2026-08-26 정정** — 초판에서 *"HCX 는 답변 생성만 필수"* 로 적었으나 **오독이었다.**
> 공지 원문 스크린샷 확인 결과 **볼드·기울임이 두 곳**(`질의 Intent분석`, `답변 생성`)이다.
> 아래는 정정본.

### 주최 공지 (8/24 디스코드 · 원문 서식 그대로)

> **[ LLM 사용 관련 공지 ]**
> 질의에 대한 답변 제작 API 제작 시 NCP Hyper ClovaX 필수 ( 아래 Bold & 기울임 부분 )
> ***질의 Intent분석*** - ( 데이터 조회 및 증거 제작 ) - ***답변 생성***
> 이외에는 제약사항 없음 ( 점수에 반영하지 않음 )
> · 유료버전의 LLM 사용은 지양 권장 ( CPU 로직, OpenRouter 등 다른 방안 사용 )

### 무엇이 풀렸나

| 단계 | HCX | 우리 파이프라인 대응 |
| :-- | :-- | :-- |
| 질의 Intent 분석 | 🔴 **필수** | Normalize·Ground·Gate 앞단의 의도 파악 |
| (데이터 조회 및 증거 제작) | 🟢 **제약 없음** | **Plan(SQL 생성)·Guard·Execute** ← 여기가 자유 |
| 답변 생성 | 🔴 **필수** | Answer |

즉 **최소 HCX 2회(Intent + Answer)는 고정**이고, 풀린 것은 **SQL 생성 부분뿐**이다.

### 왜 안건인가

회의 안건 §1-1 은 HCX 호출 구조를 `ⓐ 2회(SQL 생성+답변) / ⓑ 3회(+테이블 라우팅) / ⓒ 1회` 로 놓았는데,
공지 기준으로 보면 선택지 자체가 달라진다:

- **ⓒ 1회는 규격 위반** — Intent 분석이 필수라 최소 2회.
- **ⓐ 2회는 구성이 바뀌어야** — "SQL 생성 + 답변"이 아니라 **"Intent + 답변"** 이 필수 2회.
- **SQL 생성은 규칙 기반·경량으로 빼도 무방** → 그만큼 60초 예산에 여유. 단 "유료 LLM 지양" 이라 외부 유료 API 는 피할 것.

레포 문서(`QNA_REVIEW`·`meeting_agenda`)에서 이 내용이 검색되지 않음 → **미반영으로 보임.**
