## ② 결함 층 분해

### ②-1 🔴 G-A [플래너 · 재생성] SQL 환각이 **1·2차 동일하게** 재발해 무응답으로 끝난다 — FND-010 · OFFICIAL-005 · CROSS-001

세 문항 모두 같은 모양이다. gold 는 전부 정상 조회되는데, HCX 가 만든 SQL 이 실행 전 검사에서 걸리고 → 재생성 1회가 **똑같은 실수를 반복**하고 → `[Decision] 값이 DB 에 없거나 SQL 이 안전하지 않아 종료` 로 "질의를 안전하게 실행할 수 없어 답변을 제공하지 못했습니다" 가 나간다. 41~53초를 태우고 0점이다.

| 문항 | 1차 = 2차 실패 사유 | 실재하는 것 |
| :-- | :-- | :-- |
| FND-010 | `p.MAX(fd_nast_suma)` — 별칭 뒤에 집계 함수 | `MAX(p.fd_nast_suma)` |
| OFFICIAL-005 | `domestic_etfs.cu_risk_factor` 없는 컬럼 | `pd_risk_cd`·`pd_risk_nm`·`pd_pen_risk_nm` |
| CROSS-001 | `mtco_itm_nm` 없는 컬럼 | `mtco_itm_no`·`itm_nm` |

세 번째 것이 결정적이다. `_name_owners`(pipeline:96)가 **"철자가 비슷한 실제 컬럼: mtco_itm_no, itm_nm — 뜻이 같다는 보장은 없다"** 는 힌트를 이미 붙여 보냈는데도 재생성이 같은 컬럼을 다시 썼다. 즉 **자연어 피드백으로 HCX 를 고치는 경로는 이 계열에서 실패한다**(이 코드베이스가 이미 여러 번 확인한 "법칙 1"). 층: **플래너(HCX) → 실행 전 SQL 가드**. 고쳐야 할 자리는 HCX 가 아니라 **가드가 기계적으로 고쳐서 통과시키는 것**이다 — `p.MAX(x)` → `MAX(p.x)` 는 순수 문자열 변환이고, `mtco_itm_nm`·`cu_risk_factor` 는 편집거리 1 후보가 유일할 때 치환 가능하다.

### ②-2 🔴 부류 J′ [라우터] 교차질의에서 **값 기반 좁히기가 두 번째 상품군을 삭제**한다 — CROSS-003

`router.route()`(router:175-183):

```python
if p:
    tables = p
    if len(tables) > 1 and o & tables:   # ← 여기
        tables = o & tables
```

이 좁히기는 원래 **머리명사 하나가 여러 테이블 후보를 갖는 경우**(ETF → 국내/해외)를 값으로 가르려고 넣은 것이다. 그런데 조건이 `len(tables) > 1` 이라 **머리명사가 둘이라서 테이블이 둘인 경우에도 똑같이 걸린다.** CROSS-003 에서 `p = {domestic_etfs, public_funds}`, `o = {domestic_etfs}`('월배당'·'분배금' 어휘) → `tables = {domestic_etfs}`. `product_route` 는 `groups=2` 를 정확히 계산해 넘겼는데 쓰이지 않는다.

그 뒤 `_sql_precheck`(pipeline:266-274)의 라우팅 범위 검사가 — **의도대로 정확히 — 자기 SQL 을 기각**한다. 가드는 잘못이 없다. 잘못된 `tables` 를 받았을 뿐이다. CROSS-001 은 값이 3테이블에 고르게 걸려 우연히 살아남았다. 층: **라우터**.

### ②-3 🔴 부류 P″ [SQL 가드] 운용사 확정식이 **필터를 축으로 오인**한다 — FND-011

`ensure_fund_manager_ranking`(pipeline:2474) 발동 조건은 `_MGR_Q`(운용사|자산운용) ∧ `_MGR_RANK_Q`(상위·가장·많이·큰·top) ∧ SELECT/GROUP BY 에 운용사 컬럼. "미래에셋**자산운용**이 운용하는 공모펀드 중 순자산 **큰** 5개" 는 셋을 다 만족한다. 그러나 이 질문에서 운용사는 **결과 단위가 아니라 WHERE 조건**이다 — `[Ground]` 가 이미 `Org_00080008 → or_co_xtn_itt_cd='00080008'` 단일 코드로 핀했다.

구별 신호는 트레이스 안에 이미 있다: **Ground 가 운용사를 단일 코드로 핀했으면 그 운용사는 필터다.** 질문이 축으로 묻는 경우(`운용사별`·`어느 운용사`·`운용사 상위`·`운용사 몇 개`)는 특정 운용사명이 없어 Ground 핀이 생기지 않는다(S11 "순자산이 가장 큰 운용사 상위 3개" 가 그 자리다). 층: **SQL 가드**.

### ②-4 🔴 G-B [SQL 가드] 대표행 가드의 사각지대 — 보수 축 · HCX 자작 펀드키 — FND-005

두 구멍이 한 문항에서 겹쳤다.

1. **정렬 축 목록 누락.** `_fund_sort_target`(pipeline:566)은 `_FUND_RANK_COLS`(수익률 8종 + `fd_nast_suma`, pipeline:540)만 본다. FND-005 의 정렬 축은 `SUM(or_co_rwrd_r + sale_co_rwrd_r + trusc_rwrd_r + ofwk_trus_rwrd_r)` — 목록 밖이라 **`ensure_fund_rank_representative` 가 아예 발동하지 않았다**(트레이스에 대표행 줄이 없다).
2. **HCX 자작 펀드키를 정본으로 안 바꾼다.** HCX 의 GROUP BY 는 `or_co_xtn_itt_cd, CASE WHEN length(mtco_itm_no)>=7 …` — **`COALESCE(…, itm_no)` 가 없다.** `mtco_itm_no IS NULL` 인 **역외 110행**이 or_co 당 한 덩어리로 붕괴한다(`00130001` 한 코드에 47행). 거기에 대표값이 `MIN` 이 아니라 `SUM` 이라 그 덩어리의 합계가 커져 gold 1위 `피델리티호주펀드`(0.015)가 5위 밖으로 밀려났다. 실측 재현으로 확인했다.

`ensure_fund_rank_representative` 의 `has_group` 분기는 **GROUP BY 에 `or_co_xtn_itt_cd` 만 있으면 통과**시키고 키의 나머지를 검사하지 않는다(pipeline:640-647). 층: **SQL 가드**.
