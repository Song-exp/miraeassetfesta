## 4. 근본 원인 — 식별자 형식이 다르다

생성기는 **동일 키(티커/CUSIP/LEI)만 자동 병합**한다. 그런데 국내·해외 테이블의 식별자 체계가 서로 다르다.

| 회사 | 국내 `ticker` | 해외 `cusip` / `lei` |
| :-- | :-- | :-- |
| Li Auto Inc | `2015 HK` · `LI US` | lei `2549003R73Q70J5H4I65` |
| News Corp | `NWSA US` · `NWS US` | cusip `65249B109` · lei `549300ITS31QK8VRBQ14` |
| Zhongji Innolight | `300308 C2` · `3308 HK` | (없음) |

국내 `ticker` 형식 분포 — **공백 포함 블룸버그식 3,517종** · 6자리 숫자(한국) 1,506종 · 기타 63종.

즉 국내는 **블룸버그 티커**(`NWSA US`), 해외는 **CUSIP/LEI**를 쓴다. 겹치는 키가 없으니 자동 병합이 원리적으로 불가능하다. 이름으로 묶는 건 생성기가 의도적으로 막아 뒀다(`삼성전자 ≠ 삼성전기`).

## 5. 제안 — 수동 코드북에 parent 를 넣는다

생성기가 정해 둔 통로를 그대로 쓴다.

> `# 병합: 동일 키(티커/cusip/LEI)만 자동. 이름 동일은 병합하지 않는다.`
> `# 한↔영 교차는 수동 코드북 parent 로만.`

`ontology/codebooks/security_alias_manual.csv` 에 **103종**을 등록하면 된다. 생성기·자동 yaml 은 건드리지 않는다.

### 왜 이름만으로 자동 병합하면 안 되는가 (설계 존중)

`삼성전자` / `삼성전기` 처럼 **다른 회사가 비슷한 이름**을 갖는 경우가 실재한다. 이번 103종은 **철자가 완전히 동일**하고 국내 TOP50 안에 든 것만 추린 것이라 오병합 위험이 낮지만, **전건을 사람이 확인한 뒤** 넣어야 한다.

### 확인이 필요한 것 (리드)

| # | 물음 | 왜 |
| :-: | :-- | :-- |
| 1 | `security_alias_manual.csv` 에 103종을 내가 채워도 되는가 | 코드북은 손으로 쓰는 파일이라 내 영역이나, 채권·펀드 노드에도 영향이 간다 |
| 2 | `Sec_o_67066GAF1`(NVIDIA 회사채 추정)을 주식 노드와 이을 것인가 | 주식 ≠ 채권이지만 *"NVIDIA 관련"* 질의에선 이어져야 할 수 있다 — 채권 담당 판단 |
| 3 | `TOP_RANK = 50` 을 올릴 것인가 | 51위 이하는 설계상 제외 — 국내 4,401종 · 해외 67,671종. *"○○ 담은 ETF"* 질의가 소액 편입까지 포함해야 하면 올려야 한다 |

## 6. 왜 이게 점수와 직결되는가

주최 공식 예시 문항에 **"에코프로 자회사를 담은 ETF"**, **"Cambricon 담은 상품"** 이 있다. 전부 **"이 종목을 담은 상품 찾기"** 유형이다.

노드가 갈려 있으면 **부분 답**이 나가고, 챗봇은 빠뜨린 줄 모른 채 확신 있게 답한다. *"확인할 수 없음"* 보다 나쁘다.
