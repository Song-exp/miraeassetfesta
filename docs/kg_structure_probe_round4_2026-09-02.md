## ④ 관찰

1. **F1 은 "빼기" 만 했고 "대체" 를 안 했다.** 라벨 충돌 노드를 매칭 키에서 제외한 뒤, 그 낱말이 향할 곳을 count 경로는 이름 폴백으로 찾았고(X16 20/112) 목록 경로는 못 찾았다(Z18 2,157/5,509). 같은 낱말('ETF')에 같은 질문형인데 "몇 개야" 는 맞고 "알려줘" 는 크게 틀린다 — **질문 형태가 정답을 가르는 3R §④-3 의 패턴이 규칙만 바뀐 채 재현됐다.**
2. **같은 질문형에서 정답과 오답이 갈리는 자리는 전부 "기계 확정이 아니라 HCX 재량" 인 절이다.** Z22(2024년) 107/287 정답 ↔ X19(2025년) 2,853 오답 ↔ KG-035(2026년) 2,594 오답 — 세 문항은 문장 구조가 같고 SQL 의 날짜 절만 다르다. Z17(2호 클래스 7) 정답 ↔ X17(2호 클래스 7 조회 후 '확인 불가') — 데이터는 같고 답변 조립만 다르다. **비결정성의 소재지가 정확히 지목된다: 날짜 절 · 모수 절 · 다열 결과의 서술.** 셋 다 §③ 필수 항목이다.
3. **`retrieved_context` 를 보면 정답이 있는데 답변이 버린 경우가 4건**(X17 COUNT=7 → '확인 불가' · X22 cnt=0 → '1개' · Z23 수탁 코드 00020088 → '수록 안 됨' · KG-030 17행 → '17호'). 이 4건은 SQL·가드가 이미 옳게 일한 뒤에 조립에서 무너진 것이라 **가장 값싸게 닫히는 자리**다(G5).
4. **SQL 이 답을 리터럴로 심는 새 패턴** — X22 의 `COALESCE(public_funds.trusc_xtn_itt_cd, '국민은행') AS actual_trustee` 는 0행이면 항상 '국민은행' 을 내는 사실상의 하드코딩 답이다. precheck 의 값 사전 대조는 WHERE 절만 보므로 SELECT 절의 리터럴은 그냥 통과한다. **SELECT 절에 질문의 개체명 리터럴이 들어가면 기각**하는 규칙이 필요하다(G5 에 붙일 수 있음).
5. **KG-008 은 '숨김' 가드가 별칭에 속은 사례다.** `trim(trusc_xtn_itt_cd) AS 수탁회사명` — 가드는 `수탁금액` 컬럼만 숨겼고 코드 컬럼은 이름처럼 보이는 별칭 때문에 그대로 답변으로 갔다. **컬럼 판정은 별칭이 아니라 원 컬럼 표현식으로** 해야 한다(G4).
6. **precheck 가 문법을 안 본다는 것이 Z13 으로 처음 드러났다.** "SQL 검사 통과" 로그 뒤에 실행 예외가 나서 사용자에게 "데이터 조회 중 오류" 가 나갔다 — 오거절보다 나쁜 표면이다. `sqlite3.complete_statement` 한 줄이면 잡힌다.
7. **`ensure_fund_country_tag` 의 6R I′ 분기는 의도대로 작동한다** — 이름 토큰이 실린 개별 조회에서 태그 절을 걷어내는 코드(`_strip_tag_predicates`)가 X25·Z2·Z3 에서 클래스 결측으로 인한 축소를 막았다. I′ 는 KG 계열에서 부작용 0.
8. **Ground 의 Region closure 가 오해를 만든다** — Z5 에서 `'글로벌' → Region_Global [+후손 57: Region_GlobalExUS, Region_Asia, Region_China …] → fd_ivst_rgn_desc='글로벌' · '아시아' · '남미/북미' · '유럽' … 외 2종` 이 근거문서에 실렸고, HCX 는 이 목록을 보고 `IN ('글로벌','해외주식형')` 을 썼다. **후손 값을 나열하는 것이 "이 컬럼에 이 값들이 있다" 는 신호로 읽힌다** — S4 closure scope 이월 항목의 실증이다.
