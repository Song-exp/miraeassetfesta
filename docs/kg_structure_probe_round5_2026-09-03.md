### 🔴 KG-008 이 왜 안 고쳐졌나 — 원인 확정 (A 가 겨냥했는데 바이트 동일)

items = _split_select_items(...)      # 원본 SQL → 4개 항목
if len(items) != len(cols):           # 숨김 후 헤더는 3개
    return rows, []                   # ← 조용히 무력화

KG-008 의 SQL 은 SELECT 항목이 4개(`수탁회사명 · 수탁금액 · 펀드수 · 수탁금액_억원`)인데, `_hide_answer_columns` 가 `수탁금액`(원 단위 금액)을 지워 3열이 됐다. 그래서 arity 검사가 걸려 **G4 가드가 통째로 꺼졌고**, HCX 는 `trim(trusc_xtn_itt_cd) AS 수탁회사명` 이라는 별칭만 보고 운용사 이름 3개를 날조했다.

- **think_trace 증거**: KG-008 은 `10. [Answer] 내부 코드 컬럼 숨김 — 수탁금액` 만 있고 `기관 코드 확정 표기` 단계가 **없다**. 반대로 X13·X14·AA16 은 숨김 단계가 없고 표기 단계가 **있다**. 두 가드는 서로를 배제한다.

이건 온톨로지·KG 문제가 **아니다**. 수탁사 48개 노드는 `label_ko`·`canonical_name` 에 이름을 정상적으로 갖고 있고(`Org_trustee_00020054` = 홍콩상하이은행 서울지점), `_code_label_map()` 도 그걸 읽는다. **런타임 두 가드의 호출 순서 문제 하나**다.

## ④ 관찰 — 값은 맞지만 구조적으로 위험한 것

1. **🔴 가드가 조용히 꺼지는 실패 모드가 최소 두 곳 있다.** `label_code_columns` 는 arity 불일치에서, `_hide_answer_columns` 는 `drop` 이 빌 때 `return rows, []` 로 무음 종료한다. think_trace 에는 **아무 흔적도 남지 않는다** — 그래서 KG-008 이 두 라운드 연속 "고쳤는데 안 고쳐진" 상태로 보였다. 가드가 자기 전제 때문에 스킵될 때는 trace 에 `[Guard] … 적용 불가(사유)` 를 남겨야 다음 라운드가 헛돌지 않는다.

2. **잔여 술어 문제는 통계적으로 이미 다수다.** KG-035(`>= 20260000`) · AA3(`<= 20231231`) 는 잔여 술어가 **우연히 무해**해서 ✅ 가 됐고, X19(`<= 20250930`) · AA20(`LIKE '%2호%'`) 는 유해해서 ❌ 가 됐다. 즉 현재 ✅ 4건 중 2건은 운으로 서 있다. 부류 B 는 지금 ❌ 2건이 아니라 **✅ 2건의 안정성 문제**이기도 하다.

3. **`ext_fund_page` 는 오염된 소스인데 답변에 원문이 직접 실린다.** `mother_fund_names_raw` 는 '코어**텍**' 오탈자와 `;` 구분자를 그대로 담고 있고(X18), `mgmt_co_nm` 은 이미 FND-035 로 오염이 확인됐다. 이 테이블에서 **이름 문자열을 답변에 옮기는 경로**는 전부 `public_funds.itm_nm` 대조를 거쳐야 한다. 반면 `estb_dt` 는 실측상 깨끗하다(2019-10-23 등) — 컬럼별로 신뢰도가 다르다.
