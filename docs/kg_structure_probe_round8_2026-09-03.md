### 4. 🔴 `AA16` 악화 · `KG-008` 원인 이동 — 부류 D·G 는 **절반만 집행됐다**

12R `c3308e7`("정렬 축을 `COUNT(DISTINCT 펀드키)` 로")는 **`KG-008` 의 SQL 에는 들어갔다**. 그 SQL 을 직접 돌리면 `(00020054, 714) (00020004, 516) (00020027, 465)` — **gold 순서 그대로**다. 그런데 답변은 국민 → 홍콩상하이 → 씨티 순이고 숫자는 1656·1827·1466 이다. 두 가지가 겹쳤다:

1. **별칭 충돌** — HCX 가 `COUNT(*) as 펀드수` 를 쓰고 가드가 `COUNT(DISTINCT 펀드키) AS "펀드수"` 를 **같은 이름으로 덧붙였다**. 결과 행에 `펀드수` 가 둘이라 답변기가 어느 쪽을 읽는지 보장이 없다.
2. **답변 조립기가 재정렬** — 출력 순서가 `SUM(fd_nast_suma)` 내림차순(38.4조 · 22.6조 · 17.7조)과 정확히 일치한다. HCX 자유서술 경로가 SQL 행 순서를 무시하고 자기가 본 숫자로 다시 줄 세웠다.

`AA16` 은 더 나쁘다. SQL 에 **기본모수 WHERE 가 아예 없다**(`SUM(CASE WHEN 판매중 AND 공모 THEN 1 END) AS cnt` 로 대신하고 `GROUP BY trusc_xtn_itt_cd` 는 전체 행). 그래서 정렬용 `"펀드수"` 는 판매완료까지 센 2911·2063·1484·1416·1092 이고, 출력 숫자는 `cnt`(판매중 클래스수)다. 축이 둘 다 어긋나 **씨티(gold 3위 465)가 탈락하고 한국증권금융(gold 96)이 5위로 들어왔다**. 답변기는 SQL 을 충실히 옮겼다 — 이번 결함은 순수하게 **SQL 가드**다.

### 5. ⚠ `Z16` 판정 교정 — 한 운용사에 `or_co` 코드가 둘이다 (회귀 아님)
