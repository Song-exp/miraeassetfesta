### 2. 🔴 남은 절반 — 펀드단위 집계 교체가 교차질의 가지에서 **구조적으로** 발화할 수 없다

원인을 코드에서 특정했다. `58e823f:src/runtime/pipeline.py` `ensure_fund_distinct_count`:

```python
m = re.match(r"(\s*SELECT\s+)COUNT\(\s*\*\s*\)(?:\s+AS\s+\w+)?(\s+FROM\b)", sql, re.I)
if not m:
    return sql, False
```

**SELECT 목록 *전체* 가 `COUNT(*)` 여야 발동한다.** 그런데 교차질의 가지는 예외 없이 라벨 리터럴을 앞에 단다:

```
X8      SELECT 'S&P500 공모펀드' AS 구분, COUNT(*) FROM public_funds …
X9      SELECT '공모펀드' AS 구분, COUNT(*) AS 개수 FROM public_funds …
KG-025  … UNION ALL SELECT '공모펀드', COUNT(*) FROM public_funds …
KG-026  SELECT 'KOSPI200을 벤치마크로 쓰는 공모펀드' AS 분류, COUNT(*) AS 개수 FROM public_funds …
```

`re.match` 는 `SELECT` 바로 뒤에 `COUNT(*)` 를 요구하므로 **전부 불발**한다. 반대로 `Z13` 은 HCX 가 라벨 없이 `SELECT COUNT(*) FROM public_funds …` 로 써서 **유일하게 발화**했다(트레이스에 `가지1: 펀드단위 집계 교체` 가 찍힌 문항은 Z13 뿐이다). 즉 이 가드의 발화 여부는 **HCX 가 라벨 컬럼을 붙였느냐**라는 우연에 달려 있다.

가지 분해(P4-a)는 옳게 들어갔다 — 실패한 것은 **분해된 가지에 거는 가드 자체의 매칭 조건**이다. 처방은 §③-1.

### 3. 🔴 `Z13` — 우리 12R 변경이 만든 구조 게이트 사고

```
8.  [Plan]  (SELECT COUNT(DISTINCT …) AS "펀드수", COUNT(*) AS "클래스수" FROM public_funds WHERE …)
            UNION ALL (SELECT COUNT(*) FROM domestic_etfs WHERE …) LIMIT 2
9.  [Guard] SQL 기각 — SELECT 만 허용
12. [Guard] 재생성 후에도 실패 — SELECT 만 허용
```

`validate_sql` 첫 검사가 `re.match(r"^\s*(?:select|with)\b", s, re.I)` 다. Z13 의 문장은 **`(` 로 시작**하므로 여기서 즉시 기각된다 — 문법상 완전히 정상인 SQLite 문장인데도. 12R 이 UNION 괄호를 살렸고 `_single_select`(1254행) 와 `apply_union_branch_guards`(가지의 `(…)` 를 벗겨 넘기는 `m_par`)는 이미 괄호 가지를 다루는데, **구조 게이트만 따라오지 않았다**. `_single_select` 의 docstring 이 스스로 "12R 이 UNION 괄호를 살린 이상 UNION SQL 이 가드 체인에 계속 들어온다" 고 적어 놓고도 같은 판정을 `validate_sql` 에 못 박지 않은 것이다. 결정층: **SQL 가드(구조 게이트)**.
