## 1. ✅ 안건 4-1 — 채권 수익률 랭킹 (결정)

### 무엇이 문제였나

*"수익률 높은 채권 추천해줘"* 의 1~5위가 유동화 후순위(최대 **728.5%**)로 나온다. 부실해서 원금을 못 받을 수 있는 채권이다.

### 논의 경과

| 시도 | 결과 |
| :-- | :-- |
| 도메인 기준으로 자르기 | **`C0` 아래는 "절대 사면 안 되는" 등급**이라는 기준은 존재. 하지만 그 위(`C+`·`C`)도 안전한 채권은 아니다 — 어디서 자를지가 애매 |
| 수익률이 너무 높은 것을 빼기 | 🔴 **오폭.** 728% 뿐 아니라 **정상적으로 수익률이 높은 채권까지 함께 걸러진다** |

> 수익률이 높은 건 위험의 **대가**라서, 위험한 걸 빼면 높은 수익률도 같이 빠진다. 둘을 분리할 깨끗한 선이 없다.

### 🟢 결정 — 빼지 말고 **알린다**

종목 하나하나를 판단하면 너무 구체적이고 복잡해진다. **조건문 하나로 처리한다.**

```
답변에 도메인 기준(C0 등) 아래 등급이 하나라도 포함되면
  → 결과는 그대로 주고, 아래에 주의 문구 한 줄을 붙인다
```

예시 형태:

> 수익률 높은 순으로 정리했습니다. (목록…)
> **다만 신용등급 C 이하인 종목이 포함돼 있습니다. 통상 이 등급은 원금 손실 위험이 커 일반적으로 매수하지 않으니 판단에 주의하세요.**

### 🔴 이건 채권만의 규칙이 아니다 — **공통 패턴으로 채택**

> *"좀 더 일반화해보면, 한 케이스라도 포함되면 그 경우를 잘라서 안내하는 문구를 붙이는 식으로 가면 될 것 같아요"*

**예외 케이스가 답변에 포함되는데 빼기는 어려운 경우 → 제외하지 말고 안내 문구를 붙인다.**

ETF 에도 그대로 적용된다. 해당되는 곳:

| 상황 | 지금 처리 | 공통 패턴 적용 시 |
| :-- | :-- | :-- |
| 레버리지 질의에 **인버스가 섞임** (`ABS(배수)<>1`) | 회의 안건으로 보류 중 | 결과는 주되 *"인버스(-2배) 상품이 포함돼 있습니다"* 문구 |
| 해외 구성종목 **기준일이 2~10개월 낡음** | 상품별 `report_date` 병기 | 같은 취지 — 이미 반영됨 |
| Top-N 에 **판매종료 상품**이 섞임 | 규칙으로 제외 | 제외가 맞음(살 수 없으므로) — 문구 아님 |

> 판단 기준: **살 수 없는 것은 제외**, **살 수는 있는데 위험한 것은 알린다.**

## 4. 🔵 이제부터 할 일 — 리드 지시

### 4-1. 한 바퀴

> *"예시 질문을 우리가 구현한 네트워크 구조 내에서 어떤 경로를 타고 SQL 이 만들어지는지 확인한 다음, 값을 잘 받아왔는지 테스트"*

챗봇이 `think_trace`(생각 과정)와 `retrieved_context`(참고한 정보)를 뱉는다. **그 둘을 코드·yaml 과 대조**한다.

```
① 챗봇에 내 도메인 질문           → think_trace · retrieved_context 확인
② 개체 매핑 · 테이블 추정 · SQL 생성 경로가 의도대로인가
③ 어긋나면 yaml 수정              (문서 아님 — yaml 이어야 프롬프트가 바뀐다)
④ build_ontology.py 로 반영 → 푸시
⑤ 오답은 eval/questions_*.jsonl 로 승격
```

절차는 [`EXPERIMENT_LOOP.md`](EXPERIMENT_LOOP.md) 에 이미 정리돼 있다. **그 매뉴얼대로 하면 된다.**

> ⚠️ **yaml 반영이 서버에 자동으로 안 간다.** 리드 PC 에서 pull → 서버로 push 하는 구조다.
> 즉 **내가 고치고 푸시해도 챗봇에는 리드가 밀어 넣어야 반영**된다. 고쳤으면 리드에게 알린다.

### 4-2. 평가 관점 두 가지

> *"온톨로지에서 평가하려는 건 ① 구축된 네트워크에서 정보를 잘 뽑는지 ② 답변 내에서 예외 조항을 잘 처리하는지, 이 두 가지"*

②가 곧 §1 의 주의 문구 패턴이다.

### 4-3. 도메인 경계

> *"통합 연결망은 노드 몇 개 안 될 거다. 각 도메인으로 구성된 네트워크를 먼저 보고, 통합은 내가 관리할게"*

- **각자 자기 도메인의 yaml·서브네트워크를 본다.**
- 통합 연결망은 **리드가 관리**.
- 온톨로지는 하나라 **내 수정이 남의 도메인에 영향 가면 미리 말한다.**

> 채권 담당 질문 *"ETF·펀드는 겹치는데 채권은 겹치는 게 없나?"* → 리드 답변: *"딱히 없다, 각자 도메인만 잘 보면 된다."*
> ETF ↔ 펀드는 *"ETF 가 일종의 펀드 뷔페"* 라 구조가 비슷해 겹치는 부분이 있다.

### 4-4. 챗봇 비교

미래에셋·키움 챗봇에 같은 질문을 넣어 우리 답과 비교해 조정한다.

- 서현은 미래에셋 챗봇 접속이 안 돼 **키움으로 진행**, 필요 시 다른 사람이 대신 질의
- 관찰: 키움은 *"코덱스"* 검색이 안 되고, 간단한 ETF 질문에도 *"해당 상품이 없습니다"* 가 뜬다
- 리드 해설: *"관계상 잡는 게 어려워서 그렇다. 온톨로지 구현이 어려운 가장 큰 이유가 그것"*

### 4-5. 우리 챗봇 서버

- 주소는 **공지 댓글**에 있음. **링크를 클릭하면 안 되고 주소를 복사·붙여넣기** 해야 접속됨(보안 설정). 크롬에서 동작 확인
- `think_trace` 는 **대조용**이며 **최종 사용자에게는 노출하지 않는다**
- 비용: 5일 가동에 약 1만원 소진(잔액 19만원대). 리드 계정 서버라 **리드 것으로 계속 사용**
- 리드가 **`think_trace` 에 실행된 SQL 쿼리까지 추가**하기로 함 → 대조가 쉬워짐

### 4-6. 회의 중 관찰된 오답 (재현 대상)
