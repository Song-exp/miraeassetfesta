## 0. 한 문장 프레임

**우리 온톨로지는 "그래프를 탐색하는 장치"가 아니라, LLM 이 SQL 을 틀리지 않게 만드는 3층 장치다 —
① 값을 미리 접지하는 사전(KG), ② 규칙을 프롬프트에 싣는 문서(context form), ③ 생성 전후를 막는 게이트(runtime form).**

주최 인용 논문(JAMIA Open 2025)의 프레임을 그대로 받는다: 스키마 정보 축소·정리만으로는 정답률이 한 자릿수~10%대에
머물렀고, **업무 규칙·용어집을 담은 컨텍스트 문서를 더했을 때** 78.3% 로 뛰었다. 좌우하는 것은 스키마가 아니라
"데이터가 실제로 어떻게 생겼는지"의 명시적 문서화다 — 우리 3층은 그 문서화를 값·규칙·검사 세 형태로 나눠 구현한 것이다.

## 1. 층별 서술 골격

### 1층 — 값 사전 KG (사전 구축 · 런타임 탐색 없음)

| 항목 | 내용 |
| :-- | :-- |
| 실체 | `kg_node`·`kg_alias`·`kg_edge`·`kg_closure` (수치: NUMBERS §3) — yaml 개체 선언 + 코드북 9종 + 구성종목 실측에서 **사전 구축**, SQLite 매핑 테이블로 적재 |
| 런타임 | 질의 어휘 → alias 매칭 → 정본 노드의 closure 후손 + `subsidiaryOf` 1단 전개 → **DB 에 실재하는 리터럴만** SQL 에 주입 (`pipeline.expand_node`) |
| 왜 | LLM 은 필터 값을 추측한다 — 실패의 절반 이상이 잘못된 enum 값·컬럼이라는 관찰(ENT-1, **착안** 서술)과, 링킹된 개체명을 verbatim 으로만 쓰게 제약하자 학습 밖 사실에 대한 질의가 비로소 성립했다는 기전(KGG-1 Table 3·4, **B**) |
| 우리 사례 | "에코프로의 자회사 편입 ETF" — 자회사 3사 전개로 답이 통째로 바뀜(공식 예시 #5) · 캠브리콘 표기 6종 합집합(공식 예시 #3) |
| 쓰지 말 것 | "그래프 탐색·추론" 서술 — 관계형 데이터에서 질의 생성 ≫ 그래프 탐색(KGQA-1)이 우리 설계 근거. edge 종류 확장은 하지 않았다(직접 근거 0편) |

### 2층 — 규칙 문서 = context form (yaml → 프롬프트)

| 항목 | 내용 |
| :-- | :-- |
| 실체 | `ontology/enums/*.yaml` 의 `query_rules`(조건식 그대로 복사 가능한 형태)·`clarify`(다의어·사람의_선택)·`_refusal.yaml`(5사유)·`value_vocab`(범주값 자동 생성) — `planner_context` 가 평문화해 근거문서로 주입 |
| 선별 | 규칙 2층: always_on(모수·센티넬·단위·기준일) + triggered(질문 어휘가 있을 때만) — 전부 주입 < 선별 주입 (DK-1 Table VI, **A**) |
| 왜 | 규칙 문서의 존재 자체가 정확도를 좌우한다 — 4KB 규칙 문서로 +17~23pp, 모델 교체 차이는 5pp (SL-1 Table 1, **B**: 문서 전체 효과이며 항목별 ablation 은 없음을 명시) |
| 우리 사례 | 결측이 아닌 0(zero_is_value)·-100 센티넬·위험등급 방향(작을수록 위험)·보수 ‰ 단위·기준일 앵커(2026-08-22) — 전부 "데이터가 이래서 규칙이 이렇다" 인과로 서술(ETF 트랙 결함→설계 8건과 합류) |
| 정직성 | 효과 측정은 `run_paired.py`(full vs layered, McNemar·Wilson CI — SL-1 §4.4 방법론 이식, **A**) 결과가 나오면 그 수치만 싣는다. **논문의 절대치를 우리 효과처럼 옮기지 않는다** |

### 3층 — 구조적 게이트 = runtime form (생성 전·후 검사)

| 항목 | 내용 |
| :-- | :-- |
| 실체 | 생성 **전**: gate(enum 소속·부재 속성·상수 컬럼·미래 연도) — 해당 시 HCX 호출 0회로 기각. 생성 **후**: `validate_sql`(SELECT·허용 테이블·LIMIT) + 값 검사기(WHERE 리터럴 ↔ 값 사전 57컬럼, LLM 0회) + 실패 시에만 재생성 1회(12초 예산) + 0행 시 조건별 진단을 **거절 답변의 근거**로 제시 |
| 왜 | "생성 전, 실행 없는 답변가능성 게이트" 정식화(REF-1 §3.1)와 프롬프트 거절 템플릿의 금융 도메인 성능(REF-1, **A** — 단 답변가능성 분류 성능이지 종단 정확도가 아님을 병기). 상수 컬럼 게이트 자체는 논문 근거 없이 **우리 gold 실측에서 나온 산물**(D)로 정직하게 구분 |
| 경계 | 0행 자동 재시도·LIKE 완화는 **하지 않는다** — 거절이 정답인 문항에서 환각 경로가 된다(VAL-1 관찰, 우리 거절 문항과 충돌) |
| 우리 사례 | "신용등급 AAAA" → 게이트 기각(HCX 0회) · "신용등급 AAA 공모펀드" → 부재 속성 기각 · "EUR 거래 해외 ETF" → 상수 게이트 0.5s |

## 2. 층 사이의 연결 (서술 순서)

```
질문 → [1층] 값 접지 (alias→closure→리터럴)
     → [2층] 규칙 주입 (always_on + triggered)   → HCX SQL 생성
     → [3층] 게이트 (전: 기각 / 후: 검증·값 검사·재생성 1회·0행 진단)
     → 실행 → 답변 규약(answer_rules) 적용
```

- 같은 원천(yaml)이 세 층을 다 먹인다 — 값 사전(1층)과 값 검사기(3층)가 **같은 사전**을 쓰므로
  "프롬프트에 준 값"과 "검사하는 값"이 어긋나지 않는다. 이것이 도메인 확장 시 yaml 1개 추가로 끝나는 이유(§05 확장성 논거와 연결).
