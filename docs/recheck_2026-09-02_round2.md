### R2 "펀드를 가장 많이 운용하는 운용사 상위 5개" — ✅ → ❌

**어느 단계가 거절을 만들었나** (trace 6~12):
1. 1차 SQL: `MAX(mtco_nm)` — 존재하지 않는 컬럼(1라운드·09-01 FND-035 와 동일. 3라운드째). `guard.unknown_columns` 기각 → **재생성 1회 예산 소진**.
2. 재생성 SQL: `MAX(mgmt_co_nm)` + `LEFT JOIN ext_fund_page` 로 바르게 고쳤고 `[Guard] 운용사 최빈 이름` 도 발동. 그런데 펀드수 식이 **`COUNT(DISTINCT COALESCE(CASE … END, itm_no))`** — `itm_no` 가 비한정. `guard.ambiguous_columns`(pipeline.py:2741) 가 `한정되지 않은 모호 컬럼: itm_no` 로 기각 → 재생성 예산 없음 → `[Decision] … 종료`.

**로컬 재현** (`load_context()` + `guard.ambiguous_columns`):
- 2R 재생성 SQL 그대로 → `['itm_no']`. SQLite 직접 실행 → `ambiguous column name: itm_no`.
- 1R 재생성 SQL(COALESCE 없는 `CASE … END`) → `[]` (통과 — 1라운드가 정답이던 이유).
- `itm_no` → `public_funds.itm_no` 로 한 곳만 한정 → `[]` + DB 실행 **823·235·207·205·142 + 우리자산운용 = gold 5행**.
- `_apply_sql_guards` 를 2R 재생성 SQL 에 태워 봄 → 발동 가드는 `운용사 최빈 이름` 뿐, `itm_no` 는 건드리지 않음.

**원인 층 판정**:
- 🔴 **P1-c 의 KG yaml 변경이 방아쇠**: 커밋 84e094d 가 `ontology/enums/public_funds.yaml` `query_rules.펀드단위`(809행) 를 `COALESCE(CASE … END, itm_no)` 로 바꿨는데 **`itm_no` 가 비한정**이다(같은 커밋의 `운용사질의` 워크드 예시 890행은 `p.itm_no` 로 한정돼 있다). HCX 는 재생성에서 `펀드단위` 규칙의 식을 그대로 JOIN 문에 옮겼다. 1라운드엔 COALESCE 자체가 없어 모호 컬럼이 생길 수 없었다.
- 리뷰 ②-2(분포 조립기 top-N 불개입)·②-3(개수 조립)·P1 GROUP BY 주입은 **원인이 아니다** — 이 SQL 은 JOIN 이라 세 가드 모두 불발이고, 조립기는 실행 전에 이미 끝났다.
- 검사기(`ambiguous_columns`) 설계도 절반 책임: "실행 전에 잡아 재생성 1회를 준다" 가 전제인데 **재생성 예산이 1차 기각에서 이미 소진**되면 기각 = 거절이다. 유일하게 모호한 컬럼이 `itm_no` 하나(JOIN 상대 `ext_fund_page` 는 itm_no 로만 겹친다)이고 정답 한정이 항상 FROM 테이블이므로 **기각이 아니라 기계 한정**이 맞다.
- 근본: `mtco_nm` 환각이 3라운드 연속 1차 SQL 을 잡아먹는다 — 워크드 예시가 실려도 무시(법칙 1). 결정층으로 내린다(③-Q1-c).
