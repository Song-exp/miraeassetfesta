### ②-2 🔴 부류 M′ [SQL가드 불개입 조건] 묶기 가드가 HCX 의 **모양 변화**에 손을 뗀다 — S4 · T14

`ensure_fund_lookup_grouping`(L934~) 은 발동 조건 6개를 **전부** 만족할 때만 재작성한다. 그중 두 개가 이번에 걸렸다.

- **조건 ③ `ORDER BY` 없음** — S4 의 HCX SQL 이 `ORDER BY itm_no ASC` 를 달았다. 첫 줄 `if not _FUND_TBL.search(sql) or re.search(r"\b(?:join|union|group\s+by|having|order\s+by)\b", …): return sql, False` 에서 즉시 반환. 결과는 `SELECT DISTINCT` 클래스 37행 → LIMIT 30 절단 → HCX 산문 요약 → **펀드 1개 누락 + 등급 서술 오류**.
- **조건 ④ SELECT 에 집계 없음** — T14 의 HCX SQL 이 `AVG(fd_nast_suma)` 를 썼다. `if re.search(r"\b(?:count|sum|avg|min|max|total)\s*\(", head, re.I) … return sql, False`. 결과는 **AVG 212억** — 20행 평균을 그대로 재현했다(gold 는 4펀드 SUM).

두 조건 모두 **"모델 의도 존중"** 이라는 주석이 붙어 있는데, 개별 조회로 이미 판정된 뒤(`_has_name_filter` 참) HCX 의 정렬·집계 선택을 존중할 근거가 없다. 5R 이 이 자리를 "비결정 잔재" 로만 적은 것이 이번에 값 오류 2건으로 발현했다. 5R 에서 무사했던 이유는 단지 HCX 가 그때 `ORDER BY`·`AVG` 를 안 썼기 때문이다.

### ②-3 🔴 부류 R′ [클래스 개수 질의] '클래스' 질의가 가드 사각지대 — V12 · W5

`_LOOKUP_ROW_UNIT`('클래스'·'보수'·'수수료')이 있으면 묶기가 의도적으로 불개입한다(행 단위가 정답인 질의). 그런데 그 경로에는 **개수를 세는 확정식이 없다**. HCX 는 두 문항 모두 `SELECT DISTINCT itm_no, COUNT(*) … GROUP BY itm_no` 를 썼고, `itm_no` 는 **클래스 단위 키**라 모든 그룹이 1이다. 답변기는 그걸 그대로 옮겨 W5 "1개", V12 "모두 1개씩 … 총 30개"(LIMIT 절단값)로 갔다.

### ②-4 🔴 부류 S′ [코드 핀] KG 가 핀한 **컬럼**을 HCX 가 바꿔 써도 값사전 대조가 통과 — W11

`[Ground] 'KB중국본토A주증권자투자신탁' → Fund_789df27b8c → public_funds.rptt_ksd_itm_no='030230002D36'` 인데 최종 SQL 은 `itm_no IN ('030230002D36')`. `_sql_precheck` 의 `WHERE 값 사전 대조` 가 통과했다는 것은 **코드형 컬럼의 값 존재 검사가 없다**는 뜻이다(0행 진단은 "itm_no IN (…) → 0건" 을 정확히 짚었으니 검사할 재료는 있었다). 5R 에서 V4·W11 이 ✅ 였던 것은 HCX 가 그때 `rptt_ksd_itm_no` 를 그대로 썼기 때문 — 이번엔 V4 는 살고 W11 만 죽은 **비결정**이다.

### ②-5 🔴 부류 W1′ [0행 근접 후보] 접두 축소가 브랜드 2자까지 내려간다 — W1

### ②-6 🔴 부류 F6′ [가드 순서] 개별 조회 재작성 SQL 은 기본모수 가드를 영영 만나지 못한다 — W2 · Y11 (+ W7·Y13 잠재)

## ④ 관찰

### ④-1 결함의 성격이 바뀌었다 — "규칙이 없다" 에서 "규칙이 안 걸린다" 로

1R~5R 의 ❌ 는 대부분 *규칙 부재*였다. 6R 의 ❌ 8건 중 **5건(S4·T14·V12·W5·W11)은 규칙이 이미 있는데 발동 조건에 안 걸린 것**이다. 공통 형태: 가드가 `HCX SQL 의 모양`(ORDER BY 유무·집계 유무·GROUP BY 축·컬럼 선택)을 불개입 신호로 읽는다. HCX 는 같은 질문에도 라운드마다 다른 모양을 내므로 **이 형태의 가드는 채점 점수를 확률변수로 만든다**. 판정 규약으로 옮기면: 가드의 발동 조건은 **질문·Ground 산출물**(이름 토큰 유무·핀 유무·질문 토큰)에서 오는 것이 안전하고, **SQL 텍스트의 모양**에서 오는 것은 위험하다. M′·R′·S′ 셋 다 이 한 문장으로 설명된다.

### ④-2 5R 이 "이월" 로 미룬 두 항목이 6R 에서 ❌ 로 승격했다

- G-2(클래스 열거) → W5 가 ✅ 에서 떨어져 ❌ 2건(V12·W5). 5R 판단("V12 는 ❌ 지만 4R 부터 동일·문형 1종")은 **그 문형이 ✅ 문항도 담고 있다**는 걸 못 봤다.
- W1 근접 후보 → 이월 상태에서 F4 (c) 가 먼저 구현돼 **처방과 다른 후보 생성기**가 실전에 나갔다. 이월 항목이 다른 항목의 구현에 끌려 들어가면 처방이 반쪽만 반영된다.

### ④-3 비결정 자리 재점검(5R ④-2 표 갱신)

| 자리 | 5R | 6R | 성격 |
| :-- | :-- | :-- | :-- |
| 개별 조회 SELECT 모양 | (무사) | **S4 `ORDER BY` · T14 `AVG`** | M′ 🔴 |

**7R 안정성 확인 권고**: 같은 질문 2회 실행이 아니라 **`ORDER BY`·집계가 섞인 SQL 을 가짜 플래너로 재투입**하는 스냅샷 테스트가 결정적이다(HCX 0회). 6R 계획서의 `tests/test_snapshot_round6.py` 고정선이 이 4자리를 안 덮고 있었다는 뜻이므로, 7R 고정선에는 **문항당 SQL 모양 2종**(5R 형·6R 형)을 넣어야 한다.

### ④-4 순자산 축 — Y2 로 세 번째 자리 확인

개별 조회 SUM(T14 gold 2,528 · W11 3,345) vs 목록 MAX(R3 1,453) 는 고지로 설명되나, **랭킹 경로(Y2)에는 고지가 없다**. Y2 의 삼성MMF법인제1호는 MAX 124,295억 · SUM 127,633억으로 두 값 차이가 3,338억이다. 같은 상품이 세 문형에서 세 값으로 나가는 구조는 유지 중.

### ④-5 지연 — 기계 조립 경로는 전부 2.5~5s, HCX 경로는 26~64s

6R 에서 기계 조립이 늘어난 만큼(운용사 확정식 V5 3.2s·Y6 5.6s·Y7 3.7s, 개별 조회 조립 2.5~4.7s) 응답이 빨라졌다. 30s+ 7건은 전부 HCX 가 SQL 을 짜는 경로다 — G-1 랭킹 템플릿이 들어가면 R7(45.0s)·Y2(34.0s)·V16 이 함께 내려온다.
