## ❓ 문제
LLM 으로 기업 KG 에 질의할 때 **온톨로지 자체가 크다는 문제(schema complexity)**. 선행 Sequeda et al. [4] 의 벤치마크는 온톨로지가 11개 개념·30개 미만 관계로 너무 작아 기업 규모(수백 개념·수천 관계)를 대표하지 못한다 (§2). 저자가 지목하는 두 실패: ① 온톨로지 전체가 컨텍스트 윈도에 안 들어감 ② **온톨로지가 크고 복잡할수록 LLM 이 더 환각한다** (§1, p.1 — 저자 관찰, 수치 없음). 파인튜닝 없이(off-the-shelf), 벡터 DB 없이 풀고자 함 (§1, §2).

## 📊 데이터
미국 대형 통신사의 기업 KG 1건 — 온톨로지 약 **500 개념 · 1,000 관계, OWL 공리 7,000개 초과**, 데이터 수십 TB (§1, p.2). 질문은 사용자가 낸 **OLAP 형(긴 경로 탐색·집계·논리합)** (§1 p.2, §3 p.4). **질문 수·정답률·비교 조건 어느 것도 보고되지 않음** — 정량 실험 없음.

## 🛠 방법
LLM 과 외부 "온톨로지 서비스" 가 번갈아 동작하며 온톨로지의 **"딱 필요한 만큼(just enough)" 조각(slice)** 만 점진적으로 드러내는 3단계 (§3):

1. **근사(approximation)** — 온톨로지의 **자연어 서술**(개념·관계 이름)을 주고, 질문과 관련 있는 개념·관계 이름을 LLM 이 고르게 함. 자연어 서술은 형식 서술보다 훨씬 짧아 컨텍스트 제한이 문제되지 않음 (§3, p.3).
2. **정제(refinement, 1회 이상)** — 이전 단계 출력으로 외부 서비스가 **형식(formal) 온톨로지 조각**을 만들어 주고, "조각이 충분하면 SPARQL 로 번역, 부족하면 **빠진 개념·빠진 연결(link)** 을 나열하라" 고 요구. 빠진 연결은 서비스가 **경로 탐색(path-finding) 알고리즘**으로 온톨로지 안에서 개념들을 잇는 경로를 찾아 조각에 보탠다 (§3, p.4).
   - 종료: 빠진 항목 목록이 비면 → 번역 단계. **두 단계 연속 목록이 그대로면 → "형식 번역 불가" 로 판정** (§3, p.4).
3. **번역(translation)** — 마지막 조각에 부합하는 SPARQL 생성 → KG 실행 (§3, p.4).

RAG 와의 차이: 검색을 **LLM 자체**가 하고(벡터 DB 없음), 검색된 지식의 형식화를 즉석 생성 (§2, p.2). 질의어는 SQL 이 아닌 SPARQL (§1, p.1–2).

## ⭐ 핵심 발견
- **온톨로지 전체를 프롬프트에 넣는 것은 "불가능할 뿐 아니라 해로울 수 있다"** — LLM 에 필요한 것은 질문 번역에 충분한 조각뿐 (§1, p.1). 다만 이는 저자의 직관+현장 관찰이며 대조 실험은 없다.
- 온톨로지가 LLM 에 도움이 되려면 담아야 할 것 = ① **개념·관계 이름의 자연어 서술**(근사용), ② **형식 서술**(번역용), ③ **개념 사이 경로**(빠진 link 를 잇는 path-finding) (§3, p.3–4). 즉 값 사전이 아니라 **스키마 수준의 개념·관계·경로**가 이 논문이 말하는 "온톨로지" 다.
- 온톨로지 유무의 효과 수치는 **인용값** — Sequeda et al.: 온톨로지 없음 16% → 있음 54% (§2, p.2; 원출처 [4] arXiv:2311.07509). 이 논문 자체 수치가 아니다.
- 결과 서술은 정성적 한 문장뿐: "생성된 SPARQL 대다수가 양질이며 환각이 거의 없었다" (§3, p.4).
- "빠진 항목 목록이 두 단계 연속 불변 → 번역 불가 판정" 은 **구조적 거절(abstention) 규칙** (§3, p.4).
- 작은·중간 온톨로지(프롬프트에 다 들어가더라도)에서도 조각만 주는 편이 노이즈·환각을 줄인다는 주장 — **미검증 향후 과제** (§4, p.4).

## ▶ 적용
과제 맥락의 질문 "온톨로지를 프롬프트에 얼마나 넣는가 / 무엇을 담아야 SQL 생성에 도움이 되는가" 에 대해:

1. **`<domain>.yaml` 과 스키마를 통째로 넣지 않고 질문별 조각으로 자른다.** 이 논문의 "근사 단계" 를 HCX 로 하지 않고 **이미 있는 [Ground] KG 매핑이 대신한다** — 질문에서 매핑된 노드의 alias 가 (테이블, 컬럼) 을 가리키므로, 그 테이블·컬럼과 관련된 `query_rules`·`normalization`·컬럼 한글명만 프롬프트에 싣는다. 결과: HCX 호출은 그대로 1회, 프롬프트는 슬라이스.
2. **KG 에 추가할 가치가 있는 "관계" 는 개체 간 edge 보다 스키마 수준의 조인 경로**다. 이 논문의 path-finding 이 하는 일은 `ext_*` ↔ 마스터의 `JOIN_KEYS` 를 프롬프트 조각에 넣어 주는 것과 같다. 질문이 ext 테이블 개체(구성종목·설명서 사실)를 건드리면 **해당 조인 경로 한 줄을 조각에 포함**시키는 규칙을 둔다. `feedsInto`·`coversRegion` 같은 개체 edge 를 필터로 쓰는 근거는 이 논문에서 나오지 않는다.
3. **"조각이 부족하면 빠진 것을 말하라" 를 HCX 출력 형식에 한 줄 추가**한다: SQL 대신 `MISSING: <개념>` 을 내면 (a) 부재 선언·enum 밖이면 [Gate] 와 같이 "확인되지 않습니다" 로 종료, (b) KG 에 있는데 조각에서 빠진 것이면 그 컬럼을 보태 **최대 1회** 재호출. 이 논문의 "두 번 연속 불변 → 불가" 종료 규칙을 호출 예산 2회 안에서 흉내 낸 것이다.
4. gold 63문항으로 **전체 yaml 주입 vs 슬라이스 주입**을 한 번 대조해 본다 — 논문이 제공하지 않은 수치를 우리가 직접 만들어야 제안서에 쓸 수 있다.

## ⚠️ 한계
- **저자 인정**: 정량 평가 없음. 작은 온톨로지에서의 효과는 향후 과제 (§4). "환각이 거의 없었다" 는 관찰 진술 (§3, p.4).
- **내가 본 것**:
  - 단일 통신사 KG 1건, 질문 수 미공개, 대조군 없음 — 사실상 **경험 보고**. 인용할 수치는 Sequeda [4] 의 16→54% 뿐이며 그것도 온톨로지 크기 11개념 벤치마크의 값이다.
  - 온톨로지 규모가 우리와 정반대다: 논문은 500 개념·7,000 공리(§1)의 **컨텍스트 초과** 문제를 풀지만, 우리 스키마는 4테이블·280컬럼으로 프롬프트에 다 들어간다. 우리가 기대할 이득은 컨텍스트 절약이 아니라 **노이즈 감소** 쪽인데 그 부분이 바로 미검증 영역(§4)이다.
  - 질의어가 SPARQL·대상이 KG 다. 우리 결측 의미(위장결측·센티넬)·단위·모수 같은 **값 수준 규칙**은 이 논문의 온톨로지 개념에 포함되지 않는다.
  - 단계마다 LLM 을 호출하는 구조(근사 1 + 정제 ≥1 + 번역 1 = 최소 3회). 정제 단계에서 "충분하면 바로 번역" 하더라도 2회.
  - Figure 1 을 보지 못해 외부 온톨로지 서비스와 LLM 사이의 정확한 입출력 형식은 본문 서술로만 파악했다.
