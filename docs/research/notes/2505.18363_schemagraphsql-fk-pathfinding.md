## ❓ 문제
수백 테이블 규모의 기업 DB 에서 스키마 전체를 프롬프트에 넣으면 토큰 한도 초과·노이즈·비용 증가가 생기고, 질문은 실제로 스키마의 작은 부분만 건드린다 (§1). 기존 스키마 링킹은 (a) 신경망 링커·검색 모듈·프롬프트 기반 방식 모두 지도학습·다단 파이프라인·취약한 프롬프트 엔지니어링을 요구하고, (b) "노이즈를 줄일 만큼 정밀하면서 핵심 맥락을 놓치지 않을 만큼 넓게" 라는 정밀도–재현율 트레이드오프를 잘 못 다룬다 (§1, §2.2). 저자의 질문: 파인튜닝·복잡한 프롬프트 없이 스키마 링킹이 되는가 (§2 서두, p.2).

## 📊 데이터

- 실행 정확도는 BIRD 공식 스크립트 그대로 (§4.1, §4.4).
- 보조 평가: BIRD MiniDev (Appendix B, Table 4–6).
- 학습 데이터 없음 — 제로샷 (§1 Contributions, §3.4).
- SQL 생성기 4종: Gemini-2.5-Flash · Gemma-3-27B/12B/4B, 모두 API 호출 (§4.3, §4.5).

## 🛠 방법
1. **스키마 그래프** G=(T, K): 노드 = 테이블, 간선 = 외래키(FK) 관계, 무방향 (§3 Notation). 간선이 2개 미만인 희소 스키마는 이름에 "id" 가 들어간 컬럼을 공유하는 테이블끼리 간선을 추가해 연결성을 확보 (§3 Notation).
2. **Step 1 — LLM 1회 호출**로 질문에서 **source 테이블**(필터 조건에 쓰이는 컬럼을 가진 테이블)과 **destination 테이블**(출력 컬럼을 가진 테이블) 집합을 뽑는다. 출력은 `src=A,B, dst=C,D` 한 줄 (§3.2 Step 1, Prompt 1 p.5). Gemini 2.5 Flash, temperature 0.2 (§4.2).
3. **Step 2 — 경로 열거**: 모든 (src, dst) 쌍에 대해 그래프상 **최단 단순 경로 전부**를 열거하고(SP), 후보 집합 C 와 그 합집합 U(경로에 등장하는 테이블 전체)를 만든다 (§3.2 Step 2).
4. **Step 3 — 선택**: 설정에 따라 두 번째 LLM 호출(Prompt 2, Appendix A)로 경로 하나를 고르거나, 규칙으로 U 를 그대로 반환. 7개 설정(1-1 · 1-n · n-1 · n-n · force-longest · no-union · force-union) (§3.3 표). **기본 설정은 Mode 7 force-union = 합집합 U 를 결정론적으로 반환** → LLM 은 1회만 (§4.2).
5. 생성 프롬프트에는 `Schema` 와 별도로 **`Join Path: {join_path_string}`** 을 넣는다 (Prompt 3, Appendix A). 즉 링킹 결과를 "테이블 목록" 이 아니라 "조인 경로 문자열" 로 전달.
- 비용: 링킹 호출 평균 입력 4,593 토큰 · 출력 14 토큰 (§1 Contributions; §5.4 는 4.6K/14), 최단경로 탐색 O(|E|) 15 ms 미만 (§5.4). 질문당 호출 = 링킹 1 + 생성 1 (§4.5).
- 비교군: "LLM as Schema Linker"(FROM/JOIN 에 들어갈 테이블을 한 번에 열거시키는 단일 호출) · Dense Retriever(multilingual-E5-large-instruct 로 테이블명+컬럼명 임베딩, top-k=1…6) · 타 논문 발표치 (§4.2).

## ⭐ 핵심 발견
- **재현율 우선이 실행 정확도를 올린다.** force-union 은 재현율 95.71 / F6 95.43 으로 기존 최고 ExSLf(F6 93.92) 를 넘지만 정밀도는 86.21 로 단일 LLM 링커(91.79) 보다 낮다 (Table 1). 그런데 생성기 4종 모두에서 고재현율 force-union 이 고정밀 1-1 보다 실행 정확도 2–7 %p(Dev) · 4–12 %p(MiniDev) 높다 (§5.3, Table 3·6). 저자 해석: "LLM 은 노이즈는 무시할 수 있지만 빠진 조인은 지어낼 수 없다" (§5.3). F6 이 종단 정확도와 가장 잘 상관 (§5.3, p.8).
- **조인 경로 근거가 실행 정확도에 준 효과 (Table 3, Dev, Total):** Gemma-3-4B 23.01→29.01, Gemma-3-12B 33.96→45.96, Gemma-3-27B 41.72→53.98, Gemini-2.5-Flash 51.50→62.91 (Baseline→force-union). 저자 요약 "6–12 %p 향상" (§5.3). 이득은 Moderate/Challenging 문항에 집중 — Gemini Challenging 34.72→50.00 (Table 3; §5.3 은 "+15 %"). **다중 조인 질문에서의 이득**이다.
- **링킹이 맞으면 남는 오류는 SQL 생성 쪽.** Gemini force-union 62.91 은 oracle "Ideal Schema Linking" 64.41 에 1.5 %p 차이 (§5.3, Table 3). 약한 모델일수록 oracle 과의 격차가 큼 — Gemma-4B ideal 33.83 vs 29.01 (Table 3).
- **합집합(union) 은 필수, 불필요한 홉은 해롭다.** no-union 은 EMR 73.73 / 재현율 90.03, force-longest 는 EMR 71.64 / 재현율 88.45 로 force-union(76.60 / 95.71)·n-n(78.29 / 95.10) 보다 나쁨 (Table 2, §5.2). 그래프 탐색이 "LLM 단독으로는 놓치는 연결 오류를 고친다" — EMR 75.88(단일 LLM 링커) → 78.29(n-n) (§5.1, Table 1·2).
- **Dense retrieval 만으로는 부족.** Top-6 이 재현율 93.31 이지만 정밀도 35.43, EMR 1.04 (Table 1); 실행 정확도는 Gemini 기준 58.41 로 baseline 51.50 보단 낫지만 force-union 62.91 에 못 미침 (Table 3).

## ▶ 적용
과제 맥락 문서의 세 질문에 대한 답:

1. **FK/조인 그래프를 KG 의 관계(edge)로 잡을 것인가 → 아니다, 결정론적 사전이면 된다.** 이 논문의 이득은 "FK 그래프 + 최단경로 열거" 가 다중 조인 DB(BIRD 11 DB, 다중 홉) 에서 LLM 이 놓치는 조인 경로를 복구하는 데서 나온다 (§5.1, §5.3). 우리 스키마는 마스터 4 + `ext_*` 4, 조인 키는 `JOIN_KEYS` 로 고정 → 그래프의 최단 경로는 항상 길이 1 이고 열거할 것이 없다. 논문 자체가 "간선 2개 미만 희소 스키마" 를 예외 처리한다 (§3 Notation). **kg_edge 에 FK 관계를 추가하지 말고, `JOIN_KEYS` 를 그대로 "조인 경로 문자열" 로 프롬프트에 넣는다.**
2. **조인 경로 근거를 프롬프트에 명시한다 (0 회 추가 호출).** Prompt 3 의 `Join Path: {join_path_string}` 방식을 그대로 — 질문이 `ext_*`(ETF 구성종목·펀드 구성종목·설명서 사실) 를 건드리면 플래너 프롬프트에 `"master.X = ext_Y.Z 로 조인"` 한 줄을 넣는다. 논문의 src/dst LLM 호출(Step 1) 은 우리 [Ground] 단계의 KG alias → (테이블, 컬럼) 매핑이 이미 결정론적으로 대신하므로 HCX 호출을 늘릴 필요가 없다 (제약 2 충족).
3. **테이블 라우팅은 재현율 우선(union).** 국내ETF/해외ETF 처럼 도메인이 애매하면 하나를 고르지 말고 **둘 다** 스키마에 넣는다 — 빠뜨리는 쪽이 노이즈보다 훨씬 손해 (§5.3, Table 3 의 1-1 vs force-union). 단 force-longest 결과(§5.2) 대로 관계없는 테이블까지 넣지는 않는다.
4. **280 컬럼 스키마에서도 "해당 도메인 테이블만" 주는 것은 유효하나, 근거는 테이블 단위다.** 논문은 "스키마가 다 들어가도 초점을 날카롭게 한다" 고 주장하지만 (Abstract) 컬럼 수준 프루닝은 측정하지 않았다 (§4.4 지표 전부 테이블 집합 기준). 그러므로 도메인 라우팅으로 4테이블 중 해당 테이블(+ext) 만 주는 것까지는 이 논문이 지지하고, 그 안에서 컬럼을 더 잘라내는 것은 이 논문이 근거가 되지 못한다 — gold 63 문항으로 직접 재보고 결정.
5. **oracle 격차(§5.3) 의 함의:** 테이블이 맞아도 남는 오류는 SQL 생성이다. 우리 과제에서 "테이블 라우팅" 은 이미 거의 자명하므로, 정확도의 병목은 링킹이 아니라 도메인 규칙(결측 의미·단위·모수) 쪽이라는 기존 판단을 이 논문이 간접 지지한다.

## ⚠️ 한계
**저자 인정 (Limitation, p.8):**
- 중첩·복합 서브쿼리 질문에는 최적화되지 않음.
- FK 가 지나치게 많거나 노이즈가 많은 밀집 그래프에서는 최단경로 열거가 후보를 과하게 넓혀 정밀도가 떨어짐.
- 모든 조인 경로를 동등하게 취급 — FK 중요도·조인 비용 가중치 없음.

**내가 본 것:**
- **평가가 전부 테이블 수준.** Precision/Recall/EMR 이 모두 테이블 집합으로 정의됨 (§4.4). 컬럼 링킹·값 링킹은 다루지 않는다. 우리 과제의 어려움(컬럼 280개 안에서의 선택, 위장결측, 별칭) 에는 직접 근거가 없다.
- **Baseline 정의가 본문과 부록이 어긋난다.** §4.2 는 Baseline 을 "LLM as Schema Linker"(테이블 열거 단일 호출) 로, Appendix A 의 Prompt 4 는 "스키마 링킹 없이 전체 스키마" 로 설명한다. Table 3 의 Baseline 이 어느 쪽인지 확정할 수 없어, "6–12 %p 향상" 이 전체 스키마 대비인지 단일 LLM 링킹 대비인지 불명.
- **Baseline 생성 프롬프트가 매우 얇다** (Prompt 4: 지시 3줄). 규칙·예시·컬럼 설명이 붙은 강한 baseline 대비 이득은 더 작을 수 있다.
- **"Ours" 의 설정이 표마다 다르다.** Dev(Table 1) 는 force-union 을 대표로, MiniDev(Table 4) 의 "SchemaGraphSQL (Ours)" 수치(EMR 82.33) 는 Table 5 의 n-n 과 일치 — 대표 설정을 유리한 쪽으로 골랐을 가능성.
- 링킹 호출 자체가 전체 스키마를 읽는다 (평균 4.6K 입력 토큰, §5.4). 토큰 절감은 생성 호출 쪽에서만 생긴다.
- 영어 질문·영어 스키마 기준. 한국어 질의·한글 컬럼명에서의 src/dst 추출 정확도는 검증 안 됨. 코드는 "공개 예정" (§4.5) — 미확인.
- preprint, 동료심사 여부 미확인.

## 🚫 적용 가능성
**조건부** — "방법(그래프 경로 탐색)" 은 불필요, "교훈(재현율 우선 테이블 union · 조인 경로 문자열 명시)" 은 가능.

- 제약 1(HCX 만, 학습 불가): 충족. 제로샷·학습 없음 (§3.4). 프롬프트·규칙 수준.
- 제약 2(호출 1–2회): 충족. 논문은 링킹 1 + 생성 1 (§4.5) 이지만, 우리는 Step 1 의 LLM src/dst 추출을 KG alias 매핑으로 대체하므로 **추가 호출 0회**. 두 번째 호출(Prompt 2 경로 선택) 은 쓰지 않는다 — 기본 설정 force-union 도 그것을 쓰지 않는다 (§4.2).
- 제약 3(스냅샷 하나, 학습 데이터 없음): 충족. 외부 데이터·학습 불요.
- 제약 4(환각 감점): 간접. 없는 조인·없는 테이블을 지어내는 것은 줄이겠지만 논문은 환각률을 측정하지 않았다. "확인되지 않습니다" 거절과는 무관.
- 제약 5(한국어·무거운 도메인 규칙): 부분 충족. 언어 의존이 없는 결정론적 부분(JOIN_KEYS → 조인 경로 문자열) 만 쓰면 언어 문제는 없다. 도메인 규칙 문제에는 답하지 않는 논문.
- 제약 6(1주, SQLite+yaml+파이썬): 충족. `JOIN_KEYS` 사전 → 프롬프트 문자열 1줄, 도메인 라우팅에 union 규칙 추가 — 반나절 작업. 그래프 모듈·KG edge 신설은 **하지 않는다** (8테이블에서 퇴화, §3 Notation 의 희소 스키마 예외에 해당).

판정 조건: gold 63 문항 중 `ext_*` 조인이 필요한 문항에서 조인 경로 문자열 유/무로 SQL 재현율을 비교해 이득이 확인될 때만 유지. 이득이 없으면 이 논문은 "링킹은 병목이 아니다" 라는 근거로만 인용.
