## ❓ 문제
LLM Text-to-SQL 은 추론 시점에 **정적으로 전처리된 스키마 정보**만 받는다. 실제 DB 는 "같은 뜻의 컬럼이 여러 테이블에 흩어져 있고, 값 형식이 컬럼마다 다르고, 어떤 값은 특정 테이블에만 있는" 상태라 LLM 이 컬럼·값 조합을 사실상 무작위로 고르게 되고, 이것이 같은 문항을 어떤 때는 맞히고 어떤 때는 틀리는 **불안정성의 핵심 원인**이라고 지목한다 (§3.2). 다중 후보 생성 후 선택(MCS-SQL·CHASE-SQL 류)은 이 근본 원인을 해결하지 못한다고 본다 (§3.2). 해법으로 LLM 이 **SQL Probe** 를 스스로 만들어 실행해 DB 를 탐색하게 한다 — 생성 전(후보 탐색)과 수정 시(빈 결과 원인 진단) 둘 다.

## 📊 데이터
- **BIRD** dev: 95개 실제 DB, 12,751 question-SQL 쌍, dirty value + 컬럼 설명 + 외부 지식(evidence) 제공 (§4.1.1). 주 실험·ablation 은 BIRD dev.
- **Spider**: 10,181 질문 / 5,693 SQL / 200 DB (§4.1.1). dev/test 모두 보고 (Table 3).
- 지표: Execution Accuracy(EX) 만 (§4.1.1).
- SFT 데이터: BIRD train 9,428건을 프롬프트 파이프라인으로 롤아웃해 정답 SQL 을 낸 5,231건을 학습 샘플로 채택 (§3.4). Qwen2.5-72B-Instruct, A800 8장 24시간, LoRA rank 16 (§4.1.2, Table 4).
- 모델: Qwen2.5-72B-Instruct 단일 (앙상블 없음, §4.1.3).

## 🛠 방법
3단 파이프라인 (Fig. 1).

**1) Entity-based Schema Linking (§3.1)**
- *Value Retrieval* (§3.1.1): LLM few-shot 으로 질문에서 개체 추출 → **LSH + 의미 유사도**로 DB 안의 유사 값 검색. CHESS(Talaei et al., 2024) 검색 모듈과 같은 방식이라고만 적고 상세는 없음.
- *Soft Schema Linking* (§3.1.2): one-shot 으로 개체별 관련 컬럼 선택. 선택된 컬럼은 이름·타입·설명·값 예시·값 설명까지 풀로, **비선택 컬럼도 이름·타입은 남긴다** (완전 제거 안 함 → 오탈락 방어 + 입력 길이 절감).

**2) Generation Based on Self-Driven Exploration (§3.2)**
- 질문 = **target**(SELECT 절) + **conditions**(WHERE 등) 로 분해 (§3.2, Fig. 2).
- *Candidates Exploration* (§3.2.1): 먼저 target 후보 컬럼만 SELECT 하는 **Base SQL Probe** 여러 개 → 각 Base 에 조건 하나씩(컬럼 후보 + 값 후보) 붙인 **Condition SQL Probe** 를 트리로 전개 (Fig. 3). 조건은 하나씩만, 결합 안 함 (Fig. 9). Evidence 가 컬럼/값을 지정하면 탐색 없이 그대로 쓰라고 명시 (Fig. 9 [Attention]).
- *Combinations Exploration* (§3.2.2): 1단계에서 살아남은 후보를 **전 조건 결합**해 실행. 빈 결과를 낸 조합은 "확실히 부적합"으로 탈락. 프로브 수 = 후보 수의 곱 (예: 1×2×1×3 = 6, Fig. 10).
- *Zero-shot Generation* (§3.2.3): 스키마 + 두 탐색 결과만으로 SQL 생성. question-SQL few-shot 도, 질문 분해 전략도 안 씀. 단 **self-consistency** — 여러 SQL 을 생성해 실행 결과가 가장 일치하는 답 선택 (샘플 수 미기재).

**3) Refinement Based on Self-Driven Exploration (§3.3)**
- 실행 가능 + 비어있지 않으면 통과. SQLite 오류면 오류 메시지로 바로 수정. **빈 결과**면 3단계 (Fig. 4):
  - *Error Cause Identification* (§3.3.1): **SQLGlot 기반 규칙 분해기**(LLM 아님)가 SQL 을 AST 로 바꿔 분할 불가 조건 단위를 찾고, 조건 부분집합별 Sub-SQL 을 만들어 실행 → 각각 NULL/Not NULL 만 LLM 에 전달 (Fig. 8 예시).
  - *Solution Exploration* (§3.3.2): LLM 이 원인 가설 세우고 해법 검증용 프로브 생성. 원인 5종 = ①조건 충돌/중복(동의 컬럼 중 잘못 고름·같은 조건을 여러 컬럼으로 중복 기술) ②값 오기·대소문자(→ LIKE) ③불필요한 JOIN ④컬럼-값 불일치 ⑤서브쿼리 MIN/MAX 범위 불일치 (§3.3.2, Fig. 12).
  - *Modification* : 프로브 결과로 최종 수정 (Fig. 13).
- *Target Checking* (§3.3.3, Fig. 14): LLM 에게 **SELECT 에 불필요한 컬럼이 끼었는지만** 판정시키고, 그 경우만 제거. "확실할 때만 수정, 애매하면 손대지 말 것" 명시.

**4) SFT** (§3.4): 탐색 단계·생성 단계를 따로 파인튜닝한 Explorer/Generator 를 끼워 넣음.

## ⭐ 핵심 발견
- **탐색(SQL Probe) 이 주된 이득, 스키마 링킹은 작다.** BIRD dev ablation (Table 1, 전체 67.67): w/o Soft Schema Linker −0.79 (66.88) · w/o Exploration Before Generation −1.96 (65.71) · w/o Exploration in Refinement −1.70 (65.97) · w/o Refinement Module 전체 −2.22 (65.45) · w/o Target Checking −1.37 (66.30) · **w/o Exploration in Generation & Refinement −3.20 (64.47)**. 두 탐색의 합(−3.20)이 각 단독의 합(−3.66)보다 작다 = 일부 겹치는 오류를 잡는다.
- **탐색 이득은 Challenging 문항에 집중**: 전체 53.10 → 탐색 둘 다 제거 시 48.28 (−4.82pt) vs Simple 74.92 → 72.11 (−2.81pt) (Table 1).
- **Value Retrieval 자체는 ablation 되지 않았다.** Table 1 에 Soft Schema Linker 행만 있고 값 검색 제거 행이 없다. "개체 기반 값 검색이 얼마나 기여하는가"는 이 논문으로 답할 수 없다 — 값 검색은 CHESS 를 그대로 가져왔다고만 적음 (§3.1.1).
- **vanilla 대비**: Qwen2.5-72B-Instruct 60.17 → SDE-SQL 67.67 (+7.50pt, 상대 8.02%) (Table 2, Abstract). SFT 는 +0.52 만 (68.19, Table 1) — 프롬프트만으로 이득의 94% 가 나온다.
- **Spider 에서는 이득이 작다**: dev 73.9 → 87.3 이지만 저자 스스로 "Spider 는 정답 SQL 도 빈 결과를 내는 문항이 많아 탐색 피드백이 잘 안 먹힌다"고 인정 (§4.2.2, Table 3). 즉 **"빈 결과 = 오류" 가정이 깨지는 데이터에서는 이 방법이 약하다.**
- **빈 결과 원인 진단은 LLM 없이 규칙(SQLGlot AST 분해)으로 한다** (§3.3.1). LLM 은 NULL/Not NULL 플래그만 받는다 (Fig. 12–13).
- **Evidence 우선 원칙**: 외부 지식이 컬럼/값/수식을 지정하면 탐색을 생략하고 그대로 쓰라 (Fig. 9). = 사람이 만든 규칙이 있으면 탐색보다 우선.
- LLM 호출 수·지연·비용은 **어디에도 보고되지 않음** (§4 전체). 내가 §3 과 Fig. 9–14 로 센 최소 호출: 개체추출 1 + soft linking 1 + 후보탐색 1 + 조합탐색 1 + 생성 k(self-consistency, k 미기재) + [빈 결과 시] 해법탐색 1 + 수정 1 + target checking 1 → **정상 경로 최소 5+k회, 빈 결과 경로 8+k회**. 프로브 실행 자체는 SQLite 이라 싸지만 프로브를 *만드는* 것은 전부 LLM 이다.

## ▶ 적용
과제 맥락의 질문에 대한 답과 행동:

1. **KG alias 가 이 논문의 Candidates Exploration 을 오프라인·0회 호출로 대체하고 있다는 근거로 쓴다.** 논문이 탐색으로 푸는 문제(§3.2: 동의 컬럼·값 형식 불일치·특정 테이블에만 있는 값)는 우리 데이터의 별칭 폭발(운용사 43종)·코드 컬럼·위장결측과 같은 문제다. 논문은 이를 질문마다 LLM 이 프로브를 짜서 풀고(Fig. 9–10), 우리는 kg_alias 62,558 건에 미리 (테이블, 컬럼, raw 값) 으로 박아 Ground 단계에서 IN 리스트로 넘긴다. Fig. 9 의 "Evidence 가 컬럼/값을 지정하면 탐색 생략" 원칙이 정확히 우리 구조다. → 제안서에 "값 링킹을 런타임 탐색 대신 사전 구축 KG 로 고정해 HCX 호출 0회로 흡수" 로 쓰고, 이 논문의 Table 1 (탐색 −1.96 ~ −3.20) 을 값·컬럼 후보 해소가 정확도를 좌우한다는 근거로 인용.

2. **0행 진단기를 규칙으로 붙인다 (LLM 0회).** §3.3.1 의 SQLGlot AST 분해를 그대로 파이썬으로: HCX 가 낸 SQL 이 0행이면 WHERE 조건을 하나씩 뺀 Sub-SQL 을 실행해 어느 조건이 결과를 죽이는지 판정. 결과를 답변 조립에 반영 —
   - 모든 단일 조건이 0행 → "해당 값이 DB 에 없습니다" (거절, 안전).
   - 단일 조건은 각각 살아 있는데 결합이 0행 → "A 조건 상품 N개, B 조건 상품 M개는 있으나 둘을 동시에 만족하는 상품은 확인되지 않습니다" — 거절 답변의 **근거를 값으로** 준다. 현재 "0행이면 확인되지 않습니다" 일괄 처리보다 채점자에게 환각 아님을 보여주기 좋다.
   - 이 진단은 SQLite 재실행뿐이라 HCX 호출이 늘지 않는다. sqlglot 은 pip 한 줄.

3. **재생성(refinement) 은 조건부 1회만.** 논문의 원인 ①(동의 컬럼 잘못 선택) ④(컬럼-값 불일치) 는 우리에겐 "KG 가 넘긴 컬럼을 HCX 가 무시하고 다른 컬럼을 썼다" 는 형태로 나타난다. 2번 진단에서 **KG 매핑 컬럼 ≠ SQL 의 WHERE 컬럼** 인 조건이 결과를 죽였을 때만 2번째 HCX 호출로 수정(호출 예산 2회 안). 그 외 0행은 재생성하지 말고 거절 — 이유는 ⚠️ 참조.

4. **Target Checking 의 보수 원칙을 validate_sql 에 넣는다** (§3.3.3, Fig. 14): "확실할 때만, 컬럼 제거만" — SELECT 컬럼이 질문의 target 개수보다 많으면 조건 컬럼을 잘라내는 것은 규칙으로 가능(WHERE 에 쓰인 컬럼이 SELECT 에도 있고 질문에 요구가 없을 때). LLM 재호출 없이 처리.

5. **Soft Schema Linking 방식 채택**: 280 컬럼 전부를 프롬프트에 넣되, KG 매핑·규칙이 가리키는 컬럼만 한글명+결측 사유+단위+값 예시를 풀로 붙이고 나머지는 이름·타입만 (§3.1.2). Table 1 에서 이 항목 단독 기여는 −0.79 로 작지만, 우리는 프롬프트 길이(HCX 응답 3–6초) 절감 효과가 더 중요하다.

6. **Fig. 12 Cause 2 의 "= 을 LIKE 로 바꿔라" 는 채택하지 않는다.** 우리 부분일치 규칙은 `query_rules` 에 컬럼별로 사람이 정했고, 0행 났다고 LIKE 로 넓히면 없는 값을 있는 것처럼 만드는 환각 경로가 된다 (제약 4).

## ⚠️ 한계
**저자 인정 (§6)**
- 탐색이 전부 프롬프트 의존 — 프롬프트가 나쁘면 무의미·중복 프로브를 낸다. 프로브 생성이 정적이라 이전 성공/실패로 전략을 바꾸지 못한다.
- Spider 처럼 정답이 빈 결과인 문항이 많으면 탐색 피드백이 약하다 (§4.2.2).

**내가 본 것**
- **"빈 결과 = 오류" 가 이 방법의 전제다.** Combinations Exploration 은 빈 결과 조합을 탈락시키고(§3.2.2), Refinement 는 빈 결과를 반드시 고치려 든다(§3.3). 우리 과제는 **거절이 정답인 문항이 있다** — 이 파이프라인을 그대로 붙이면 "확인되지 않습니다" 가 맞는 문항에서 조건을 느슨하게 바꿔(LIKE, 컬럼 교체, JOIN 제거) 없는 답을 만들어낼 위험이 정면으로 있다. 부록 프롬프트 어디에도 "원래 없는 값일 수 있다"는 분기가 없다 (Fig. 12–13).
- Value Retrieval 은 ablation 없음 → 이 논문은 값 링킹의 기여를 **입증하지 않는다**. 값 링킹 근거는 CHESS 원 논문에서 가져와야 한다.
- 호출 수·비용·지연 미보고. 내 추정(최소 5+k회, k 미기재)은 §3 서술과 프롬프트 개수로 센 것이지 저자 수치가 아니다.
- BIRD/Spider 는 영어·범용 도메인이고 evidence(외부 지식) 가 주어진다. 한국어·금융 도메인 규칙(결측 4분류·센티넬·클래스별 다중 행)에서의 거동은 검증된 바 없다. 특히 "한 펀드가 클래스별로 여러 행" 인 우리 데이터에서 Sub-SQL 의 Not NULL 은 조건이 맞다는 뜻이 아닐 수 있다(다른 클래스 행이 걸릴 수 있음).
- Self-consistency 샘플 수를 밝히지 않아 Table 1 의 이득 중 얼마가 다중 샘플링에서 온 것인지 분리 불가.
- SFT 대비는 같은 Qwen2.5-72B 지만 Table 2 의 상단(AskData, CHASE-SQL 등)은 GPT-4o/Gemini 라 "GPT-4 기반 대부분을 능가" 주장(§4.2.1)은 모델 크기 통제가 안 된 비교다.

## 🚫 적용 가능성
**조건부** — 파이프라인 전체는 **불가**, 규칙 부분만 **가능**.

- 제약 2 (HCX 1–2회) **위반**: 전체 파이프라인은 최소 5+k회 (내 추정, §3 기준). 후보탐색·조합탐색·self-consistency·해법탐색·수정·target checking 이 모두 별도 LLM 호출이다. 프로브 실행은 싸도 프로브 작성이 LLM 이다.
- 제약 4 (환각 감점) **충돌**: 빈 결과를 무조건 오류로 보고 조건을 완화해 고치는 설계(§3.2.2, §3.3, Fig. 12 Cause 2 LIKE) 는 거절이 정답인 문항에서 정확히 반대로 작동한다.
