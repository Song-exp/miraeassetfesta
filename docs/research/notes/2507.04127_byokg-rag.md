## ❓ 문제
학습 데이터 없는 커스텀("bring-your-own") KG 위의 QA. 기존 두 갈래의 실패를 지목한다 (§1):
- KG 별로 파인튜닝한 그래프 검색기(RoG·SubgraphRAG·GNN-RAG)는 2.7만~3만 건의 학습 데이터가 필요 (Table 4).
- LLM 에이전트가 한 홉씩 탐색하는 방식(ToG 등)은 **탐색 시작점(entity linking) 오류에 민감**하고, 집계(aggregation) 같은 연산은 홉 탐색으로 얻을 수 없다 (§1, Fig. 1).

## 📊 데이터
5개 벤치마크·4종 KG, 전부 zero-shot (Table 6, 부록 B):
- WebQSP-IH / CWQ-IH: Freebase 1.5M 트리플, 각 500문항(원본에서 in-house 표본). 1–2홉 / 1–4홉.
- CronQuestions: 시간 Wikidata 325K 트리플, 600문항(유형별 200 표집). 4원조(h,r,t,time)를 (h, r:time, t) 로 변환 (§4.1).
- MedQA + DrugBank 질병 KG: 44.5K 트리플, 227문항. 객관식 보기를 제거해 난도 상향 (§4.1).
- **Northwind (Text2cypher KG): 3K 트리플, 178문항** — 주문·상품·카테고리 같은 관계형 스키마를 그래프화한 "In-Domain Query" 유형. 정답 결과를 그래프에서 실제로 뽑을 수 있는 문항만 남김 (§4.1). **우리 데이터(관계형 마스터 테이블 + 집계 질문)와 가장 닮은 벤치마크.**
- 지표: Hit(정확 문자열 일치), MedQA 는 H@2, Northwind 는 Claude-Sonnet-3.5 LLM-as-a-judge (1/0.5/0) (§4.1). Hit 과 LLMaaJ 정합성 확인: WebQSP-IH 86.6 vs 86.8 (부록 C).
- LLM: Claude-Sonnet-3.5 / Claude-Haiku-3.5 / Llama-3.3-70B, Bedrock API. 그래프 저장소는 Neptune Analytics + openCypher (§4.2).

## 🛠 방법
2단계: **KG-Linker(LLM) 가 그래프 산출물을 만들고, 그래프 도구가 그것을 KG 에 링크·검색** (§3, Fig. 2).

1. **KG-Linker 프롬프트** (§3.1, Fig. 3, 부록 F.1) — 입력은 질문 + KG 스키마(노드 타입·관계 타입·속성, `graph.get_schema()` 수준, p.2 각주 1) + (있으면) 이전 검색 컨텍스트. **한 번의 LLM 호출**로 4개 산출물을 동시에 뽑는다 (§3.1 "single LLM call"):
   - Ẽ 질문 개체 — 프롬프트가 **"애매하면 질문 표기와 함께 DB 에 있을 법한 별칭·전체명·약어를 같이 내라"** 고 지시 (Fig. 4)
   - P̃ 관계 경로 — "스키마에 명시된 관계만 사용, 3개 이상 다양하게" (Fig. 5)
   - Q̃ 실행 가능한 openCypher 질의 — "스키마에 정의된 타입·속성만 사용" (Fig. 6)
   - Ã 초안 답 — LLM 자체 지식 또는 컨텍스트로, 모르면 빈 태그 허용 (Fig. 7)
2. **Entity Linking** (§3.2): 개체 텍스트로 퍼지 문자열 매칭(thefuzz) + 노드 임베딩(bge-m3) 유사도, top-m=3 (기본은 문자열만, 실험은 둘 합집합 §4.2).
3. **Path Retrieval** (§3.3): 링크된 개체에서 P̃ 를 BFS 로 실제 실행해 유효 경로만 남김(Follow-Paths, 식 5) + 개체↔초안답 사이 최단경로(Dijkstra, 식 6).
4. **Graph Query Retrieval** (§3.4): Q̃ 를 그래프 DB 에서 실행, 결과 Qa.
5. **Triplet Retrieval** (§3.5): (a) 에이전트 탐색 — 1홉 확장→LLM 이 관계 선택→LLM 이 다음 개체 선택, 최대 TA=3회 (Alg. 1, 부록 F.2); (b) 점수 기반 — 질문-트리플 임베딩 유사도 top-k(부록 A.1, 트리플을 h/r/t 로 분해해 임베딩 합산) 또는 리랭커 2단 가지치기(부록 A.2: 관계 top-20 → 트리플 top-100 → 최종 top-k).
6. **반복 정제** (§3.6, Alg. 2): C = Tq ∪ Pf ∪ Ps ∪ Qa 를 템플릿으로 verbalize 해서 KG-Linker 프롬프트의 `graph_context` 로 되먹임. 기본 TR=2, 새 개체가 없으면 자체 종료. 마지막에 A = LLM(q, C).

## ⭐ 핵심 발견
- **KG 유형에 따라 이기는 검색 전략이 다르다** (Table 1, Sonnet-3.5): 다중홉 Freebase 는 에이전트 탐색(WebQSP-IH 86.2 / CWQ-IH 69.3), 시간 KG 는 텍스트 임베딩 검색(CronQ 59.8), **관계형 스키마 Northwind 는 질의 생성(LLM+graph-query 55.3)** 이 각각 최강 baseline. Northwind 에서 텍스트 검색 0.7 · 리랭커 3.4 · 에이전트 탐색 3.4 — **집계·필터 질의는 트리플 검색·홉 탐색으로는 사실상 못 푼다** (§5.2 "the ability to generate and execute Cypher queries proves crucial").
- **링킹 산출물을 개체 하나에서 개체+경로+질의+초안답으로 넓히면** (Table 3, CWQ-IH): 점수 검색 63.0→71.6 (+8.6), 에이전트 검색 69.3→73.6 (+4.3). CronQ 도 59.8→63.2, 57.3→65.5. 즉 **entity linking 만으로는 부족하고, LLM 이 경로·질의 형태의 "구조 가설" 을 함께 내는 것이 기여**.
- **실행 결과 되먹임(refinement) 의 이득** (Table 7): 질의 생성 단독 55.3 → 정제 후 64.9 (Northwind, +9.6); 경로 검색 75.2→80.2 (WebQSP-IH); 리랭커 63.0→68.8 (CWQ-IH). Northwind 사례(Table 9): 1차 Cypher 는 `QUANTITY` 를 노드 속성으로 잘못 두어 결과 NONE → 검색된 샘플 트리플에서 `QUANTITY` 가 관계(엣지) 속성임을 보고 2차 질의 성공. **"어느 테이블/관계에 그 속성이 있는가" 를 실제 데이터 샘플로 보여주는 것이 질의 오류를 고친다.**
- **비용**: 점수 기반 변형은 LLM 호출 2–3회로 WebQSP 85.4 / CWQ 68.7, 에이전트 변형은 4.5–6.3회로 87.1 / 71.1; ToG 11.2–14.3회, FiDeLiS 10.7–15.2회 대비 훨씬 적음 (Table 2). 자체 종료로 WebQSP-IH 평균 1.1회, CWQ-IH 2.3회 반복 (부록 D). 지연은 질의 생성 단독 1.0× 대비 BYOKG-RAG 2.4× (Table 8).
- 학습 데이터 0 으로 Recall@10 70.5 (에이전트) — 2.7만~3만 건으로 학습한 RoG 54.5 / SubgraphRAG 58.7 / GNN-RAG 64.1 보다 높음 (Table 4).
- LLM 을 Haiku-3.5 · Llama-3.3-70B 로 바꿔도 개선 방향 유지 (Table 1, §5.1). Northwind 는 Llama 가 68.9 로 오히려 최고.

### 이번 조사 질문에 대한 답
- **어떤 검색 전략이 가장 기여했나** — KG 유형 의존적이되, 우리와 닮은 관계형·집계형 KG(Northwind) 에서는 **질의 생성 ≫ 나머지** (Table 1). 그 위에 **링킹 산출물 다변화(Table 3)** 와 **실행 되먹임(Table 7)** 이 각각 +4~10pt. 관계(edge) 를 필터로 쓰는 "경로 검색" 은 다중홉 백과사전 KG 에서 의미가 있고, Northwind 에서는 별도 수치가 없다.
- **커스텀 KG 가 담아야 하는 것** — 논문이 요구하는 최소치는 (1) **스키마**: 노드 타입·관계 타입·속성 목록 (p.2 각주 1, Fig. 5·6 이 "스키마에 있는 것만 써라" 로 강제), (2) **개체의 텍스트 표기**(문자열/임베딩 링킹용, §3.2), (3) **질의를 실제로 실행할 수 있는 저장소** (§3.4). 어떤 관계 타입을 추가로 잡아야 하는지에 대한 ablation 은 없다.

## ▶ 적용
현재 아키텍처(Ground→Gate→Plan(SQL)→validate→실행)를 바꾸지 않고 옮길 수 있는 것:
1. **Ground 단계에 "LLM 별칭 생성" 을 붙이지 말고, 반대로 kg_alias 가 이미 하는 일이 §3.2 의 문자열 링킹임을 확인** — 논문은 여기에 LLM 이 낸 별칭 후보(Fig. 4 "possible_alias") 를 더해 재현율을 올린다. 우리는 HCX 1회 호출 안에서 Plan 프롬프트에 "질문 표기 → kg_alias 미적중 시 후보 표기 3개를 함께 내라" 항목을 넣어 미적중 로그를 회수하는 정도가 현실적. 임베딩 링킹(bge-m3)은 6번 제약(1주) 상 도입하지 않는다.
2. **Plan 프롬프트를 KG-Linker 식 다중 산출물로** — SQL 만 내게 하지 말고 같은 호출에서 `<entities>`(사용한 테이블·컬럼·IN 값) `<paths>`(JOIN_KEYS 경로) `<sql>` 을 태그로 분리 출력 (§3.1, Fig. 3). validate_sql 이 `<entities>` 의 컬럼이 스키마에 있는지 대조하면 "없는 컬럼 지어내기" 를 실행 전에 잡는다 (4번 제약).
3. **실행 되먹임 1회 = 2번째 HCX 호출** (Table 7·9 근거): 0행이거나 validate 실패면 곧바로 "확인되지 않습니다" 로 가지 말고, 해당 컬럼의 DISTINCT 값 표본·해당 개체가 실제로 존재하는 행 3건을 `graph_context` 로 넣어 SQL 을 한 번 고쳐 쓰게 한다. Northwind 사례가 정확히 "속성이 어느 관계에 붙는가" 를 샘플로 교정한 것 — 우리의 "펀드는 클래스별 다중 행" "위장결측 더미" 문제가 같은 유형. 호출 예산 2회 안 (2번 제약). 되먹임 뒤에도 0행이면 그때 거절.
4. **스키마 프롬프트에 "정의된 컬럼·값만 사용" 강제 문구**(Fig. 5·6 형식)와 **빈 태그 허용**(Fig. 7 "genuinely cannot determine → empty tags") 을 답변 조립 프롬프트에 넣어 거절 문항을 흡수.
5. **KG edge 확장 우선순위는 낮춘다** — 논문의 경로 검색 이득은 백과사전형 다중홉 KG 에서 나왔고(Table 7 WebQSP-IH), 관계형 KG 에서는 질의 생성이 지배적이다. 1주 예산은 edge 보다 `JOIN_KEYS` 를 프롬프트의 관계 경로로 명시하고 실행 되먹임을 붙이는 데 쓴다.

## ⚠️ 한계
- **저자 인정** (Limitations, p.9): 컨텍스트 가지치기가 없어 검색 결과가 길어지면 소형 LLM 이 혼란; KG 를 유일한 외부 소스로 가정. 지연 2.4× (Table 8).
- **내가 본 것**:
  - Northwind 는 3K 트리플·178문항으로 작고(Table 6), 정답을 그래프에서 뽑을 수 있는 문항만 남겨 걸렀다(§4.1) — **"답이 없는 질문에 거절" 하는 능력은 어느 벤치마크에서도 측정하지 않았다.** 환각 감점 체계엔 근거가 없다.
  - **초안 답(Ã) 은 LLM 파라미터 지식에서 나온다** (Fig. 7 "using your existing knowledge base"). 최종 답도 Freebase/MedQA 에서 vanilla LLM 이 이미 54~70% 맞히는 조건(Table 1) 위에서 측정된 것이라, 이득 중 얼마가 KG 에서 왔는지 분리되지 않는다.
  - Table 3 의 KG-Linker ablation 은 개체·경로·질의·초안답을 한 덩어리로 넣고 뺀 것 — **넷 중 무엇이 기여했는지는 분리하지 않았다.** "관계(edge) 를 더 잡으면 좋아진다" 의 직접 근거로는 쓸 수 없다.
  - 관계 타입별·엣지 종류별 ablation 없음. "커스텀 KG 에 무엇을 넣어야 하나" 는 스키마·개체 표기·실행 저장소라는 전제 조건 수준으로만 답한다.
  - 영어 벤치마크만. 한국어 별칭 폭발(운용사 43종 표기 등) 에서 퍼지 매칭·bge-m3 가 같은 재현율을 낼지는 미검증.
  - Table 8 의 행 정렬이 텍스트 추출에서 흐트러져(1.6× 가 에이전트인지 여부) 본문 부록 D 서술로 복원했다.
  - 코드 프리즈 1주 기준으로, 논문의 그래프 DB(Neptune) 의존 부분은 SQL 로 치환해야 하므로 "재현" 이 아니라 "패턴 이식" 이다.

## 🚫 적용 가능성
**조건부** — 프레임워크 통째가 아니라 세 패턴만 이식하는 조건.
- 충족: 1번(학습 없음, 프롬프트+도구만 — 전 파이프라인 zero-shot §4.2), 3번(외부 KB 없이 자체 KG/DB 만 §3), 5번(스키마를 프롬프트에 넣고 "정의된 것만 써라" 강제 — Fig. 5·6), 6번(질의 생성+되먹임은 파이썬+SQLite 안에서 구현 가능).
- 충족하려면 조건: 2번(호출 수) — **에이전트 탐색 변형(4.5–6.3회, Table 2) 은 불가**, 점수 변형도 2–3회이므로 우리는 "KG-Linker 1회 + 되먹임 1회" 로 잘라야 한다. 임베딩 링킹은 bge-m3 추론 자체는 학습이 아니라 1번엔 걸리지 않지만 6번(인덱스 구축·한국어 검증 기간) 상 보류.
- 위반하므로 버릴 것: 4번(환각) — 초안 답 Ã 를 LLM 자체 지식에서 생성하는 부분(Fig. 7) 은 "DB 값만으로 답" 원칙과 정면 충돌, 채택 금지. 거절 능력 미측정(§4.1 필터링) 이므로 거절 정확도는 우리 gold 63 으로 따로 검증해야 한다.
