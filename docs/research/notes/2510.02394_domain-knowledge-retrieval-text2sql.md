## ❓ 문제
LLM text-to-SQL 정확도는 DB 마다 크게 달라지며, 그 원인은 질문의 **도메인 어휘**와 스키마 사이의 간극이다 (§I).
기존 벤치마크(BirdSQL)는 **질문마다 붙은 oracle "evidence"** 로 도메인 지식을 주는데, 실제 서비스에서는 새 질문마다 전문가가 힌트를 써 줄 수 없으므로 비현실적이다 (§I, §III 앞부분).
저자가 지목하는 실패: (a) 힌트가 없으면 정확도 급락, (b) 관련 없는 지식까지 프롬프트에 넣으면 LLM 이 혼란 [9] (§I) — 즉 **"DB 수준 지식 저장소 + 질문별 선별 검색"** 이 필요하다.

## 📊 데이터
- BirdSQL Dev 11개 DB (의료·금융·스포츠 등). DB 평균 6.8 테이블·77.5 컬럼·139.5 질문·131.2 도메인 문장(DS) (Table IV).
- DB 별 질문을 50:50 무작위 분할. **IN Set** 질문들의 oracle evidence 합집합을 "전문가가 준 DB 수준 저장소"로 간주(질문↔DS 매핑은 쓰지 않음). **OUT Set** 의 DS 는 저장소에 없음. OUT 의 약 77% 는 저장소와 겹치는 DS 가 전혀 없는 **OUT-NO Set** (§IV-A).
- 저장소 크기 변화 실험: IN 비율 50→20% 로 줄이면 DS 수 128.5→53.5 (Table X).
- 원 데이터 품질: 질문의 20.17% 는 oracle DS 가 **누락**, 6.72% 는 **오류** (§IV-C, Table V).
- LLM 5종: GPT-3.5-turbo, Mixtral-8x7B, Llama3-70B, sqlcoder-8B, Gemini-1.5-Flash, 모두 temperature 0 (§IV-B). 평가는 실행 정확도(EX), 보조로 evidence F1 (§IV-C).

## 🛠 방법
3단계 프레임워크 (Fig. 1 캡션, §III):
1. **NL 도메인 문장 수집** — 전문가가 자연어로 적는다. 4범주: ① 암호 같은 컬럼명 설명, ② 범주형 컬럼의 값 설명, ③ 형식 불일치(날짜·숫자 표기), ④ 자연어 표현→수식/술어(나이·비율·"가장 흔한") (§III-A, Table I).
2. **구조화 (Structuring)** — LLM few-shot 으로 `'d.x(자연어 표현)' refers to d.q(SQL 조각)` 형태로 번역 (Table II 프롬프트). 숫자·날짜 상수는 고정 자리표시자(예: `100`)로 정규화. DBA 가 선택적으로 교정. LLM 자동 번역과 DBA 수동 번역의 겹침은 어휘 77.67%·의미 88.82% (3개 DB, §III-B).
3. **부분문자열 기반 검색 (SbR)** — 질문 `t` 도 같은 자리표시자로 정규화한 뒤, `t` 의 **연속 부분문자열** 중 길이가 `|d.x|±n` 범위인 것만 임베딩(all-mpnet-base-v2)해 각 DS 의 `d.x` 와 코사인 유사도를 계산.
   `Score(t,d) = max_{|d.x|-n ≤ i ≤ j ≤ |d.x|+n} SIM(d.x, t[i..j])` (Eq. 1) — "DS 하나는 질문의 **일부**에만 대응하고, 한 질문은 여러 DS 를 필요로 한다"는 관찰에서 나온 설계 (§III-C).
   DS 의 `d.x` 평균 4.28 단어 vs 질문 평균 14.55 단어라 후보 부분문자열이 크게 줄어 검색이 "수 분→수 ms" (§III-C). `n` 은 소수의 NL-SQL 쌍으로 튜닝, 실험에서 2~4 (§III-C, §IV-B). K=4(IN)/K=10(OUT) (§IV-B).
4. **SQL 생성** — 스키마(컬럼 설명 포함) + 질문 + "일부는 유용하지 않을 수 있는" 상위 K DS 를 한 프롬프트에 넣어 **LLM 1회 호출** (Table III).

비교 기준선: QS(질문별 oracle DS, 상한), No-DS, All-DS(저장소 전부 주입, NL/Str), 검색 기준선 BM25·BERT 임베딩·MS-MARCO·STSb (전체 질문 매칭), sBSR(단어 단위 분해) (§IV-D).

## ⭐ 핵심 발견
- **도메인 문장 자체의 효과가 크다**: GPT-3.5 IN Set 에서 No-DS 32.2 → QS 42.1 → SbR-Str 47.5 (Table VI). 저장소 없는 OUT-NO 에서도 SbR-Str 36.6 > No-DS 30.1 (QS 41.7) (§IV-E RQ2). 저자는 자기 이득 15.3%p 를 DS 생성 접근 [28] 의 5.7%p 와 대비 (p.4).
- **전부 주입(All-DS) 은 선별 검색보다 일관되게 나쁘다**: GPT-3.5 IN Set All-DS-Str 39.0 vs SbR-Str 47.5 (Table VI); OUT Set 34.2 vs 39.5 (Table VIII). 5개 LLM 모두 같은 방향. 저자 결론: "프롬프트 길이가 문제가 아니어도 **관련 있는 DS 만** 넣는 것이 중요하다" (§IV-E RQ3). **BM25 로 골라만 줘도**(BM25-Str 41.2) 전부 주입(39.0)보다 낫다 (Table VI).
- **구조화 형식(`'표현' refers to SQL조각`) 이 자연어 문장보다 낫다**: 모든 LLM·모든 검색법에서 Str > NL (Table VI). GPT-3.5 All-DS 는 NL 35.1→Str 39.0, SbR 는 NL 38.3→Str 47.5 (Table VI).
- **사람 교정이 중요하다**: LLM 이 자동 구조화한 DS(L-Str) 는 IN 평균 43.6, DBA 교정 후(Str) 47.5 (Table VII); OUT 에서는 32.4 → 39.5 로 격차가 더 크다 (Table IX). 부분 지식만 있는 질문일수록 **틀린 규칙이 치명적** (§IV-E RQ4).
- **질문을 부분문자열로 쪼개 매칭**하는 것이 전체 질문 임베딩보다 낫다: evidence F1 BM25 0.35·BE 0.33·MS-M 0.34·STSb 0.37·sBSR 0.35·SbR 0.39 (§IV-E RQ5). 실전처럼 IN/OUT 구분 없이 K=10 고정 시 SbR-Str 42.6 > QS 41.7 > All-DS-Str 36.6 > BE-Str 31.4 (§IV-E RQ5).
- **저장소가 작아져도 IN 성능은 유지, OUT 만 떨어진다**: IN 47.5→46.8, OUT 39.5→34.4 (50:50→20:80, Table X). 즉 규칙이 **있는** 질문은 안정적으로 맞고, 없는 질문이 손해를 본다.
- **오답 3유형** (§IV-E RQ3, Table XI): (i) 맞는 DS 를 줘도 LLM 이 틀림 — 검색된 DS 를 **필터 조건으로 과잉 적용** (Ex.3: `carcinogenic` 규칙을 SELECT 투영이 아니라 WHERE 에 넣음), (ii) All-DS 가 의미상 틀린 SQL 로 우연히 정답, (iii) 잘못 검색된 DS 가 잘못된 컬럼(`races.name` vs `raceId`)으로 LLM 을 유도 (Ex.2).
- **관계(edge) 에 대한 근거는 없다**: 이 논문의 지식 단위는 값 사전(범주 ②)·컬럼 설명(①)·표기 정규화(③)·유도 수식(④)이며, 엔티티 간 관계·조인 경로는 다루지 않는다. DB 간 DS 는 "우연히·드물게만" 겹친다고 관찰 — 단일 DB 내 지식 설정을 가정 (§II).

## ▶ 적용
과제 맥락의 질문에 대한 이 논문의 답:
- **관계(edge) 를 더 잡아야 하나?** → 이 논문은 근거를 주지 않는다. 대신 우리가 이미 쓰는 **alias 값 사전(범주 ②)** 과 **유도 규칙(범주 ④)** 이 정확도의 주 원천이라는 근거다. 엣지 확장보다 아래를 먼저.
- **관계 외에 무엇이 좌우하나?** → ① 규칙의 **존재**(+10~15%p), ② 규칙의 **선별 주입**(전부 vs 선별 +8.5%p, Table VI), ③ **`표현→SQL조각` 구조**(+3.9~9.2%p), ④ **사람 검수**(+3.9~7.1%p). 실행 피드백·거절은 다루지 않음.

구체 행동 (코드 프리즈 전 1주 내):
1. **`query_rules` 를 두 층으로 나눈다.** `always_on`(더미/센티넬 배제, 기본 모수, LIMIT — 모든 질문에 필요) 과 `triggered`(특정 표현이 나올 때만 필요한 규칙: 위험등급 방향, 클래스 대표행, 벤치마크 부분일치, 레버리지 유도 등). `triggered` 에는 `triggers: [표현 변형 목록]` 을 붙여 **질문에 그 표현(정규화 후)이 있을 때만 프롬프트에 넣는다**. 논문의 SbR 대신 우선 **exact/부분문자열 매칭 + BM25 수준**으로 시작 — BM25-Str 이 이미 All-DS-Str 보다 나았다 (Table VI).
2. **규칙 서술 형식을 `'한국어 표현' refers to <컬럼 조건 SQL 조각>` 으로 통일**한다. 지금 평문 `normalization`·`derivation_rules` 중 SQL 조각으로 쓸 수 있는 것은 그 형태로 바꾼다 (Table II·III 형식). 숫자·날짜는 자리표시자로 정규화한 뒤 매칭 (§III-B) — 한국어 질의도 "보수 1% 이하" → "보수 N% 이하" 로 같은 처리.
3. **프롬프트에 "아래 규칙 중 일부는 이 질문과 무관할 수 있다" 를 명시** (Table III 문구) — 오답 유형 (i)·(iii) 완화. 특히 값 규칙을 WHERE 필터로 과잉 적용하는 실패(Table XI Ex.3) 는 우리 gold 63 에서 "속성을 **보여달라**" 질문과 "그 속성으로 **걸러달라**" 질문을 분리해 검증할 것.
4. **규칙 수가 100개를 넘는 도메인(공모펀드) 부터 선별 주입을 적용**하고, gold 63 으로 전부 주입 vs 선별 주입 EX 를 비교 기록한다. 논문의 저장소 규모(DB 당 ~131 DS, Table IV) 가 우리와 비슷한 도메인부터 효과가 나타날 것.
5. **KG alias 가 이미 범주 ② 검색기다** — 논문의 (ii) "범주형 값 설명" 을 우리는 KG grounding 이 수행한다. 여기에 더할 것은 범주 ③(표기 정규화)·④(유도 수식) 규칙을 **같은 트리거 방식**으로 붙이는 것이지, 새 검색 인프라가 아니다.
6. **규칙의 검증 절차**: 규칙을 사람이 쓴다는 점은 이미 충족(yaml 을 사람이 판정). 논문의 L-Str→Str 격차(OUT +7.1%p, Table IX) 는 **틀린 규칙 하나가 규칙 없음보다 나쁠 수 있다**는 뜻이므로, 규칙마다 gold 문항 1개 이상을 대응시켜 pytest 에 넣을 것.

## ⚠️ 한계
저자 인정:
- SbR 은 저장소에 **관련 DS 가 있을 때**를 위한 것이며, 없는 질문(OUT)을 돕도록 설계되지 않았다 (§IV-E RQ2). 미해결 표현을 자동 식별해 전문가에게 넘기는 것은 향후 과제 (§V).
- 임계값 `n` 튜닝에 소수의 NL-SQL 쌍이 필요 (§III-C).
- LLM 자동 구조화는 노이즈가 있어 DBA 교정 없이는 OUT 에서 오히려 나빠지기도 한다 (§IV-E RQ4, Table IX).
- 대규모 저장소는 ColBERT 후보 검색 + 재순위가 필요하다고만 언급, 실험 없음 (§III-C).

내가 본 것:
- **절대 정확도가 낮다** (최고 47.5%, GPT-3.5 세대). 최신 모델에서 "전부 주입 vs 선별" 격차가 유지되는지는 미검증 — HCX 로 재확인 필요.
- **oracle(QS) 을 이기는 결과는 BirdSQL evidence 의 품질 문제(누락 20%·오류 6.7%, §IV-C) 에 일부 기댄다.** evidence F1 이 최고 0.39 인데 EX 는 oracle 을 넘으므로, "검색이 정확해서" 라기보다 "oracle 이 부실해서" 인 몫이 있다.
- 50:50 단일 무작위 분할, 분산·유의성 보고 없음. "significantly higher" 는 통계 검정 없이 쓰였다.
- **영어 단어 경계 기반 부분문자열**이다. 한국어는 조사·어미가 붙어 어절 단위 매칭이 불안정 — SbR 을 그대로 옮기려면 형태소 분석 또는 문자 n-gram 이 필요하다.
- 임베딩 모델이 영어 전용(all-mpnet-base-v2, §IV-B). 한국어 다국어 모델로 바꾸면 논문 수치가 보장되지 않는다.
- 우리 규칙은 논문의 DS 저장소(DB 당 ~131) 보다 작을 수 있어 "전부 주입의 혼란" 효과가 약할 수 있다. 실제 규칙 수를 세어 본 뒤 적용 우선순위를 정할 것.
- Fig. 1·2 는 텍스트 추출이 깨져 검색 파이프라인의 그림 세부(캐시·배치 단계)는 본문 설명으로만 확인했다.

## 🚫 적용 가능성
**가능** (트리거 기반 선별 주입 + 구조화 형식) / **조건부** (임베딩 SbR 자체) — 제약 대조:
- 제약 1 (HCX API 만, 학습 불가): **충족**. 모델 학습 없음. 논문의 LLM 구조화 단계는 우리 yaml 이 이미 사람 손으로 되어 있어 필요 없다. SbR 의 임베딩 모델은 추론만 쓰지만 영어 모델이라 한국어 대체가 필요 → 이 부분만 조건부.
- 제약 2 (질문당 HCX 1~2회): **충족**. 검색은 LLM 외부(문자열/임베딩), SQL 생성 1회 (Table III). 자기일관성·다중 샘플링 없음 (§IV-B, t=0).
- 제약 3 (스냅샷 하나, 학습 데이터 없음): **충족**. DB 수준 지식 저장소는 우리 yaml 이 그 자체. `n` 튜닝용 소수 NL-SQL 쌍은 gold 63 으로 대체 가능.
- 제약 4 (환각 감점): **주의하며 충족**. 논문은 관련 없는 규칙이 **잘못된 컬럼·불필요한 필터**를 유도한다는 사례를 보여 준다 (Table XI Ex.2·3) — 선별 주입은 환각 감소 방향이며, 거절 로직은 논문 범위 밖이므로 우리 Gate 를 그대로 둔다.
- 제약 5 (한국어·무거운 도메인 규칙): **조건부**. 부분문자열·임베딩 매칭은 한국어 어절 문제로 그대로 옮길 수 없다 → 규칙마다 `triggers` 표기 변형 목록(KG alias 와 같은 방식)을 사람이 적는 **사전 기반 트리거**로 대체하면 충족.
- 제약 6 (1주·SQLite+yaml+파이썬): **충족**. yaml 에 `triggers` 필드 추가 + 플래너에서 규칙 필터링 한 함수. 벡터 인덱스 불필요(규칙 수백 개 이하는 온라인 계산).

판정 요약: **"규칙을 통째로 넣지 말고 질문에 걸리는 규칙만 넣어라, 규칙은 `표현→SQL조각` 으로 써라, 규칙은 사람이 검수하라"** 는 세 주장은 모두 우리 제약 안에서 1주 내 적용 가능. 임베딩 기반 SbR 그 자체는 한국어 검증 없이는 도입하지 않는다.
