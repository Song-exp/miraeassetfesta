## ❓ 문제
Text-to-SQL 에서 답할 수 없는(unanswerable)·불충분한(underspecified) 질문이 들어오면 LLM 이 "그럴듯하지만 틀린" 실행 가능 SQL 을 만들어 조용히 잘못된 결과를 내는 것 (§1). 기존 거절 방식은 두 갈래 모두 약점이 있다고 지목한다 (§1, §2):
- **프롬프트 기반 거절**("모르면 거절하라"): 지시 문구에 민감하고, 모델이 환각 상태에 들어간 바로 그 순간에 실패한다.
- **불확실성 기반 거절**(self-consistency · semantic entropy): 여러 번 샘플링해야 하고, SQL 후보끼리 동치 판정을 하려면 실행이 필요한데 "안전 게이트 이전에 의심스러운 SQL 을 실행"하는 것 자체가 목적과 모순된다.

저자는 거절을 **생성 전(pre-generation)·실행 없이(execution-free)·1회 forward pass 로** 결정하는 "답변가능성 게이팅(answerability gating)" 문제로 정식화한다 (§3.1 Design goal).

## 📊 데이터
네 벤치마크, 모두 이진(답변가능/불가) 분류로 변환 (§4.1):
1. **TriageSQL** (Zhang et al. 2020) — 의료 의도 중심 거절 과제
2. **AMBROSIA** (Saparina & Lapata 2024) — 명확/모호 질문 쌍으로 언어적 모호성 감도 측정
3. **SQuAD 2.0** — Text-to-SQL 밖(독해)으로의 교차 과제 일반화 확인용
4. **MD-Enterprise** — 중국어 금융 수직 도메인 6종(Stock·HR·Loan·Retail·Risk Control·Supervise), 업무 로직·안전 제약 기준 전문가 라벨. **비공개 내부 데이터** (§4.1 각주 1)

분할: 학습/검증 8:2, 데이터셋마다 300건을 held-out 테스트로 샘플 (§4.1 Training Protocol). 백본은 Qwen-3-8B · Llama-3.1-8B (bf16, 최대 길이 2048) (§4.1, Table 1 캡션). 프롬프트 기반 기준선은 DeepSeek-Chat API 제로샷 (§4.1 Baselines).

## 🛠 방법
**LatentRefusal** — 동결된 LLM 의 **중간층 hidden state** 에서 답변가능성을 읽는 탐침(probe) + 임계값 게이트 (§3.1, Figure 2 캡션).
1. 입력 `x = T(schema, question)` 을 동결 LLM 에 1회 통과시켜 층 `l` 의 hidden state `H^(l) ∈ R^{T×d}` 를 뽑는다 (Eq. 1, 6). 층은 개발셋으로 고르며 최종적으로 32층 중 **-16층(중간)** (Table 4).
2. **TRGE(Tri-Residual Gated Encoder)** 탐침: 표준 Transformer 블록(attention + FFN)에 **SwiGLU 게이트 잔차 가지를 하나 더** 붙인 4층 인코더 (Eq. 2–3, d=512, 8 heads, 19M 파라미터 = 백본의 0.3% 미만) (§3.2, §4.3). 의도: 스키마 토큰이 프롬프트를 지배하는 상황에서 "빠진 컬럼·매칭 안 되는 개체·불가능한 조인 경로" 같은 **드물고 국소적인 불일치 신호**를 증폭하고 스키마 상용구는 억제하는 입력 조건부 소프트 마스크 (§3.2 Why tri-residual gating helps).
3. 평균 풀링 → 선형 → 시그모이드로 `p̂` (Eq. 4). 학습은 BCE(Eq. 9; 실제 최적은 label smoothing 0.1, Table 6). LLM 파라미터는 건드리지 않고 탐침만 학습 (§3.3).
4. 게이트: `p̂ < τ` 면 거절 응답, 아니면 SQL 생성으로 진행. `τ` 는 개발셋에서 "허용 오거절률 하에서 거절 재현율 최대" 같은 운영점으로 고른다 (§3.1 Gating rule, §3.3.3). 선택적 분류(reject option) 틀의 적용.

학습 비용: 데이터셋당 300 샘플, A100-80G 1장 10분 (§4.2 Training Efficiency). 추론: LLM forward 52ms + 탐침 2ms = 54ms (Table 2).

**비답변(unanswerable) 분류 체계** — 모델 라벨은 이진 `y∈{0,1}` 뿐이고 (§3.3.1), 세분류는 정의와 프롬프트 템플릿에만 있다:
- §1 정의: 답변가능 = "스키마 하에서 유일하고 유효한 SQL 로 해소되는 질문"; 불가 = 스키마 요소 부재 · 범위 밖 요청 · 주관성 · 언어적 모호성.
- §3.1: 컬럼/테이블 부재 · 제약 모호 · 존재하지 않는 개체 · 범위 밖.
- 부록 A 영문 템플릿(p.13): 답변가능 5특성(특정 시점 값 조회 / 단순 통계 / 조건 검색 / 개체 기본 속성·식별자 / 기간 한정), 답변불가 9특성(구체적 계산 로직 없음 / 미래 예측 / 주관 평가 / DB 밖 정보 필요 / 열린 조언 요청 / 의사결정 지도 / 인과 설명 / 실시간 데이터 / 심층 분석·복잡 모델). 출력은 `{label, tables[{table_name, fields}], reason}` JSON.

## ⭐ 핵심 발견
- 4개 벤치마크 평균 F1 **88.5%(Llama-3.1-8B) / 88.8%(Qwen-3-8B)**. 최강 기준선 SAPLMA(84.6, Qwen) · TSV/SAPLMA(82.9, Llama) 대비 +4.2 / +5.6 (Table 1, §4.2).
- **API 제로샷 프롬프트(DeepSeek-Chat) 기준선도 평균 83.2%** 이고, 특히 **금융 도메인 MD-Enterprise 에서는 97.2%** 로 LatentRefusal(99.6 / 98.8) 과 2점 남짓 차이 (Table 1). 프롬프트 기반이 크게 뒤지는 곳은 언어적 모호성(AMBROSIA 70.3 vs 80.2/80.9)과 의료 의도(TriageSQL 77.8 vs 87.7/87.1) 이다 (Table 1).
- 샘플링 기반(Semantic Entropy, K=10)은 AMBROSIA 에서 62.1 로 LatentRefusal 보다 18.1점 낮고, 지연 740ms vs 54ms (§4.2, Table 2). 저자는 SQL 의 **구문 다양성이 의미적 과신을 가린다**(JOIN 순서·alias 만 다른 동치 SQL 이 불일치로 세어짐)고 해석 (§4.2, §4.4).
- 선형 탐침은 70.4 F1 로 TRGE 87.1 보다 16.7점 낮다 — 답변가능성은 hidden state 의 선형 방향으로 안 읽히고 질문–스키마 비선형 상호작용이 필요 (Table 3, §4.5.1).
- 거절 신호는 **중간층(-16)** 에서 가장 강하고 마지막 층에서 약해진다(재현율 99.8 vs 99.0) — 불확실성이 출력층에 이르며 "자신 있는 환각"으로 붕괴한다는 해석 (Table 4, §4.5.1).
- 실패 유형 두 가지: (1) **의미적 근접 오류** — `revenue` vs `gross_profit` 처럼 이름이 비슷하지만 논리적으로 다른 컬럼일 때 탐침이 불확실성을 과소평가, (2) **다중 홉 조인**이 필요한 질문에서 신호가 약함 (§4.4 Error Analysis).
- 도메인 간 일반화는 안 되고 배포 도메인마다 탐침을 다시 학습해야 한다고 저자가 인정 (Limitations, p.9).

## ▶ 적용
탐침 자체는 못 쓰지만(아래 🚫), 다음은 이번 주 안에 반영할 수 있다.
1. **거절 판정을 "생성 전·실행 없이" 내린다는 원칙을 [Gate] 의 설계 근거로 명시**한다. 지금 `absent_in`·enum 범위 밖 기각이 LLM 0회로 SQL 생성 전에 끝나는 구조는 이 논문의 Design goal (i)(ii)(iii) (§3.1) 과 같은 자리이며, 제안서에 "실행 기반 불확실성 추정을 피한다"는 문장으로 인용 가능. 다만 이 논문은 "실행 = 위험" 이라는 전제인데 본 과제는 SELECT 전용·validate_sql 이 있어 실행 후 0행 → "확인되지 않습니다" 경로도 안전하다. 두 경로를 구분해 쓸 것: **스키마 부재는 Gate(생성 전), 값 부재는 실행 후(0행)**.
2. **부록 A 의 답변가능 5 / 답변불가 9 특성을 HCX 프롬프트의 거절 규칙으로 옮긴다.** 특히 본 과제 문항에 걸릴 것: "DB 밖 정보 필요"(실시간 시세·발행일 8/24 이후), "미래 예측·추천·의사결정 지도"(어떤 펀드가 좋을까), "인과 설명"(왜 수익률이 떨어졌나). 이 특성들은 `ontology/enums/*.yaml` 의 `query_rules` 옆에 `refusal_rules` 로 평문화하고, Plan 프롬프트 한 번에 `{label, tables/fields, sql, reason}` 을 같이 내게 해서 HCX 호출을 늘리지 않는다.
3. **gold 63 에 "거절이 정답인 문항" 을 비답변 유형별로 라벨**해 두고, 게이트 임계값 대신 규칙 커버리지를 그 유형별로 센다 (§3.3.3 의 "오거절률 상한 하에서 거절 재현율" 운영점을 규칙 버전으로). 유형 축은 §1·§3.1·부록 A 를 합쳐 최소 5개: 컬럼/속성 부재 · 값(개체) 부재 · 범위 밖(실시간·외부) · 주관/추천/예측 · 모호(클래스 미지정 등).
4. **§4.4 의 두 실패 유형을 우리 규칙 게이트의 강점으로 뒤집는다.** "의미적 근접 컬럼" (예: 채권의 `표면금리` vs `만기수익률`, 펀드의 `총보수` vs `판매수수료`) 은 학습 탐침이 놓치는 곳이므로 KG alias 와 yaml 의 컬럼 한글명·결측 사유(`not_applicable`)로 **명시적으로** 분기해 두는 것이 정당화된다. 제안서에 이 대조를 쓴다.
5. AMBROSIA 계열 **언어적 모호성**(예: "미래에셋 펀드 수익률" — 클래스 A/C 중 무엇?) 은 어떤 방법도 80% 대에 머문다 (Table 1). 모호 문항은 거절보다 **기본 모수(`query_rules` 의 대표 클래스)로 답하고 가정을 답변에 명시**하는 쪽이 감점 위험이 낮다.

## ⚠️ 한계
**저자 인정**
- 도메인 간 일반화 불가, 배포마다 재학습 필요 (Limitations, p.9).
- Semantic Entropy 기준선은 SQL 동치를 **구문 일치로 근사**해 최선의 성능을 과소평가했을 수 있음 (§4.2, 부록 C.1).
- 의미적 근접 컬럼·다중 홉 조인에서 약함 (§4.4).

**내가 본 것**
- 주력 결과인 MD-Enterprise 는 **비공개 데이터**라 재현 불가 (§4.1 각주 1). 공개 벤치마크만 보면 LatentRefusal 은 80–88 F1 이고 API 프롬프트와의 격차는 데이터셋에 따라 −0.2(SQuAD, Qwen 기준 88.6 vs 87.4)부터 +10.6(AMBROSIA, Qwen) 까지 편차가 크다 (Table 1).
- 학습 데이터 크기가 모순됨: §4.1 은 8:2 분할 후 300건을 **테스트**로 뽑는다고 하고, §4.2 와 Table 5 캡션은 "300 샘플로 **학습**" 이라 한다. 어느 쪽이든 테스트 300건에 임계값을 개발셋에서 맞춘 F1 이므로 신뢰구간이 넓다.
- 지표가 **답변가능성 이진 분류 F1** 이지 종단 SQL 정확도가 아니다. 게이트가 통과시킨 질문의 SQL 이 맞는지는 측정되지 않았다.
- 탐침 입력은 (스키마, 질문) 뿐이라 **값 수준 부재**(존재하지 않는 펀드명, 코드북에 없는 코드)는 원리상 못 잡는다. 본 과제의 거절 문항 상당수가 여기에 있다.
- 프롬프트 기반 기준선은 DeepSeek 제로샷 하나뿐 (§4.1). few-shot·규칙 동봉 프롬프트와의 비교가 없어 "프롬프트 거절은 취약하다"(§1)는 주장은 MD-Enterprise 97.2 (Table 1) 와 잘 맞지 않는다.
- 부록 Table 8 의 하이퍼파라미터 표는 PDF 에서 열이 어긋나 있어(예: "Dropout rate 4096") 값을 신뢰할 수 없다. 본문 값(4층, d=512, dropout 0.2, 층 -16)만 인용했다.
- 과제 지시에는 5쪽으로 적혀 있었으나 실제 파일은 부록 포함 18쪽이다.

## 🚫 적용 가능성
**불가(핵심 기법) / 조건부(정식화·분류 체계·프롬프트 템플릿)**

- **제약 1 위반 — 불가.** LatentRefusal 은 동결 LLM 의 **중간층 hidden state 에 대한 white-box 접근**을 전제로 하며 저자 스스로 "closed API 가 아닌 로컬 배포 모델용" 이라고 못 박았다 (§3.1 Design goal). HCX 는 API 만 제공하므로 hidden state 를 못 뽑고, 탐침을 학습할 GPU 학습 경로도 제약 1 에서 막힌다. 다른 오픈 8B 모델을 로컬에 띄워 탐침만 쓰는 우회는 제약 1(LLM 은 HCX 만)·제약 6(1주, 인프라 추가 불가)·학습 라벨 부재(제약 3, gold 63 뿐 — 논문도 최소 수백 건 라벨 필요, §4.2) 모두에 걸린다.
- **조건부로 되는 것.** (a) "생성 전·실행 없는 게이트" 정식화 (§3.1) 는 이미 있는 [Gate] 와 동형이라 인용·근거로 쓸 수 있다. (b) 부록 A 의 답변가능/불가 특성 목록은 모델 무관한 **프롬프트·규칙 자산**이라 HCX 프롬프트와 yaml 규칙에 그대로 옮길 수 있고 추가 호출이 없다(제약 2 충족). 단 이 템플릿은 논문에서 **기준선**이었고 그 기준선이 금융 도메인에서 97.2 F1 (Table 1) 이었다는 것이 우리가 기댈 수 있는 유일한 근거다 — 중국어·비공개 데이터 결과라 한국어 금융상품 DB 에 그대로 옮겨진다는 보장은 없고(제약 5), gold 의 거절 문항으로 직접 확인해야 한다.
- **규칙 게이트와의 관계.** 논문의 게이트는 확률 임계값이고 우리 [Gate] 는 결정적 규칙이지만, 논문이 학습 탐침의 약점으로 든 "의미적 근접 컬럼" (§4.4) 은 규칙·KG alias 가 정확히 강한 영역이다. 따라서 이 논문은 규칙 게이트를 대체할 근거가 아니라 **규칙 게이트 + 프롬프트 내 거절 규칙 + 실행 후 0행 거절** 의 3단 구조를 정당화하는 데 쓴다.
