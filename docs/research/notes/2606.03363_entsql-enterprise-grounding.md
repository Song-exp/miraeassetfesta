## ❓ 문제
Spider·BIRD·Spider 2.0 은 스키마 일반화·대규모 DB·공개 문서 워크플로를 평가하지만, **사내 지표 정의·보고 관행·회계연도 규칙·조직/상품 매핑 같은 사적(private) 업무 지식**에 SQL 생성이 의존하는 기업 환경은 다루지 않는다 (§1). 저자들은 "구문상 맞는 SQL 을 쓰는 것" 이 아니라 "긴 사내 문서에 SQL 을 접지(grounding)하는 것" 을 과제로 잡는다 (§1 끝–§2 도입).

## 📊 데이터
- 단일 기업의 실제 사용자 Q&A 로그에서 수집 (§2.2 Data Collection). 5 도메인(Treasury 441 · Finance 351 · HR 124 · Business Management 100 · Union/Party Building 50), 15 하위 도메인, DB 그룹 15 · 테이블 35 · 컬럼 1,489 (Table 1, §2.3).
- 인스턴스 = 질문 + gold SQL + **evidence(전문가가 뽑은 짧은 업무 규칙 스니펫)** + **domain document(evidence 와 보조 자료로 합성한 긴 문서)** + DB (§2.2 Context Synthesis). 문서 평균 3.4k–6.1k 토큰(cl100k_base), 질문 평균 22.8–58.3 토큰 (Table 1).
- 96.0% 의 예제가 질문+스키마 밖의 도메인 지식을 요구; gold SQL 평균 388.7 토큰, CTE 84.1% · GROUP 88.6% · JOIN 53.8% · CASE 51.0% · WINDOW 56.1% · RANK 39.7% (§2.3, Fig. 2 좌측).
- 난이도는 gold SQL 토큰 길이로만 구분: Easy <200 · Medium 200–400 · Hard >400 (§2.3). 중국어 원본을 영어로 번역해 정렬 (§2.2). 익명화: 차원 테이블 먼저 치환 후 조인 키로 사실 테이블에 전파 (§2.2).
- 분할 없음 — 평가 전용 벤치마크, 전체 1,066 건이 테스트셋 (§3.1).

## 🛠 방법
방법 제안 논문이 아니다. 평가 프로토콜만 정리한다 (§3.1):
- 세 입력 설정: **Base**(질문+스키마) / **w/Doc**(+긴 문서) / **w/Evidence**(+짧은 전문가 evidence, ablation 용).
- 8개 시스템: 단독 LLM 7종(Claude Opus/Sonnet 4.6, GPT-5.4, Gemini 3.1 Pro, Qwen 3.6 Max, Kimi K2.6, GLM 5.1)은 **단일 턴, temperature 0, 다중 샘플링 없음**(래퍼 재시도 3회는 API 실패 처리용). 에이전트 1종은 Claude Code(Sonnet 4.6) 기본 설정 — 도구 사용·실행 검증·피드백 수정 포함.
- 스키마는 DDL 형식 텍스트, 문서/evidence 는 프롬프트에 그대로 연결. 지표는 SQLite 실행 결과의 순서 무시 동치(EX, 식 (1)(2), §2.1).
- 전문가 상한: 212개 샘플에서 사람 전문가가 같은 세 설정으로 SQL 작성 (§3.3).
- 오류 분석: Qwen 3.6 Max 실패 982건에 1차 오류 라벨 1개씩 부여 (§3.6).

## ⭐ 핵심 발견
- **짧은 evidence > 긴 문서 > 없음.** 최고 시스템(Claude Code) Avg 가 Base 6.8% → w/Doc 15.9% → w/Evidence 21.4% (Table 2, §3.2(2)). 저자 해석: 지식은 "국소화(localized)" 됐을 때 유용하며, 병목은 문맥 길이가 아니라 **관련 규칙의 선택과 접지** (§3.2(2)).
- **evidence 의 이득은 사람에게 훨씬 크다.** 212개 샘플에서 전문가 33.5 → 46.2 → 84.0%, Claude Code 6.1 → 14.6 → 20.3% (Table 3). 저자: 남은 격차는 검색 난이도만이 아니라 "업무 규칙 접지·제약 해석·다단계 SQL 조립" 한계 (§3.3).
- **실패의 절반 이상이 필터(WHERE) 오류.** WRONG_FILTER 54.6% — 필요한 조건 누락, 불필요한 필터 추가, **잘못된 enum 값**, 잘못된 컬럼에 필터 적용. WRONG_SCOPE 14.4%(기간·조직 단위·테이블 입도·엔티티 범위), WRONG_AGGREGATION 10.0%, Other 21.1%(구문·**조인**·계산·분류·지표 누락을 모두 합친 것) (Fig. 4, §3.6). 즉 **조인 경로 오류는 21.1% 안의 일부**이고 값·조건 접지 오류가 지배적이다.
- **긴 문서는 도메인에 따라 효과가 없거나 역효과.** 시스템 평균으로 Treasury 2.1 → 17.7 → 23.4%, Union/Party 0.0 → 0.0 → 20.2%, HR 27.0 → 26.9 → 30.4%(문서 추가 시 소폭 하락), Finance 0.0 → 0.0 → 0.1% (Fig. 3, §3.4). 저자: evidence 는 "정의·범위·필터 조건이 SQL 로 직접 사상될 때" 가장 유용 (§3.4(3)).
- **입력 언어(중/영) 차이는 미미.** BM·Finance 두 도메인, 8시스템 평균에서 최대 차이 0.9pt (Table 4, §3.5). 난이도는 언어가 아니라 도메인·SQL 조립에서 온다는 해석.
- **에이전트(실행 피드백) 의 이득은 있으나 크지 않다.** w/Doc 에서 Claude Code 15.9 vs 최고 단독 Opus 13.3 (+2.6pt), w/Evidence 21.4 vs Sonnet 17.6 (+3.8pt) (Table 2). Easy 에서는 Qwen 3.6 Max 단독이 35.1% 로 최고 (Table 2, §3.2(3)).
- 저자가 제시한 세 방향: 명시적 중간 표현(query planning), 업무 규칙 접지 강화, **생성 후 검증 모듈(스키마 사용·문서 제약·테이블 입도·enum 값 점검)** (§3.6 끝).

## ▶ 적용
과제 맥락의 질문에 대한 이 논문의 답:
1. **"어떤 관계(edge)를 KG 에 잡아야 하는가"** — 이 논문은 KG·관계를 실험하지 않았다. 다만 조인 오류가 Other 21.1% 의 일부에 불과하고 필터/enum/컬럼 접지가 54.6% 라는 점(Fig. 4)은, 우리 KG 가 지금처럼 **값 사전(alias) 역할에 집중하는 것이 정확도 관점에서 옳은 우선순위**라는 간접 근거다. 조인 경로 edge 추가는 이 논문으로는 정당화되지 않는다.
2. **"관계 외에 무엇이 정확도를 좌우하는가"** — 규칙의 **양이 아니라 선택**. 지금 프롬프트에 yaml `query_rules`·`normalization` 를 평문으로 통째로 넣는 것은 이 논문의 w/Doc 설정에 해당한다. 행동: Ground 단계에서 확정된 (테이블, 컬럼, 값) 에 매달린 규칙만 골라 evidence 형태(한 질문당 몇 줄)로 넣는 **규칙 라우팅**을 만든다. yaml 의 각 규칙에 `applies_to: [table, column]` 키를 달고, KG 매핑 결과와 교집합인 규칙만 프롬프트에 넣는다 (Table 2 · §3.2(2) · §3.4(3) 의 evidence 효과). HR 도메인에서 긴 문서가 오히려 성능을 깎은 점(Fig. 3)을 보면 무관한 규칙 제거 자체가 이득일 수 있다.
3. **validate_sql 확장** — 현재는 SELECT 만·허용 테이블·LIMIT 검사. 여기에 §3.6 이 권하는 "enum 값 점검" 을 추가: 생성된 SQL 의 WHERE 리터럴을 파싱해 (컬럼, 값) 쌍이 `ontology/enums` 의 enum 또는 kg_alias 에 있는지 확인, 없으면 재생성 1회 또는 "확인되지 않습니다" 로 거절. 이는 WRONG_FILTER 54.6% 의 하위 유형 "잘못된 enum 값·잘못된 컬럼" 을 LLM 호출 없이 잡는다. 더미 `000000000000`·센티넬 `-100` 배제 규칙이 SQL 에 실제 들어갔는지도 같은 검사기에서 확인 (WRONG_SCOPE 유형).
4. **gold 63 문항의 오류 라벨링** — 실패 문항에 §3.6 의 4분류(Filter / Scope / Aggregation / Other)를 한 개씩 붙여 우리 분포를 확인한다. 우리 도메인은 이 벤치마크와 달리 CTE·윈도우가 거의 없으므로 Filter 비중이 더 높을 것으로 예상되고, 그러면 위 2·3 이 우선.
5. **한국어 입력 자체를 걱정할 근거는 약하다** (Table 4) — 번역·영문화 우회보다 값 링킹과 규칙 선택에 시간을 쓴다. 단 §3.5 는 두 도메인·번역본 기준이라 강한 근거는 아니다.

## ⚠️ 한계
저자 인정:
- 단일 기업·5개 BI 도메인이라 대표성 없음; 익명화가 배포에 중요한 조직 세부를 지웠을 수 있음 (Limitations).
- 영문 입력은 중국어 번역본이라 번역 아티팩트 가능; 중/영 비교는 두 도메인 부분집합에 한정 (Limitations, §3.5).
- 오류 분석은 Qwen 3.6 Max 한 모델 기준 — "진단적 증거" 이지 모델 간 결론이 아님 (§3.6).
- 난이도가 SQL 토큰 길이만으로 정의됨 — "coarse" 하다고 스스로 인정 (§2.3).
- EX 는 견고성·효율·접근제어·업무 효용을 못 잡음 (Limitations).

내가 본 것:
- **거절(abstention)·환각 감점을 전혀 평가하지 않는다.** 모든 문항에 gold SQL 이 있고 "답 없음" 문항이 없다. 우리 과제의 핵심 채점 요소(거절이 정답인 문항)에 대한 근거는 이 논문에서 얻을 수 없다.
- **KG·엔티티 링킹·스키마 링킹을 분리 측정하지 않는다.** evidence 는 사람이 문항별로 고른 것이라 "자동 규칙 선택기" 의 효과가 아니라 **상한(oracle)** 이다. 우리 규칙 라우팅이 이 상한에 얼마나 접근하는지는 별도 검증이 필요.
- 벤치마크 SQL 은 평균 388.7 토큰·CTE 84% 의 BI 분석 쿼리라 우리(단일 테이블 조회·집계 중심, 280 컬럼) 와 형태가 다르다. Finance 도메인 0% 는 우리 도메인의 난이도 예고가 아니라 긴 SQL 조립 난이도다 (§3.4(2)).
- "Doc" 이 evidence 를 포함해 합성된 문서(§2.2)이므로 w/Doc → w/Evidence 차이는 순수하게 "찾기(선택)" 비용이다 — 이 점은 오히려 우리 해석(규칙 선택이 핵심)을 강화한다.
- 단독 LLM 은 모두 최신 프런티어 모델이고 HCX 는 없다. 절대 수치는 이전 불가, 상대 경향(evidence>doc, Filter 지배)만 가져온다.
- Fig. 2 의 토큰 길이 히스토그램·난이도 비율 패널은 미판독 — 본문의 388.7 토큰·난이도 임계값만 사용했다.

## 🚫 적용 가능성
**조건부** — 벤치마크 자체는 쓸 수 없고, 설계 근거로서의 세 가지 결론만 가져온다.
- 데이터셋 직접 사용: **불가**. 제약 3(외부 데이터 금지·한국어 금융상품 도메인 불일치) — 중국어/영어 기업 BI 데이터로 우리 gold 63 을 대체·보강할 수 없고, 도메인이 다르다.
- 규칙 라우팅(evidence 화, ▶ 2): **가능**. 제약 1(프롬프트·규칙 수준), 2(호출 수 불변 — 프롬프트를 줄일 뿐), 6(yaml 키 추가 + 파이썬 교집합, 1주 내). 조건: 규칙마다 `applies_to` 를 사람이 달아야 하며, gold 63 으로 라우팅 전후 EX 를 비교해 확인해야 한다 (논문의 evidence 는 사람이 고른 oracle 이라 자동 선택의 효과는 보장 없음).
- 생성 후 enum/컬럼 검증기(▶ 3): **가능**. 제약 1·2(LLM 호출 0회, SQL 파싱만), 4(없는 값이 WHERE 에 들어가면 차단 → 환각 감점 방어). 조건: 재생성 1회를 붙이면 제약 2 의 "질문당 1~2회" 안에 들어가지만 그 이상은 안 된다.
- 에이전트식 다중 턴 실행 피드백(Claude Code 설정): **불가에 가까움**. 이득이 +2.6~3.8pt 로 작고(Table 2), 제약 2(HCX rate limit·3~6초/호출) 를 넘긴다. 단일 재시도 1회까지만.
- KG 관계(edge) 확충의 근거로: **해당 없음** — 논문이 관계를 실험하지 않았으므로 edge 추가를 지지하지도 반박하지도 않는다. 조인 오류가 소수 범주(Other 21.1% 일부) 라는 점만 "지금 하지 말 것" 의 약한 근거.
