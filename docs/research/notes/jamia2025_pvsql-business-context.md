## ❓ 문제
약물감시(PV) 안전성 DB(500+ 테이블, 테이블당 50+ 컬럼, 5,000+ 필드, 최대 테이블 13억 행)에서 비전문가가 자연어 질문으로 SQL을 만들지 못한다 (p.2 Introduction). 저자가 지목하는 실패: DB 메타데이터(스키마)만 주면 LLM은 "합리적이지만 완벽하지 않은" SQL을 내고, 없는 컬럼을 참조하는 환각·오류가 생긴다 (p.2). 해법으로 PV 전문가의 업무 규칙·DB 지식을 평문으로 정리한 **business context document** 를 RAG 로 넣는다.

## 📊 데이터
- 단일 기업 DB (Oracle Argus 기반 상용 제품, 스키마 비공개) (p.3).
- NLQ 60개 — 과거 사용자 로그에서 선별, 복잡도 저/중/고 = 17/31/12 (p.3 "NLQ selection"; p.6 Results). 학습/검증 분할 없음 — 60개 전부가 평가셋.
- 정답: SME 가 작성한 gold SQL. 복잡도 점수는 gold SQL 기준으로 계산 (p.4) — 시간·테이블수·조인수·WHERE수·GROUP BY/ORDER/집계 유무의 합 (Algorithm 1, p.4), 25/75 백분위로 저/중/고 구분 (p.6).
- 판정: 안전성 데이터 전문가 1인이 pass / partial pass(≤2회 수정으로 정답과 동일 결과) / fail 로 분류 (p.5).

## 🛠 방법
3단계 실험, 모두 GPT-4(Azure) + RAG, 파인튜닝 없음 (p.2–5):
1. **Phase 1 (스키마만)**: SQL Developer 로 자동 export 한 290쪽 스키마 PDF 만 RAG 코퍼스로 사용 (p.2).
2. **Phase 2 (+비즈니스 컨텍스트)**: SME 가 작성한 평문 문서 — 핵심 33개 테이블 정의 + 용어집 + 업무 규칙 + 조인에 필요한 관계 (p.5 "Constructing the business context document"). 예: "New case" 정의(p.5), "후속 서한(follow-up letter) 건수" 는 DB 에 직접 없으므로 `CLASSIFICATION like '%FU Attempt%'` 로 답한다는 규칙(p.5). SQL 생성 힌트도 포함: `SELECT *` 금지, PK/FK 로 조인, 성능 고려 (p.5).
3. **Phase 3 (스키마 축소만)**: Phase 1 스키마를 33개 핵심 테이블로 줄이되 컨텍스트 문서는 뺌 — 스키마 링킹만으로 되는지 확인 (p.2–3). 33개 테이블은 gold SQL 을 보고 선정 (p.2–3).

공통 파이프라인: LangChain 청킹(1000자, overlap 200) → text-embedding-ada-002 → FAISS → 질문당 top-7 청크 검색 → GPT-4 (p.4–5). 페르소나 프롬프트: "Oracle SQL 전문가. 없는 컬럼 조회 금지, 컬럼-테이블 연결 주의, WHERE 는 대소문자 무시 비교. **SQL 을 못 만들면 추가 정보 없이는 만들 수 없다고 말하고 지어내지 말 것**" (p.3–4 인용문). 각 NLQ 는 컨텍스트 초기화 후 독립·무작위 제시, 대화 이력 없음 (p.4–5).

## ⭐ 핵심 발견
- **주최 인용 수치 확인됨**: 스키마만 → pass 5/60 (8.3%), fail 47 (78.3%), partial 8 (13.3%) (Table 1, p.6). 컨텍스트 문서 추가 → pass 47/60 (78.3%), fail 5 (8.3%), partial 8 (Table 2, p.6). 저·중 복잡도만 보면 41/48 = 85.4% pass, fail 5 (10.4%) (p.6). Abstract·Conclusion 도 동일 (p.1, p.7).
- **스키마 축소(링킹)만으로는 부족**: 33개 테이블로 줄여도 pass 6/60 (10%), partial 24 (40%), fail 30 (50%) (Table 3, p.7). fail 은 78%→50% 줄지만 partial 이 급증 — 구조는 맞는데 컬럼명·참조 오류로 손봐야 하는 상태 (p.7). 저자 결론: 스키마 최적화보다 컨텍스트 문서가 더 결정적 (p.7).
- **효과의 구체적 기전 = 개념→(컬럼, 값) 규칙**: "후속 서한" 질문은 스키마 어디에도 letter 가 없고, 컨텍스트 문서의 `CLASSIFICATION like '%FU Attempt%'` 규칙이 있어야만 풀림; 스키마만으로는 LLM 이 유추 못함 (p.5). 문서 구성요소는 테이블 정의·용어집·업무 규칙·조인 관계 (p.5) — 즉 값 사전 + 도메인 규칙 + 조인 경로.
- 고복잡도(12문항)는 컨텍스트가 있어도 pass 6 / partial 6 (Table 2) — 다중 조인·집계 질의는 여전히 수작업 보정 필요 (p.6–7).
- 저자의 통계: Fisher 정확검정 P = .1655 (Phase 1) → .0006 (Phase 2) → .2373 (Phase 3) (p.6–7).

## ▶ 적용
과제 맥락의 질문(관계 vs 규칙 vs 링킹 vs 거절 vs 검증)에 대해 이 논문이 말하는 것:
1. **규칙 문서(semantic layer)가 가장 강한 근거** — 관계(edge)가 아니다. 이 논문의 "관계"는 PK/FK 조인 경로뿐이며 (p.5), 계층·동의 관계 edge 의 효과는 실험하지 않았다. 지금 아키텍처의 `query_rules`·`normalization`·`derivation_rules` yaml 이 정확히 이 논문의 business context document 에 해당하므로, **남은 1주는 KG edge 확장보다 규칙 문서의 빈칸 메우기**에 쓴다. 구체적으로: gold 63 문항 각각에 대해 "질문 속 개념 → (테이블, 컬럼, 술어)" 매핑이 yaml 에 평문으로 존재하는지 점검하고, 없는 것(예: "후속 서한"류의 DB 에 직접 없는 개념 — 우리로 치면 '레버리지', '모자펀드', '고위험 제외')을 규칙으로 추가한다 (p.5 사례).
2. **ext_* 조인 키를 평문 규칙으로 프롬프트에 넣는다** — 논문은 "PK/FK 로 조인" 지시와 관계 서술을 문서에 명시 (p.5). `JOIN_KEYS` 를 스키마 표가 아니라 "펀드 구성종목은 X 컬럼으로 마스터와 잇는다" 식 문장으로 [Plan] 프롬프트에 포함.
3. **스키마 링킹(컬럼 축소)에 기대지 않는다** — Table 3: 축소만으로 pass 10%. 우리 280 컬럼은 이미 작으므로 컬럼 프루닝보다 컬럼별 결측 의미·단위 서술이 우선.
4. **거절 지시문 유지** — 페르소나 프롬프트의 "지어내지 말고 못 만든다고 말하라" (p.4) 를 [Plan] 프롬프트에 그대로 둔다. 단 논문은 거절 정확도를 따로 재지 않았으므로(fail 에 섞임, p.7) gold 의 거절 문항으로 우리가 직접 측정.
5. **벡터 검색은 도입하지 않는다** — 논문의 RAG(top-7 청크)는 290쪽 스키마·5,000 필드를 프롬프트에 못 넣어서 쓴 우회 (p.2, p.4–5). 우리는 도메인당 규칙 문서 전체를 인라인하고, 길이가 문제면 [Ground] 가 정한 테이블(도메인)로 규칙을 잘라 넣는다 — 제약 6 안에서 해결.
6. **평가 분류를 빌린다** — gold 63 결과를 pass / partial(≤2회 수정) / fail 로 나누고 (p.5), Algorithm 1 (p.4) 로 복잡도 층을 매겨 층별 정확도를 보고서에 적는다. partial 이 많으면 컬럼명 매핑(값 사전) 문제, fail 이 많으면 규칙·의도 문제로 원인을 분리할 수 있다 (Table 3 해석, p.7).

## ⚠️ 한계
**저자 인정**
- NLQ 60개, 단일 기업 DB — 확장성·일반화 미검증 (p.7 Discussion, p.7–8 Conclusion).
- 고복잡도·모호한 의도는 여전히 미해결 (p.7–8).
- 운영 시 스키마 변경마다 컨텍스트 문서를 유지보수해야 함 (p.5).
- 상용 DB 라 스키마·문서 전문 비공개, 편집본만 부록 (p.3, p.5).

**내가 본 것**
- **Phase 3 의 33개 테이블은 gold SQL 을 보고 골랐다** (p.2–3) — 테스트셋 정보가 코퍼스 선정에 들어간 누출. Phase 2 문서도 같은 33개 테이블 기반이므로(p.5) 78.3% 는 "정답에 필요한 테이블이 이미 추려진 상태에서의" 수치다. 공정한 Phase 1 대비 이득은 과대평가될 수 있다.
- 판정자 1인, 이중 판정·일치도 없음 (p.5). partial 의 "≤2회 수정" 도 판정자 재량.
- Fisher 검정을 "단계별 P 값"으로 보고(p.6–7)하는데 무엇과 무엇의 2×2 표인지 본문에 없다 — 통계 서술은 인용하지 않는 것이 안전.
- 실행 피드백·자동 검증 없음: SQL 실행 결과 비교는 사람이 했다 (p.5). 우리의 validate_sql + 0행 처리 같은 자동 검증 효과는 이 논문에서 알 수 없다.
- GPT-4 결과. HCX 에서 같은 폭의 이득이 나는지는 미지수 — 규칙 문서 길이가 커지면 소형 모델은 오히려 혼동할 수 있다.
- 제목·초록의 "RAG" 는 사실상 규칙 문서 청크 검색이며, 논문 스스로 "hybrid" 라 부른다 (p.6). 검색이 얼마나 기여했는지 ablation 없음.
- Fig.1–4·부록 S1 은 이미지/외부 파일이라 본 카드에서 확인 못 함 — 문서의 실제 서식(표 정의가 어떤 문장 형태인지)은 부록을 열어야 안다.

## 🚫 적용 가능성
**가능** — 방법 전체가 프롬프트·문서 수준이다.
- 제약 1 (HCX API 만): 파인튜닝 없음, 생성은 API 호출만 (p.5 "without additional fine-tuning") → 충족. 임베딩 검색(ada-002, p.4)은 우리 규모에서 불필요하므로 생략해도 방법의 핵심(규칙 문서)이 유지된다.
- 제약 2 (호출 1~2회): NLQ 당 GPT-4 1회 호출, 다중 샘플링 없음 (p.4–5) → 충족.
- 제약 3 (스냅샷·학습 데이터 없음): 외부 KB 없음, 문서는 SME 가 손으로 작성 (p.5) → 충족. 우리 yaml 이 그 문서다.
- 제약 4 (환각 감점): 거절 지시문이 프롬프트에 있음 (p.4) → 부합. 단 거절 성능은 미측정.
- 제약 5 (한국어·금융): 도메인 무관 방법. 한국어 결과는 없음.
- 제약 6 (1주): 새 인프라 없음. 규칙 yaml 보강 + 프롬프트 문장화는 파이썬·yaml 안에서 끝난다.
조건: 78.3% 라는 절대치는 옮겨 오지 말 것 (n=60, gold 기반 테이블 선정, GPT-4). 옮길 것은 "스키마만 < 스키마 축소 < 스키마 + 평문 규칙 문서" 라는 순서와 "개념→(컬럼,값) 규칙이 없으면 LLM 은 유추 못한다" 는 기전이다.
