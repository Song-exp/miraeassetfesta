### 2-2. ② `REFUSE:` — 플래너 층 답변불가

`enums/_refusal.yaml` 5사유(실시간 시세 · 미래 예측 · DB 밖 정보 · 인과 설명 · 주관 판단→CLARIFY 유도)가 근거문서 `# 답변불가 규칙` 블록으로 실리고, 플래너는 해당 시 `REFUSE: <사유>` 한 줄을 낸다. 파이프라인은 SQL 실행·답변 생성 호출 없이 종료.

**PROJECT.md 가드**를 규칙 본문에 박았다 — "추천" 은 정렬 축이 있으면 답변 가능(Top-N), 축이 없으면 REFUSE 가 아니라 CLARIFY. "현재 판매 가능한" 은 스냅샷 상태라 REFUSE 아님. "2027년 만기" 는 만기 조건이라 답변.

**예시 (gold BND-R-005, 플래너 스텁)**
```
4. [Gate] 통과 — 대상 테이블 ['domestic_bonds'] · 기준일 이후 시점 ['2027'] 포함 → SQL 의 mat_dt 사용 여부로 사후 판정
6. [Refuse] 답변불가 — 플래너 판정 (근거: 답변불가 규칙 블록) · 사유: 시장 전망은 데이터에 없는 미래 예측입니다
7. [Decision] 데이터 범위 밖 — HCX 답변 생성 없이 종료
answer: 요청하신 내용은 제공된 데이터(기준일 2026-08-22)로 확인할 수 없습니다. 시장 전망은 데이터에 없는 미래 예측입니다
```
개선 전엔 이 문항이 HCX 의 SQL 생성 → `mat_dt` 사후검사에 걸려 "기준일 이후 정보는 확인할 수 없습니다" 로 갔다 — 맞는 결과지만 **답변 생성 호출까지 갔고 사유가 '기준일'뿐**이었다. 전망·인과·실시간처럼 연도가 없는 범위 밖 질문은 경로가 없었다.

**기대효과·근거**: REF-1 Table 1 — 학습 탐침 없이 **프롬프트 기준 거절만으로도 금융 도메인 97.2 F1**. 우리 제약(HCX API·1주)에서 쓸 수 있는 유일한 ② 층 방법. 호출 수: REFUSE 시 답변 생성 호출이 빠져 오히려 1회 감소.

## 3. R-4 — 값 검사기 · 조건부 재생성 1회 · 0행 진단

### 3-1. 값 검사기 `guard.check_values` (HCX 0회)

WHERE 의 `col = '리터럴'`·`col IN (...)` 을 뽑아 **그 컬럼의 전 값을 아는 사전**과 대조한다. 사전 = `loader._build_value_index` — kg_alias 가 컬럼 distinct 를 ≥98% 덮는 22컬럼 + R-1 어휘 35컬럼 = **57컬럼**. 부분 사전(상품명·자유 텍스트)은 검사하지 않는다 — 정상 값을 기각하면 안 되므로. `LIKE` 는 부분일치 규칙의 정당한 경로라 건너뛴다.

**예시 (실제 trace — 첫 SQL 이 틀린 리터럴을 낸 경우)**
```
7. [Guard] 값 검사 실패 — domestic_bonds.crd_grd = 'AA-등급' 은(는) DB 에 없는 값 (실제 값 예: A+ · A- · A0 · AA+)
8. [Plan] 재생성 1회 — 문제를 근거문서에 붙여 다시 요청 (누적 0.0s)
9. [Plan] 재생성 SQL — 아래 문장을 실행합니다
10. [Guard] SQL 검사 통과 (SELECT 단일문 · 테이블 화이트리스트 · LIMIT · WHERE 값 사전 대조)
11. [Execute] 5행 조회 (상한 30)
```
재생성 프롬프트에는 이전 SQL·문제·"없는 값이면 조건을 빼지 말고 REFUSE 로" 가 붙는다. 두 번째도 실패하면 **조건을 완화하지 않고** "요청하신 조건의 값이 데이터에 없어 확인할 수 없습니다" 로 종료:
```
7. [Guard] 값 검사 실패 — overseas_etfs.cu_fund_mgmt_co = 'Samsung Asset Management' 은(는) DB 에 없는 값 (실제 값 예: 21Shares US LLC · …)
10. [Guard] 재생성 후에도 실패 — …
11. [Decision] 값이 DB 에 없거나 SQL 이 안전하지 않아 종료 (조건을 완화하지 않는다)
```

**예산 가드**: 재생성은 `validate_sql` 실패 또는 값 검사 실패 **때만**, 그리고 SQL 1회차 이후 누적 시간이 `REGEN_BUDGET_S = 12초` 안일 때만. 0행은 재생성 대상이 아니다(거절이 정답인 문항에서 조건 완화 = 환각, PROJECT.md §9).

**기대효과·근거**: 기업 Text-to-SQL 실패의 **54.6% 가 WHERE 필터·enum 값 오류**(ENT-1 Fig. 4), 개체명을 verbatim 으로 제약하니 질의 성공 0→82%(KGG-1 §5). 실행 되먹임 1회는 관계형 QA 에서 55.3→64.9(KGQA-1 Table 7). 배포 스모크에서 실제로 본 사고 — 깨진 입력에 HCX 가 `cu_fund_mgmt_co = 'BlackRock' AND cu_base_index = 'S&P 500 Index'` 를 지어냈다 — 가 이 검사기의 첫 대상이다.

### 3-2. 0행 진단 `guard.diagnose_zero_rows` (HCX 0회)

0행이면 WHERE 의 최상위 AND 조건을 하나씩 떼어 각각 몇 건인지 센다(SQLite 재실행뿐). 서브쿼리·UNION·HAVING 이 있으면 건너뛴다.

**예시 (실제 trace)**
```
8. [Execute] 0행 조회 (상한 30)
9. [Diagnose] 0행 원인 — 조건별 단독 조회: crd_grd = 'AAA' → 8,722건 / srfc_irt > 20 → 0건. 값 자체가 없는 조건: srfc_irt > 20.
answer: 조건에 해당하는 상품이 데이터에서 확인되지 않습니다. 조건별 단독 조회: crd_grd = 'AAA' → 8,722건 / srfc_irt > 20 → 0건. 값 자체가 없는 조건: srfc_irt > 20.
```
두 조건이 각각 존재하나 교집합이 없으면 "각 조건은 존재하나 동시에 만족하는 상품이 없습니다" 로 적는다.

**기대효과**: 거절 답변에 **값으로 된 근거**가 붙는다 — 채점자가 "확인되지 않습니다" 를 환각 회피가 아니라 데이터 판정으로 읽게 한다(`think_trace` 근거 배점). SDE-SQL(VAL-1 §3.3.1)의 규칙 분해기를 LLM 없이 옮긴 것이며, 그 논문의 위험(빈 결과를 오류로 보고 조건 완화)은 **의도적으로 뺐다**.

## 5. R-2 — 규칙 2층 (`always_on` / `triggered`)

**변경**: `query_rules` 값이 `{triggers: [...], text: ...}` 이면 질문에 트리거 낱말이 있을 때만 프롬프트에 싣는다. 문자열 규칙은 종전대로 항상. `planner_context(tables, question)` 시그니처 확장(호환: question 없으면 전부). `RULES_MODE=full` 환경변수로 종전 방식 복원(paired 실험 대조군).

**적용**: 펀드 규칙 4종(`이름표기_구조어휘`·`이름표기_우선순위`·`벤치마크검색`·`영문명`) — 내가 만든 규칙만. **채권 26종·펀드 나머지는 담당자 판단으로 태깅**해야 효과가 난다.

**실측**: 펀드 규칙 17.0KB(전부) → **14.9KB**(트리거 없는 질문, −13%). 채권은 태깅 전이라 14.3KB 그대로. 근거문서 전체(펀드, 목표전환 질문)는 22.4KB.

**기대효과·근거**: 규칙 저장소 전부 주입 39.0 < 선별 47.5(DK-1 Table VI), 긴 문서 < 짧은 evidence(ENT-1 Table 2). 반대 근거(SL-1 §6.5: 2.2K 토큰 문서는 통째가 낫다)가 있어 **우리 크기에서 어느 쪽이 맞는지는 §7 paired 실험이 결정**한다 — 그래서 `RULES_MODE` 스위치를 함께 넣었다.
