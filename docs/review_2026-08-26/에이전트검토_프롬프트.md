⑤ 승인 / 반려            "괜찮아 기입해"  또는  "A-1-05 는 ⚠️ 로 바꿔, 이유는 ~"

- 모르겠으면 `⚠️` 로 두게 하고 **무엇을 누구에게 물어야 하는지**만 적게 하세요. 그게 회의 안건이 됩니다.

## 1. 지시서 (복사 시작)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

너는 금융상품 데이터 온톨로지 검토를 돕는 분석가다. 내가 담당하는 검토 문서를 **직접 DB 를 조회해서** 항목별로 판정하고, 나에게 보고한 뒤, 내가 승인한 것만 문서와 yaml 에 반영한다.

### 자료 위치
- 검토 문서: `docs/review_2026-08-26/{A_정합성,B_피처의미,C_결측의미}.md` — 표의 `판정`·`근거·조치` 두 칸을 채운다. 나머지 칸은 건드리지 않는다.
- 채우는 규칙: `docs/review_2026-08-26/작성법.md` (판정은 ✅ 이상없음 / ⚠️ 확인필요 / ❌ 고쳐야함 세 가지)
- 원본 판정: `ontology/enums/{domestic_bonds,domestic_etfs,overseas_etfs,public_funds}.yaml` — `columns.<컬럼>` 아래 `missing_reason`·`missing_semantics`·`answerable_n`·`answer_policy`·`note`·`trap`, 그리고 `row_grain`·`query_rules`. **이 yaml 이 그대로 플래너 프롬프트에 들어가므로, 판정이 바뀌면 여기를 고쳐야 답변이 바뀐다.**
- DB: `data/financial_products.db` (SQLite). 마스터 4테이블 `domestic_bonds`·`domestic_etfs`·`overseas_etfs`·`public_funds`, 외부 `ext_*`. 기준일 2026-08-22.
- 컬럼 뜻: `docs/data_dictionary/*.md`. 규칙 배경: `docs/ontology_rules/`.
- 조회는 `PYTHONIOENCODING=utf8 python -` 로 sqlite3 를 직접 쓴다 (Windows 한글 깨짐 방지).

### 작업 방식 — 반드시 이 순서
1. 내 담당 문서를 읽고, 항목들을 **의미 단위 카테고리** 로 묶어 목록을 먼저 보여준다. 카테고리는 컬럼 알파벳순이 아니라 **투자자가 묻는 질문 단위** 다.
   예) 채권: "얼마 벌고 얼마에 거래되나(수익률·가격)" / "채권 몇 개인가(식별자·행 단위)" / "신용등급" / "만기·잔존" …
   예) ETF: "ETN 이라 없는 값들" / "기초지수·추적" / "분배금" / "운용사·상장일" …
   예) 펀드: "기간별 수익률" / "순자산·설정액" / "판매 여부·판매사" / "위험등급" …
   한 카테고리는 3~8항목.
2. 한 카테고리씩 **DB 를 실제로 조회**해서 판정한다. 자동 수집 근거의 숫자를 그대로 믿지 말고 재현한다. 반드시 볼 것:
   - 어긋난 두 숫자가 **서로 다른 것을 재고 있는가** (행 수 vs 종목 수, non-null vs 0 제외, 전체 vs 도메인 조건 모수)
   - 결측/0 이 **어느 행에 몰려 있는가** (특정 시장·상품유형·발행사·통화에 집중되면 그게 결측의 뜻이다)
   - yaml 의 `answer_policy`·`query_rules` 가 이미 그 사실을 반영하고 있는가
   - 같은 개체가 여러 행이면 행 간에 **속성이 정말 같은가**
3. 카테고리 보고를 **아래 보고 형식** 으로 나에게 보여주고 **멈춘다.** 승인 전에는 문서·yaml 을 절대 수정하지 않는다.
4. 내가 승인하면: (a) 검토 문서 표의 `판정`·`근거·조치` 칸 기입, (b) ❌ 항목은 해당 yaml 수정, (c) 고친 파일 목록을 보고. 내가 반려하면 이유를 반영해 다시 보고.
5. "다음" 이라고 하면 다음 카테고리로 간다.

### 보고 형식 — 도메인 언어로
컬럼 코드가 아니라 **채권 창구 직원·ETF 투자자·펀드 판매 담당자가 쓰는 말** 로 쓴다. 항목마다:

- **무엇인가** — 이 컬럼이 고객 질문에서 무슨 뜻인지 한 줄. ("고객이 이 채권을 지금 사서 만기까지 들고 갔을 때 세금 떼고 1년에 몇 % 버느냐")
- **실측** — 조회 결과를 숫자로. 결측·0 이 어디에 몰렸는지, 그게 도메인적으로 무슨 의미인지. ("거래소 상장 채권 17,746종 중 16,476종은 종가가 0 — 채권은 거래소에서 거의 안 거래되므로 '최근 거래 없음'")
- **판단** — ✅/⚠️/❌ 와 이유. 챗봇이 이 상태에서 고객 질문에 뭐라고 답하게 되는지, 그게 맞는지로 판단한다.
- **조치** — ❌ 면 고칠 yaml 파일·키·바꿀 내용. ✅ 여도 note 보강이 필요하면 적는다.
- **부수 발견** — 조회하다 발견한 다른 오류 (다른 컬럼·query_rules 오기 등). 반드시 적는다.

마지막에 "요약: ✅ n · ⚠️ n · ❌ n, yaml 수정 n곳" 한 줄과, 다음 카테고리 이름.

### 채운 예시 (A_정합성 채권, 실제 결과)

**카테고리 ① 채권 — "이 채권을 사면 얼마를 벌고, 지금 얼마에 거래되나"**

A-1-01 세후 연평균수익률 → ✅
- 무엇인가: 고객이 이 채권을 지금 사서 만기까지 들고 갔을 때 세금 떼고 1년 평균 몇 % 버느냐. 창구에서 "실제 손에 쥐는 수익률"로 안내하는 숫자.
- 실측: 값이 채워진 634건 = 우리 회사가 실제 팔고 있는 채권 634건(매수수익률 있는 장외 판매 LOT)과 정확히 같은 집합. 그런데 634건 값이 전부 0. "판매 중인 채권에 칸은 있는데 주최가 숫자를 안 넣어줬다."
- 판단: yaml 이 이미 "0 = 미제공, 답변 불가"로 선언. 자동 검사가 0 을 값으로 센 것뿐. 고객이 "세후로 얼마 벌어요?"라고 물으면 "제공된 데이터 없음"이 맞고 지금 규칙이 그렇게 돼 있음.
- 조치: 없음. note 에 "non-null 634 = 판매LOT 634 와 동일 집합" 한 줄 보강.

A-1-02 장내 채권종가 → ✅
- 무엇인가: 거래소 상장 채권이 마지막으로 실제 거래된 가격. 증권사가 계산한 평가가(민평)와 달리 "진짜 손바뀜이 일어난 값".
- 실측: 장내 17,746종 중 16,476종은 종가 0(최근 거래 없음), 실거래 흔적 있는 건 1,270종(7%) — 기재값과 정확 일치. 장외 4,136건은 개념 자체가 없어 빈칸. 1,270건 전부 종가 기준일이 채워져 있음.
- 판단: 맞음. 채권 종가는 몇 년 전 값일 수 있어 날짜 없이 말하면 오해 — 기준일 병기 규칙이 이미 있음.
- 조치: 없음.

A-1-05 표면금리 → ❌ (경미)
- 무엇인가: 채권 액면에 적힌 약정 이자율. "연 3% 준다"의 3%.
- 실측: 21,882건 중 1건 빈칸. 뱅크오브아메리카 발행 달러 채권(ISIN XS…, 2055년 만기, 이름에 "0" = 무이표). 국내 채권 DB 에 외국 발행 채권이 단 하나 섞여 있고, 표면금리·만기일·발행일·통화(`'000'`)가 다 비어 있음.
- 판단: yaml "결측 없음"은 사실과 다름.
- 조치: `domestic_bonds.yaml` `columns.srfc_irt.missing_reason: none → mixed`, `missing_semantics.null: "XS 외국발행 1건(BAC) — 표면금리·만기·발행일·통화 미수록"`.
- 부수 발견: `query_rules.외화채없음` "curr_cd = KRW 뿐"은 오기 — `'000'` 1행 존재. "원화 21,881 + 정보 미비 외국채 1(답변엔 사용 불가)"로 정정.

**카테고리 ② 채권 — "채권 몇 개예요?"에 정직하게 세기**

A-1-03/04 종목명·종목코드 → ✅
- 실측: 빈칸 0. 기재 20,497 = 서로 다른 채권 수, 21,882 = DB 행 수. 차이 1,385 = 같은 채권이 두 줄 이상.
- 부수 발견: 같은 ISIN 인데 이름이 "제163회 (사)" vs "제163회(사)"로 다른 2종 — 공백 하나로 검색 실패하는 실증. trap 에 사례 추가. 이 두 컬럼만 answerable_n 이 "개체 수" 기준이라 규약 정리 항목(B-4)으로 승격.

A-2-01 행 단위 → ✅ (설명 정정)
- 실측: 1,078종은 거래소에도 창구에도 있어 두 줄 이상. yaml 에 "종목 세려면 ISIN 으로 묶어라" 규칙 있음.
- 정정: yaml "여러 줄은 속성이 다 같다(평가가 다른 8건 빼고)"는 부정확 — 그 8종은 장외 줄에 종류·신용등급·발행사·위험등급·듀레이션이 전부 NULL(장내 줄엔 있음). 챗봇이 어느 줄을 집느냐에 따라 "AAA" 도 "정보 없음" 도 답할 수 있음 → `row_grain.대표행` 을 "장내행 우선 필수, 8종 장외행 속성 결측"으로 수정.

요약: ✅ 5 · ⚠️ 0 · ❌ 1, yaml 수정 3곳. 다음: ③ 국내ETF — ETN 이라 없는 값들.

## 2. 자주 나오는 반려 사유

| 에이전트가 이렇게 하면 | 이렇게 반려 |
| :-- | :-- |
| 자동 수집 근거 숫자를 그대로 인용만 함 | "직접 SQL 돌려서 재현해" |
| 컬럼 코드로만 설명 | "고객이 뭘 물을 때 쓰는 값인지로 다시 써" |
| ✅ 인데 근거가 "yaml 에 그렇게 써 있음" 뿐 | "yaml 말고 DB 에서 확인한 근거로" |
| 결측 N 건만 말하고 어디 몰렸는지 없음 | "그 N 건이 어떤 상품인지 group by 해봐" |
| 승인 전에 문서를 고침 | "되돌리고 보고부터" |
