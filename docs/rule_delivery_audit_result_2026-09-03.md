### 1-2. "필요했는데 미주입" — 판정 기준과 결과

🔴 **판정 기준** (지시서 §4-1-2 가 요구한 "표 머리에 적는" 기준):

> ① 그 문항의 `gold_sql` 이 외부 테이블(`ext_*`)을 쓴다 = 그 테이블이 **필요했다.**
> ② 그런데 그 이름이 **스키마 프롬프트에도, 실제로 실린 규칙 블록에도 없다.**
> → 모델은 존재를 모르는 테이블을 쓸 수 없다. 이 조합은 **오답이 확정된 미주입**이다.
>
> `ext_*` 로 한정하는 이유: 마스터 컬럼은 `schema_text` 가 항상 싣기 때문에 규칙이 빠져도 모델이 알 수 있다.
> `ext_*` 만이 "규칙(또는 cross 판정)이 유일한 전달 경로"다.

폐기한 기준 2개도 남긴다 — 같은 실수를 반복하지 않기 위해서다.

| 폐기 기준 | 왜 못 쓰나 |
| :-- | :-- |
| `gold_reason` 산문에 규칙 이름 글자매칭 | '레버리지'·'단일종목' 같은 규칙 이름이 설명 문장 속 낱말과 겹쳐 **오탐 10건** |
| 규칙이 언급한 마스터 컬럼이 `gold_sql` 에 있으면 필요 | `sale_yn`·`itm_no` 가 거의 모든 gold 에 있어 662건 중 **550건**이 잡힌다(무의미) |

**결과 — 확정 1건.**

| 문항 | 없는 것 | 라우팅 | cross | 전달 가능했던 규칙 | 트리거 히트 |
| :-- | :-- | :-- | :-: | :-- | :-- |
| `OFFICIAL-002` "국민성장펀드의 구조와 투자전략 동향 등 찾아서 알려줘" | `ext_fund_page` | `[public_funds]` | False | `설명서항목` · `운용사질의` | **없음** |

이 문항이 **공식 예시**라는 점이 중요하다. 세 겹이 동시에 비켜 갔다:

1. `설명서항목` 트리거(`설정일·환매·설명서·모펀드…`)에 "구조·투자전략·동향" 이 없다
2. `운용사질의` 트리거(`운용사·운용하는·자산운용…`)에도 없다 — 이 규칙 본문에도 `ext_fund_page` 가 있어 우연히 전달자가 될 수 있었다
3. 안전망 `pipeline._FUND_EXT_HINTS`(설정일·환매·설명서·모펀드·지급일)도 못 잡아 `cross=False` → 스키마에서도 빠짐

대조: **"삼성자산운용이 운용하는 공모펀드는 몇 개야?"** 는 `운용사질의` 가 발동해 `ext_fund_page` 가 **우연히** 실린다.
설명서와 무관한 질의에는 실리고, 정작 설명서가 필요한 질의에는 안 실린다.

**처방(H1): yaml 한 줄.** `설명서항목.triggers` 에 `구조 · 투자전략 · 동향 · 어떤 펀드 · 특징` 을 더한다.
(같은 낱말을 `_FUND_EXT_HINTS` 에도 넣으면 이중 방어지만 그건 코드다 — 규칙 쪽만으로 닫힌다.)

### 2-2. 모순 쌍 — 지시서가 지목한 3쌍 중 **1쌍만 진짜다**

| 쌍 | 둘 다 always_on | 판정 |
| :-- | :-: | :-- |
| 펀드 `종목단위` ↔ `펀드단위` | ✅ | 🔴 **진짜 모순** |
| 채권 `대표행` ↔ `판매행` | ✅ | 모순 아님 — 주제가 다르다(종목 집계 vs 판매조건 행) |
| ETF `ETF만` ↔ `상품명조회` | ✅ | 모순 아님 — 필터 vs 이름 컬럼 선택 |

진짜 모순의 실물 — `"삼성자산운용이 운용하는 공모펀드는 몇 개야?"` 프롬프트에 **동시에** 실린다:

```
- 종목단위: 행 = itm_no (dedup 불필요 — 2차)
- 펀드단위: GROUP BY or_co_xtn_itt_cd, COALESCE(CASE WHEN length(mtco_itm_no) >= 7 …)
```

개수 질문에서 **행 단위와 펀드 단위를 함께 지시받는다.** 15R 최다 오답(클래스 수를 펀드 수로 답함)과 형태가 같다.
기계 훑기로 "둘 다 always_on 이면서 집계 단위를 지시하는" 쌍을 훑으면 27쌍이 나오는데(채권 21 · 펀드 6),
채권 21쌍은 전부 같은 6개 규칙의 조합이라 실질 후보는 펀드 쪽이다.

**처방(H2) 1차 시도 — 🔴 회귀를 만들어 되돌렸다 (2026-09-03).**

리드 지시대로 트리거로 내리지 않고 **문장을 자기 범위로 한정**해 봤다:

```
종목단위: 개별 조회는 행 = itm_no (클래스 단위 · dedup 불필요).
         개수·집계·랭킹은 `펀드단위` 규칙을 따른다.
```

통과 조건 ①(개별 조회 21문항 회귀 0)은 **통과**했다 — 결과집합 기준 20/21 동일,
나머지 1건(`OFFICIAL-NA-002`)은 채권 라우팅 문항이고 양쪽 다 올바르게 거절했다(펀드 규칙과 무관).

통과 조건 ②(개수 문항 대조)에서 **불합격**했다. `KG-025` 가 악화됐고, **비결정성이 아니라 3/3 재현**이다:

| 조건 | ETF 가지의 운용사 필터 | 답변 |
| :-- | :-- | :-- |
| before (원문) | **3/3 유지** | 공모펀드 207 · 국내 ETF **240** |
| after (처방) | **3/3 소실** | 공모펀드 207 · 국내 ETF **1,160** ← 삼성 것이 아니라 **전체**(DB 실측: 삼성 265) |

펀드 축(207펀드)은 양쪽 다 맞다. 무너진 것은 **ETF 가지**다 —
`종목단위` 문장을 늘리자 UNION 의 다른 가지에서 운용사 조건이 사라졌다.
왜 그런지는 이 실험으로 못 가른다(프롬프트 위치 밀림 · 펀드 축으로의 주의 쏠림 둘 다 가능).
분명한 것은 **"규칙 문장 한 줄을 늘리는 것도 부작용이 있다"** 는 사실이고, 그것 자체가 H3 기각과 같은 방향의 증거다.

→ **되돌렸다.** `종목단위` 는 원문 그대로다. 이 모순은 문장 손질로 닫지 않고
**이관 절차 P0-2**(`docs/guard_to_yaml_migration_2026-09-03.md`)에서 슬롯으로 처리한다 —
슬롯은 프롬프트를 건드리지 않고 SQL 을 직접 고치므로 이 부작용 경로가 없다.
원자료: `eval/h2_grain_check.json`.

## 3. §4-3 형식 실험 (H3) — HCX paired

### 3-1. 설계

| 항목 | 값 |
| :-- | :-- |
| 조건 A | 현행 규칙 텍스트 그대로 |
| 조건 B | (i) SQL 조각 대응표 (ii) 사고 이력 문장 제거 (iii) `종목단위` 를 triggered 로 (iv) 블록 축소 |
| 대상 규칙 | `기본모수` · `펀드단위`(+`종목단위`) · `대표행` · `국가태그` · 위험등급 방향 |
| 코드 가드 | **양쪽 다 끔** (`pipeline._apply_sql_guards` 인메모리 우회 — 서버 배포 대상 아님) |
| 문항 | **41 = 15R ❌30 + 🟡11** (리드 제공 · `eval/qids_15R_fail.txt` · `qids_15R_mid.txt`) |
| 소요 | 1,633초 · 질의당 19.9초 · HCX 164회 |

🔴 **정답률은 이 셋에서 거의 잴 수 없다.** 41문항 중 `gold_sql` 이 있는 것이 **7개뿐**이다
(나머지 30은 probe 유래라 정답 기준이 없다). 그래서 지시서 §4-3-4 가 함께 요구한
**규칙별 준수 여부**(SQL 에 확정식이 나타났는가)를 41문항 전부에서 재고, 그쪽을 주 지표로 읽는다 —
"규칙을 지켰는가" 라는 H3 본래 질문에 더 가까운 자이기도 하다.

### 3-2. 결과 ① 정답률 (분모 7 — 판정 불가)

| 조건 | 정답 | 정답률 | Wilson 95% | 규칙블록 평균 |
| :-- | --: | --: | :-- | --: |
| A (현행) | 0/7 | 0.0% | [0.0%, 35.4%] | 4,330자 |
| B (교정) | 0/7 | 0.0% | [0.0%, 35.4%] | **3,527자** (−803, −18%) |

McNemar b=0 · c=0 · p=1.0000. **양쪽 다 0점이라 이 지표로는 아무것도 못 가른다.**
15R 이 이미 틀린 문항만 모았고 코드 가드까지 껐으니 0/7 자체는 놀랍지 않다.

이번 셋에서는 **B 가 실제로 18% 짧다**(A 4,330 → B 3,527). 1차 대체 셋에서는 크기가 거의 같았는데,
이 41문항이 트리거를 더 많이 발동시켜 A 쪽이 커졌기 때문이다. 즉 **B 는 짧고 형식도 다른데도** 아래 결과가 나왔다.

### 3-3. 결과 ② 규칙 준수 — 이쪽이 결론이다

대상 문항 = 그 규칙이 적용돼야 하는 문항(예: `펀드단위` 는 펀드 개수 질의).

| 규칙 | A 지킴/대상 | B 지킴/대상 | 판정 |
| :-- | --: | --: | :-- |
| `기본모수` | 17/27 (63%) | 19/27 (70%) | B 가 2건 많다 — 통계적 의미 없음 |
| **`펀드단위`** | **0/18 (0%)** | **0/18 (0%)** | 🔴 **양쪽 다 한 번도 안 지켰다** |
| `대표행` | 1/9 (11%) | 2/9 (22%) | 둘 다 사실상 안 지킨다 |
| `국가태그` | 1/7 (14%) | 1/7 (14%) | 동일 |
| 등급방향 | 대상 0 | 대상 0 | 이 셋에 '안전' 질의가 없다 |

🔴 **`펀드단위` 0/18 이 이 감사 전체에서 가장 센 숫자다.**
15R 최다 오답(클래스 수를 펀드 수로 답함)이 바로 이 규칙의 불이행인데,
**규칙을 어떻게 쓰든 18번 중 0번 지켰다.** 검사기 오류가 아님을 원문으로 확인했다 —
18문항 전부 `COUNT(*)`(클래스 행)이고 `mtco_itm_no` 가 **단 한 번도 SQL 에 나오지 않는다**:

```
[KG-025] SELECT '국내 ETF', COUNT(*) … UNION ALL SELECT '공모펀드', COUNT(*) FROM public_funds …
[X9]     SELECT '공모펀드', COUNT(*) FROM public_funds WHERE or_co_xtn_itt_cd = '00080008' …
[KG-031] SELECT COUNT(*) FROM public_funds WHERE or_co_xtn_itt_cd = '00080029' …
```

`or_co_xtn_itt_cd` 는 쓰는데(운용사 필터로) **집계 키로는 안 쓴다.** 규칙에 GROUP BY 식이 통째로 실려 있는데도 그렇다.

### 3-4. 판정 — H3 기각 (1차와 같은 방향, 더 강한 근거)

**형식 교정으로 준수율이 오른다는 증거가 없다.** 오히려 지정 셋에서 더 분명해졌다 —
B 는 18% 짧고 SQL 조각 형식인데도 `펀드단위`·`국가태그` 준수율이 **한 건도 안 올랐다**.

**그럼에도 검정력은 여전히 낮다. 정직하게 남긴다:**

- 정답률 지표는 분모 7 · 양쪽 0점이라 **판정에 쓸 수 없다**
- 준수율은 n=41 이지만 규칙별 대상은 7~27건이고, 규칙별 차이(+2/27 · +1/9)는 **우연과 구분되지 않는다**
- 가드를 껐으므로 절대 수치는 운영 수치가 아니다 — 15R 실측(73%)과 비교하면 안 된다
- 15R 이 이미 틀린 문항만 모은 셋이라 **난이도가 극단적으로 치우쳐 있다**

**§4-4 판독 규칙 적용**: "차이 없으면 → enforce 슬롯 후보로 확정(코드 가드는 그때까지 유지)".
그리고 `펀드단위` 0/18 은 후보를 넘어 **1순위**임을 말한다 — 프롬프트로는 이 규칙이 전달되지 않는다.
(이관 절차 P0-2 가 정확히 이 규칙이다.)

## 6. 🔴 실행자가 밟은 함정 2건 — 다음 사람을 위해

측정·전환 작업에서 **결과를 조용히 틀리게 만드는** 자리 둘이다. 둘 다 실측으로 잡았다.

### 6-1. `load_context()` 는 `@lru_cache(maxsize=1)` 다 — 두 번 불러도 같은 객체다

A/B 두 조건을 비교하려고 `load_context()` 를 두 번 부르고 한쪽에만 규칙을 덮었더니,
**A 까지 같이 바뀌었다.** 증상이 고약하다 — 에러가 아니라 "A 와 B 의 규칙 블록 크기가 정확히 같다"
는 그럴듯한 숫자가 나온다. 그대로 뒀으면 "형식을 바꿔도 차이 없다" 를 **비교하지도 않고** 발표할 뻔했다.

```python
ctx_a = load_context()
ctx_b = load_context()        # 🔴 같은 객체다
ctx_b.enums[...] = ...        # ctx_a 도 바뀐다
```

→ 조건별 컨텍스트는 **반드시** `copy.deepcopy(load_context())`.
(`eval/rule_delivery_paired.py:fresh_ctx` · `eval/check_h2_grain.py` 가 그렇게 한다.)

### 6-2. yaml 에서 `off:` 는 키가 아니라 **불리언**이다 (YAML 1.1)

enforce 슬롯을 꺼 두려고 `off: true` 라고 썼는데 슬롯이 안 꺼졌다.
YAML 1.1 은 `off`·`on`·`yes`·`no` 를 **불리언으로 파싱**한다 — 딕셔너리에 `False` 키가 생기고
`enf.get("off")` 는 영원히 `None` 이다. 조건문이 조용히 통과한다.

```yaml
enforce:
  off: true        # 🔴 파싱 결과: {False: True}  →  .get("off") is None
  enabled: false   # ✅ 이렇게 쓴다
```

→ 슬롯 비활성 키는 `enabled: false`. `tests/test_enforce_slots.py::test_off_slot_never_fires` 가 지킨다.
같은 함정이 `y`·`n`·`true`/`false` 대문자 변형에도 있으니, **불리언처럼 보이는 낱말은 키로 쓰지 않는다.**

## 7. 제안서에 들어갈 한 단락 (2.3.2 · 5.3 용)

> 규칙을 프롬프트에 싣는 것과 모델이 규칙을 지키는 것은 다른 문제다. 우리는 이 간극을 세 겹으로 나눠 측정했다.
> ① **미주입** — 트리거 어휘가 질문과 어긋나 규칙이 애초에 실리지 않는 경우가 있었다. 공식 예시 #2 가 그랬는데,
> 답에 필요한 외부 테이블 이름이 프롬프트 어디에도 없어 모델이 그 테이블의 존재를 모른 채 SQL 을 썼다.
> ② **모순 동시 주입** — 집계 단위를 행 기준과 펀드 기준으로 동시에 지시하는 규칙 두 개가 함께 실렸다.
> ③ **불이행** — ①②를 걷어내고 규칙을 SQL 조각 형식으로 다시 쓰고 사고 이력을 지운 판본(18% 더 짧다)을
> 만들어 같은 문항으로 대조했으나 준수율은 개선되지 않았다. 특히 집계 단위 규칙은 **어느 판본에서도
> 18번 중 0번** 지켜졌다 — 규칙이 프롬프트에 실려 있고 확정식까지 적혀 있는데도 그렇다.
> 이 결과가 설계를 갈랐다 — 형식 교정으로 살릴 수 있는 규칙은 yaml 로 닫고, 그렇지 않은 규칙은
> 프롬프트가 아니라 **실행 계층에서 강제**하기로 했다(`enforce` 슬롯). 규칙은 여전히 온톨로지 한 곳에 있고,
> 달라지는 것은 그것을 **누가 집행하는가**다.
