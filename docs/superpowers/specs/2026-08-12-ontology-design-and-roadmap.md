## 1. 설계 원칙

### 1.1 온톨로지가 하는 일은 하나 — 없는 외래키를 만드는 것

**4개 테이블 사이에 조인 키가 하나도 없습니다.**

| 테이블 | 식별자 컬럼 | 한글명 | 형태 | 접두 대역 |
| :--- | :--- | :--- | :--- | :--- |
| `public_funds` | `itm_no` | 종목번호 | ISIN 12자리 | `KR51` `KR50` `KR55` `KR52` |
| `domestic_bonds` | `PD_NO` | 종목코드 🔸 | ISIN 12자리 | `KR6` `KR3` `KR2` `KR1` |
| `domestic_etfs` | `pd_itm_no` | 상품번호 | ISIN 12자리 | `KR74` `KRG5` `KR70` `KR72` |
| `overseas_etfs` | `pd_itm_no` | 상품번호 🔸 | 티커 | `AAA` `AAAA.K` |

대역이 겹치지 않아 **직접 조인이 불가능**합니다. 같은 상품인 상장지수펀드 23종조차 `itm_no ∩ pd_itm_no` = **0건**이고 종목명 문자열로만 이어집니다.

> 따라서 *"미래에셋이 운용하는 상품 전부"* 는 **SQL로 표현할 수 없습니다.**
> **온톨로지 = 그 조인을 가능하게 하는 층.** 상품의 속성을 기술하는 문서가 아닙니다.

### 1.2 그래서 KG 개체로 세울 것의 판별 기준

> **"이 값으로 다른 테이블을 찾아가야 하는가?"**
> - **예** → KG 개체 (표기가 달라서 정규화가 필요하므로)
> - **아니오** → SQLite 컬럼 그대로. **범주형이어도**

🔴 **"범주형이면 KG"가 아닙니다.** 범주형 컬럼 대부분은 한 테이블 전용이라 SQL이 바로 처리합니다.

#### 이 기준으로 전 컬럼을 거르면 — 정확히 §3의 6종만 남습니다

| KG로 감 | 왜 |
| :--- | :--- |
| Organization | `삼성` / `0008xxxx` / `(주)신한은행` / 영문 — 4테이블 표기가 전부 다름 |
| Index | ETF `cu_base_index` ↔ 펀드 `bmrk_nm`. 해외는 체계가 다르고 펀드는 복합식 |
| Region | 한글 11종 ↔ 영문 59종 ↔ ISO3 17종 |
| AssetClass | `주식` ↔ `Equity` |
| RiskGrade | INTEGER `1` ↔ 문자열 `PD_RISK_GCD_11` ↔ REAL `1.0` |
| Currency | `KRW` ↔ `CURR_CD_KRW` |

**KG에 안 가는 범주형 — 훨씬 많습니다** (한 테이블 전용이라 다른 테이블을 찾아갈 일이 없음)

```
채권      BD_KND(39) · STD_PD_MCLS_NM(6) · STD_PD_SCLS_NM(16) · CRD_GRD(20) · PD_EXG_MKT
국내ETF   cu_strtegy(4) · cu_lev_fector · pd_pen_tr_yn · wu_core_yn · pd_sect_cd
해외ETF   cu_index_repl_mthd · cu_inverse_short_yn · pd_exg_mkt_cd
펀드      or_attr_desc(11) · prfd_attr_cd(210) · exchdg_yn · prvo_pbff_desc · sale_yn
```

> 💡 **위험등급은 KG에 갑니다** (4테이블 걸침 + 표기 3종). 반면 **펀드 `or_attr_desc`(11종)는 범주형인데 안 갑니다** — 펀드에만 있으니까요.

#### ⚠️ `.ttl`에 있다고 KG 인스턴스가 필요한 건 아닙니다

`pd_grp_no`(ETF/ETN)가 그 예입니다.

```
.ttl  ✅  ETF owl:disjointWith ETN     ← 제약은 필요
KG    ❌  인스턴스 불필요               ← 국내·해외 표기가 'ETF'/'ETN' 로 동일
SQL   ✅  WHERE pd_grp_no='ETF'        ← 바로 필터
```

`.ttl ⊃ KG` 관계가 아니라 **역할이 다릅니다.** `.ttl`은 모든 클래스·제약을, KG는 그중 **표기 정규화가 필요한 값만** 인스턴스로 갖습니다.

#### ⚠️ KG는 원본 값을 대체하지 않습니다

```
SQLite  domestic_etfs.wu_inv_ast_type = '주식'      ← 원본 그대로
SQLite  overseas_etfs.wu_inv_ast_type = 'Equity'    ← 원본 그대로
KG      kg_assetclass: Equity(정규명) ─┬→ domestic_etfs · '주식'
                                       └→ overseas_etfs · 'Equity'
```

**정규명 ↔ 원본값 매핑만** 갖습니다. §1.5 additive only와 같은 원리입니다.

207개 컬럼 중 200개는 SQLite에 그대로 두고, KG는 **노드 종류 6종짜리 작은 그래프**로 유지합니다.

### 1.3 `.ttl` / KG / `yaml` — 셋의 역할 분담

| | 표준 용어 | 답하는 질문 | 형식 | 예 |
| :--- | :--- | :--- | :--- | :--- |
| **`ontology.ttl`** | **T-Box (스키마)** | *"어떤 것이 존재할 수 있나"* | RDF/Turtle | `ETF ⊥ ETN` · `riskGrade ∈ [0,6]` · `OverseasETF has no riskGrade` |
| **KG** | **A-Box (인스턴스)** | *"무엇이 실제로 있나"* | **SQLite 매핑 테이블** | `삼성자산운용 manages KODEX200`<br>`KODEX200 tracks KOSPI200` |
| **`<domain>.yaml`** | (표준 용어 없음) | *"이 컬럼 값을 어떻게 다룰까"* | YAML | `cu_charge_rt: 0 → missing` · `answerable_n: 67` · `query_rules` |
| 에이전트 코드 | — | `qtype` 8종 → 3분기 | Python | `answer` / `unanswerable` / `clarify` |

#### 🔑 무엇이 어디로 가나 — 판별 기준 한 줄

> **"데이터가 완벽했어도 참인가?"**
> - **참** → 금융 도메인의 사실 → **`.ttl`**(구조) 또는 **KG**(관계)
> - **거짓** → 이 데이터셋에서만 참 → **`yaml`**

| 사실 | 데이터 완벽해도 참? | 위치 |
| :--- | :-: | :--- |
| "ETF와 ETN은 다른 상품이다" | ✅ | `.ttl` |
| "위험등급은 낮을수록 위험하다" | ✅ | `.ttl` |
| "삼성자산운용이 KODEX 200을 운용한다" | ✅ | KG |
| "KODEX 200과 KOSPI200 추종 펀드는 같은 지수를 본다" | ✅ | KG |
| "`cu_charge_rt`의 `0`은 미입력이다" | ❌ | `yaml` |
| "`du_er_1y = -100`은 센티넬이다" | ❌ | `yaml` |
| "국내ETF 총보수 유효 모수는 67건이다" | ❌ | `yaml` |

> ⚠️ **`yaml`은 "예외 처리"만이 아닙니다.** `query_rules`의 `pd_grp_no='ETF'` · `GROUP BY itm_no` · `TRIM()` 은 예외가 아니라 **모든 질의에 항상 붙는 기본 필터**입니다. 예외 처리가 아니라 정상 동작의 일부입니다.

#### SQL 한 문장을 만드는 데 셋이 각각 기여합니다

```
.ttl   →  어떤 컬럼을 쓸 수 있나      (없으면 즉시 unanswerable)
KG     →  어떤 값으로 필터하나        (조인 키·정규화된 값)
yaml   →  어떤 필터를 반드시 붙이나   (ETF 한정·센티넬 제외·GROUP BY)
```

> 🔴 **질문 유형(`qtype`)은 `.ttl`에 넣지 않습니다.** 도메인 모델이 아니라 앱 로직입니다.
> `yaml`이 시맨틱 레이어 논문의 그 문서와 같은 역할입니다 (정확도 **45.5 → 68.7%**).

#### LLM은 셋 중 무엇을 보나

| | LLM이 보나 | 어떻게 |
| :--- | :--- | :--- |
| `.ttl` | ✅ **간접** | 라우팅된 상품군 부분만 직렬화해 **프롬프트 주입** → SQL 생성 근거 |
| KG | ❌ **안 봄** | 코드가 조회해 조인 키를 얻고, 그 결과가 **SQL `WHERE`에 값으로** 들어감 |
| `yaml` | ✅ **절반** | `query_rules` → 코드가 SQL에 주입 (LLM 안 봄)<br>`answer_policy` → 프롬프트 주입 (LLM 봄) |

**셋 중 어느 것도 LLM이 "검색"하지 않습니다.** 전부 코드가 읽어 프롬프트를 조립하거나 SQL을 만듭니다. **LLM은 DB 커넥션을 갖지 않습니다** — SQL 문자열을 만들 뿐이고 실행은 코드가 합니다 (`SELECT`만 허용 · 컬럼 화이트리스트 · `LIMIT` 강제).

#### 📊 차원 / 사실 — 스타 스키마와 같은 구분

```
KG  =  차원 (무엇으로 찾아가나)          SQLite  =  사실 (답이 되는 값)
       운용사 · 지수 · 지역                        수익률 · AUM · 보수
       자산군 · 위험등급 · 통화                     종가 · 만기 · 듀레이션
         └─────────── 조인 키 ───────────┘         + KG에 안 간 범주형 전부
```

**KG에는 수치가 없습니다.** `WHERE` 절을 만들고, `SELECT`·`ORDER BY`는 SQL이 담당합니다.

#### 한 질의에서 셋이 도는 모습

> *"미래에셋이 운용하는 미국 주식형 ETF 중 1년 수익률 상위 3개"*

```
① .ttl  DomesticETF 에 realizedReturn 속성 있음        → 진행 (없으면 즉시 기각)
② KG    '미래에셋자산운용' → cu_fund_mgmt_co = '미래에셋'
        '미국'             → wu_inv_rgn      = '미국'      (해외였다면 'United States of America')
        '주식형'           → wu_inv_ast_type = '주식'      (해외였다면 'Equity')
             ↓ 여기까지 수치는 하나도 없음
③ yaml  query_rules.ETF만      → AND pd_grp_no='ETF'
        query_rules.수익률정상 → AND du_er_1y > -100      (센티넬 34건 제외)
④ SQL   SELECT … ORDER BY du_er_1y DESC LIMIT 3
             ↓ 여기서 처음 수치가 나옴
⑤ HCX   결과 3행 + 근거로 문장 생성
```

**①②③이 빠지면** — ①없으면 없는 속성을 지어내고, ②없으면 `'미래에셋자산운용'` 조회가 0건이고, ③없으면 ETN이 섞이고 센티넬이 최하위를 채웁니다.

#### 📌 KG는 트리플스토어가 아니라 **SQLite 테이블**로

```sql
CREATE TABLE kg_organization (canonical_name, table_name, column_name, raw_value);
-- '미래에셋자산운용' | domestic_etfs | cu_fund_mgmt_co  | '미래에셋'
-- '미래에셋자산운용' | public_funds  | or_co_xtn_itt_cd | '00080012'
```

교차 상품군 질의가 **SQL `JOIN` 한 방**이 됩니다. `.ttl`은 제출물 겸 스키마 단일 원천으로 남고, 별도 그래프 엔진 의존성이 안 생기며, Dockerfile 재현성도 지켜집니다.

### 1.4 채택안 — A안 (얇은 공통 상위 클래스)

`FinancialProduct`를 두되 **공통 속성 5개 이내**로 제한합니다. 4개 테이블은 공통 속성이 거의 없어서, 크게 잡으면 절반이 빈 값이 됩니다.

**공통 속성 후보 검증 — 4개 테이블 커버리지:**

| 후보 속성 | 채권 | 국내ETF | 해외ETF | 펀드 | 채택 |
| :--- | :-: | :-: | :-: | :-: | :-: |
| 식별자 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 종목명 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 운용사/발행사 | ✅ | ✅ | ✅ | ✅(코드만) | ✅ |
| 통화 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 위험등급 | ✅ | ✅ | 🔴 없음 | ✅(결측19.3%) | ✅ optional |
| 순자산(AUM) | 🔴 없음 | ✅ | ✅ | ✅ | ❌ 하위로 |
| 판매여부 | 🔴 없음 | ✅ | ✅ | ✅ | ❌ 하위로 |
| 총보수 | 🔴 없음 | ⚠️ 유효67건 | ✅ | 🔴 컬럼없음 | ❌ 하위로 |

→ **공통 속성 5개 확정.** 나머지는 전부 하위 클래스 고유 속성.

### 1.5 전처리 방침 — **additive only**

> **원본 컬럼은 읽기 전용. 파생은 옆에 컬럼으로 더한다.**

#### 성능은 전처리의 이유가 아닙니다 (실측)

```
인덱스 정확일치            0.02 ms
채권 42,394 TRIM 스캔     14.70 ms   ← 735배 느리지만
펀드 95,619 TRIM 스캔     36.78 ms
펀드 TRIM+GROUP BY 복합   236.62 ms   ← 15초 예산의 1.6%
```

HCX 한 번이 수 초이므로 SQLite는 병목이 아닙니다. **전처리의 이유는 속도가 아니라 ⓐ 복구 불가능성 ⓑ 일관성입니다.**

> 🔸 `sqlite_db_architecture.md` §4의 *"0.001초 만에 즉시 조회"* 는 **인덱스 정확일치일 때만** 참입니다. 실제 질의는 전부 `TRIM`을 거쳐 풀스캔이라 15~240ms입니다. → 해당 문서 정정 대상.

#### 3분류

| | 항목 | 왜 |
| :--- | :--- | :--- |
| 🔴 **반드시 빌드 시점**<br>(런타임 복구 불가) | **선행 0 손실** `dtype=str` | `00040010` → `40010.0`. **값이 이미 파괴됨** |
| | Holdings 외부 적재 + `as_of ≤ 2026-07-11` 필터 | 원본에 없는 데이터 (§7.2-2b) |
| | 컬럼 시프트 오염(`20054.0`) 원인 규명 | 적재 문제인지 원본 문제인지 |
| 🟢 **새 데이터 · 인덱스**<br>(파생이 **아님**) | **운용사·지수·지역 매핑 테이블** | 🔴 **DB 어느 컬럼에서도 유도 불가.** `삼성 = 삼성자산운용 = 0008xxxx`. **KG 조인 키** (§3·§7.4②) |
| | Holdings | 외부 데이터 (§7.2-2b) |
| | 엔티티 링킹 인덱스 (FTS5) | 값이 아니라 **인덱스**. 정확일치 실패 시 리콜용. 트랙1에서 판단 |
| ❌ **파생변수 금지**<br>(규칙으로 선언) | 정규화 컬럼 `*_norm` · 특수구조 플래그 8종 · 만기 4상태 · `axis_*` 유도 컬럼 | 아래 사유 3가지 |
| ❌ **절대 금지** | 결측 채우기 (평균·중앙값 대치) | **환각.** EDA_GUIDE 명시 |
| | 센티넬 삭제 (`-100`·`해당없음`·더미 식별자) | 🔴 **지우면 "왜 없는지"를 못 답함** (§6) |
| | 이상치 제거 (수익률 2,738%) | 실제 값으로 검증 완료 |
| | 만기 도래분 삭제 (16,180건) | 이력 가치 — **발행사 28.6%가 여기에만 존재** |
| | ETN 591건 · 사모 102행 삭제 | *"ETN도 알려줘"* 질의 대비. **구분만, 삭제 금지** |

#### 🔴 파생변수를 만들지 않는 이유 3가지

기존 컬럼에서 계산되는 것은 **DB 컬럼이 아니라 yaml 규칙으로 선언**합니다.
`domestic_etfs.yaml`의 `axis_derivation:` 블록이 이미 그 형태입니다 (`accuracy` + `rule` + `pending_workshop`).

1. **판정이 바뀌면 DB를 재빌드해야 합니다.** yaml은 선언을 고치면 그 자리에서 반영되는데 파생 컬럼은 `build_db.py` 재실행이 필요합니다. 그런데 `axis_derivation.pending_workshop`이 보여주듯 **판정은 워크샵에서 바뀔 예정**입니다.
2. **진실의 원천이 둘이 됩니다.** yaml 규칙과 DB 컬럼이 어긋나면 어느 쪽이 맞는지 판별 불가. `.ttl`↔yaml 이중 관리를 피하는 것과 같은 원리.
3. **성능이 이유가 못 됩니다** — 최악 236ms = 15초 예산의 1.6%.

#### additive only가 단순 위생 규칙이 아닌 이유

**① 값을 고치면 §6 답변 매트릭스의 근거가 사라집니다.** `cu_charge_rt=0`을 NULL로 바꾸면 *"0으로 기록되어 있으나 미입력입니다"* 라고 답할 수 없고 그냥 "없음"이 됩니다. **"왜 없는지"를 답하는 게 차별점인데, 그 원료가 바로 그 이상한 값들입니다.**

**② 판정은 워크샵에서 바뀝니다.** 원본이 살아 있어야 파생만 재생성하면 됩니다. EDA_GUIDE의 *"yaml 선언을 바꾸면 결측 집계가 그 자리에서 바뀐다 — yaml이 문서가 아니라 동작"* 구조가 유지되려면 원본이 그대로여야 합니다.

> 📌 **팀 내 용어 정렬 필요:** 일반 EDA의 "전처리(채우기·제거)"와 반대입니다.
> 이 프로젝트의 전처리 = **"값을 고치는 것"이 아니라 "라벨과 파생을 더하는 것"**.

## 3. 공유 개체 6종 — 컬럼 배정표 ★ 온톨로지의 본체

### 3.0 🔴 먼저 — **등장이 같다고 층위가 같은 게 아닙니다**

같은 개념이 여러 테이블에 등장한다는 것과, 그 **값을 나란히 놓고 비교할 수 있다**는 것은 다릅니다. 불일치는 5유형이고, **③⑤가 위험합니다** — ①②는 매핑이 틀리면 "못 찾음"으로 드러나지만 ③⑤는 **그럴듯하게 매핑되어 조용히 틀린 답**이 나갑니다.

| 유형 | 뜻 | 해결 | 실제 사례 |
| :-: | :--- | :--- | :--- |
| ① 표기 불일치 | 같은 것, 다르게 적힘 | `owl:sameAs` 매핑 | `삼성` = `삼성자산운용` = `0008xxxx` |
| ② 입도 불일치 | 한쪽이 더 세분 | `rdfs:subClassOf` 계층 | 지역 11종 vs 59종 |
| ③ 🔴 **척도 불일치** | **범위·방향·단위가 다름** | **변환 함수 + 검증** | **AUM 통화** · RiskGrade 범위 |
| ④ 집합 불일치 | 한쪽에만 있는 값 | 부분 매핑 + **"대응 없음" 선언** | `Alternatives` 1,760건 |
| ⑤ 🔴 **축 자체가 다름** | 이름은 비슷한데 **개념이 다름** | **매핑 금지** | 채권 `BUY_YIELD` vs ETF `du_er_1y` |

#### ④-1 자산군 — 대응되는 5쌍 + **대응 없는 큰 덩어리**

```
✅ 대응    주식↔Equity  채권↔Bond  혼합자산↔Mixed Assets
           단기자금↔Money Market  원자재↔Commodity
🔴 대응 없음
   해외 Alternatives  1,760건 (해외ETF의 31.5%)  ← 국내에 개념 자체가 없음
   국내 부동산 16 · 통화 12  (합 28건)           ← 해외에서는 Alternatives에 묻힘
```

> *"대체투자 ETF"* 는 **해외에만** 있고, *"부동산 ETF"* 는 국내 16건인데 해외에서는 별도로 못 셉니다.
> → 부분 매핑 + **`Alternatives`는 국내 대응 없음을 명시적으로 선언**. 교차 집계 시 모수 표시 필수.

**⑤ 유형 주의 — 펀드 `or_attr_desc`는 자산군이 아닙니다:**
`주식형 · 재간접 · 채권혼합 · 채권형 · 파생형 · MMF · 특별자산…` 중 **재간접 30,243행은 "무엇에 투자하나"가 아니라 "어떻게 운용하나"** 입니다. ETF 자산군과 이름이 비슷하다고 매핑하면 *"채권형 상품 전부"* 에서 재간접이 어디로 갈지 정의되지 않습니다. → **매핑 금지, 별도 축으로.**

## 5. 제약 — 가드레일로 실제 동작하는 것

`.ttl`이 장식이 되지 않으려면 아래가 **런타임에 질의를 기각**해야 합니다.

| 제약 | TTL 표현 | 기각하는 질의 |
| :--- | :--- | :--- |
| ETF ≠ ETN | `ETF owl:disjointWith ETN` | *"채권형 ETF Top3"* → `pd_grp_no='ETF'` 자동 주입 |
| 위험등급 범위 | `riskGrade` range **0~6** | *"7등급 펀드"* → 즉시 기각 |
| 신용등급 화이트리스트 | `CRD_GRD` 20종 enum | *"AAAA 등급 채권"* → 즉시 기각 |
| **속성 부재** | `OverseasETF`에 `riskGrade` 미정의 | *"위험등급 낮은 해외ETF"* → `unanswerable` |
| **속성 부재** | `FundClass`에 `hasFee` 미정의 | *"보수 낮은 펀드"* → `unanswerable` |
| **답변 모수** | `answerable_n` (yaml) | *"보수 낮은 ETF"* → 답하되 **모수 67건 명시** |
| 계층 역추적 금지 | 채권 3단은 트리 아님 | 소분류→대분류 유도 규칙 생성 차단 |

> 🔑 **HCX 호출 0회로 기각됩니다.** 레이턴시 예산도 같이 지켜집니다.
> `think_trace`에 *"온톨로지상 `OverseasETF` 클래스에 `riskGrade` 속성이 정의되어 있지 않음"* 을 쓸 수 있고, 이게 근거 제시 배점에 직결됩니다.

### 5.1 분류축 값은 `skos:Concept`으로

축 값(`Equity`·`Passive`·`Lev2X`·`FundAttribute` 210종…)을 `owl:Class`로 만들면 클래스가 300개로 폭발합니다. **상품군만 Class**(disjoint 제약이 걸려야 하므로), **축 값은 SKOS individual**.

### 7.0 시간 예산 — 불편한 사실

완료된 것은 전부 **2단계(EDA)**입니다. 3단계(에이전트)·4단계(배포)가 **통째로 남았습니다.**

```
기술제안서 40점  ← EDA 문서 5,400줄이 재료. 아직 한 줄도 안 씀
API 답변  40점  ← 🔴 엔드포인트가 없으면 0점
```

국내ETF가 1순위인 이유: **단일 소스 · 한국어 · 규모 최소**이고, *"삼성전자를 담은 ETF"* 류가 한국어 평가 문항에 나올 개연성이 가장 높습니다.

**🔑 감점 방어는 "수집 안 하기"가 아니라 "기준일을 데이터와 답변에 못 박기"입니다:**

1. 모든 외부 레코드에 **`as_of` 컬럼 필수** — 수집 시각이 아니라 **데이터 기준일**
2. 적재 시 **`as_of <= '2026-07-11'` 하드 필터** — 코드로 강제, 사람 판단에 맡기지 않음
3. **커버리지 명시** — Holdings 확보 N종 / 1,202. 없는 종목은 여전히 "확인 불가" (§6 정책 유지)
4. **`retrieved_context`에 출처·기준일 노출** — *"KRX PDF 2026-07-11 기준"*. 감점 방어 근거가 답변 자체에 들어감

> 📌 **워크샵 안건은 "할까 말까"가 아니라 "어디까지"로 바뀝니다** — 해외ETF 포함 여부와 종목당 상위 몇 종목까지 담을지.
