## 0. 먼저 합의할 것 — 분담의 원칙

### 0-1. "도메인별로 나눠 쓴다" ≠ "온톨로지가 셋이다"

실제 구조는 **공통 개체 하나 + 도메인 파일 넷**이다.

| 파일 | 내용 | 줄 |
| :-- | :-- | --: |
| `common.ttl` | 클래스 14 · 관계 16 · 공유 개체 11종 인스턴스(Security·Fund·Index·Organization·Region·Country·CreditGrade·RiskGrade·AssetClass·Currency·FundAttribute) | 58,967 |
| `bond_kr.ttl` / `etf_kr.ttl` / `etf_gl.ttl` / `fund_pub.ttl` | 테이블 클래스 1개 + **ABSENT 선언** + 위험등급 **범위 제약** | 21~36 |

즉 도메인 담당이 쓸 절의 주어는 *"내 도메인의 온톨로지"* 가 아니라 **"공통 개체를 내 데이터가 어떻게 쓰고, 무엇을 부재로 선언했는가"** 다.
심사자가 세 절을 읽고 "온톨로지가 세 개"라고 느끼면 §01 의 통합 서사가 무너진다. 아래 §0-3 공통 템플릿으로 막는다.

## 01. 전체 아키텍처 및 특화기능 — 리드

**한 문장 프레임** (`ontology_3layers_frame` §0 그대로):
> 우리 온톨로지는 그래프를 탐색하는 장치가 아니라, LLM 이 SQL 을 틀리지 않게 만드는 3층 장치다 — ① 값을 미리 접지하는 사전(KG), ② 규칙을 프롬프트에 싣는 문서, ③ 생성 전후를 막는 게이트.

**온톨로지가 "어디에" 있는가** 표 — 심사자가 ttl 파일만 온톨로지로 오해하지 않게:

| 형태 | 실체 | 런타임 소비처 |
| :-- | :-- | :-- |
| 선언 형태 | `ontology/*.ttl` 5분할 (규격 p.9) | 제출·검증용. 런타임은 읽지 않음 |
| 값 사전 형태 (1층) | SQLite `kg_node·kg_alias·kg_edge·kg_closure` | Route 어휘 · Ground 개체 해소 · WHERE 값 검사 |
| 규칙 문서 형태 (2층) | `ontology/enums/*.yaml` `query_rules·clarify·_refusal` | HCX 프롬프트 근거 문서 (always_on / triggered) |
| 게이트 형태 (3층) | `absent_in · range_by_table · gate_constants · 등급 표준표` | 생성 전 기각(HCX 0회) · 생성 후 SQL 검증 |

**차별화 포인트 3개** (각 1단락):
1. **손으로 쓴 ttl·KG 가 없다.** yaml(사람) + 코드북(출처·기준일 필수) → `build_ontology.py` 가 ttl 5개와 KG 4테이블을 **같은 선언에서** 생성. 검증 V1~V7 실패 시 산출물 생성 거부(죽은 alias·값 충돌·기준일 위반 등).
2. **테이블 축과 상품종류 축을 분리했다.** 마스터 파일 = 데이터 출처, ETF/ETN = 실제 분류. `owl:disjointWith` 가 장식이 아니라 필터.
3. **프롬프트에 준 값과 검사하는 값이 같은 사전이다.** 1층 값 사전과 3층 값 검사기가 kg_alias 하나를 공유하므로 어긋날 수 없다. 이것이 §05 "yaml 1개 = 도메인 1개 추가" 확장성의 근거.

주최 필수 구성요소 4종(Parsing/Ontology · Extraction/EntityResolution · NL2SQL/Retrieval · 근거기반/환각방지) 대응표를 여기서 한 번 보여준다 (`PROJECT.md` §5 표 재활용). ER 이 우리 데이터셋에서 특히 무거웠다는 점(펀드 더미 키 49%, 운용사 표기, 센티넬 문자열)을 02-② 예고로 적는다.

### 02-② 어떤 온톨로지 엔지니어링을 적용했는가 — **3인 분담의 본체**

**리드 도입 (1쪽):**
- 설계 원칙: *값을 고치지 않고 의미를 선언한다* (`ontology_engineering_etf` §1). 주최 "0·결측은 의도된 값" 공지가 출발점.
- 2층 구조: `enums/*.yaml`(컬럼층, 담당자별) ↔ `shared/*.yaml`(개체층, 횡단). 둘을 잇는 것은 `kg_entity` 한 줄.
- 공유 개체 11종과 관계(`manages↔hasManager` · `issues↔hasIssuer` · `holds↔isHeldBy` inverseOf 3쌍, `skos:broader` 계층 3종: Region·CreditGrade·Index).
- `holds` 를 kg_edge 에 넣지 않은 결정: 100만 행이라 `ext_*` 테이블 자체를 edge 로 간주.
- 빌드 검증 V1~V7 표.
- 규칙 12종 목록(지칭정리·결측방어·외부병합·grain·기본모수·파생유도·배타분리·단위스케일·금지규칙·부재선언·계층·기준일) — 도메인 절이 이 번호를 인용한다.

### 02-③ 어떤 검색 방법론을 왜 택했는가 — 리드

관계형 마스터 데이터에서는 **질의 생성이 그래프 탐색보다 낫다**는 판단(KGQA-1)을 출발점으로, 파이프라인을 단계별로 "온톨로지가 어디서 개입하는가"로 서술:

```
Route  : 사람이 쓴 단어 목록 없음 — kg_alias raw(가중 3) + 범주값 distinct(2) + 약어명 + synonyms 로 자동 어휘. 한국어 수식구조 마지막 명사가 머리
Ground : 질의 ↔ 노드 라벨. 대상 테이블에 alias 없는 노드는 버림 · closure 후손 + 자회사 1단 전개 · 구상호/후계법인
Gate   : ABSENT · enum(등급 표준표 4분기) · range_by_table · 상수 컬럼 → HCX 0회 기각
Plan   : HCX 프롬프트 = KG 개체 매핑(개체 ID 는 넘기지 않음, DB 실제 값만 ≤60/컬럼) + 조인키 4쌍 + 규칙 2층(always_on/triggered) + 되묻기·답변불가 규칙 + 스키마
검증   : validate_sql(SELECT·허용 테이블·LIMIT) + WHERE 리터럴 ↔ 값 사전(커버리지 ≥98% 컬럼만) + 실패 시 재생성 1회 + 0행 시 조건별 진단을 거절 근거로
조립   : 목록형 답변은 기계 조립(HCX 0회), 규칙 문구·모수 병기
```

왜 그렇게: 규칙 문서 유무가 정확도를 좌우(SL-1, B등급) · 선별 주입 > 전부 주입(DK-1, A) · verbatim 값 제약(KGG-1, B) · 생성 전 게이트(REF-1, A). 인용 등급 규율은 `ontology_3layers_frame` §3 표 그대로. **0행 자동 재시도·LIKE 완화는 하지 않는다** — 거절이 정답인 문항에서 환각 경로가 되기 때문.

도메인 담당이 주는 1단락씩: 해외 ISIN 조인 폐기(63종 오배정 8건 실증) · 펀드 `grp` 단독 금지 · 채권은 단일 테이블이라 교차 조인 없음.

## 04. 주요 기능 흐름도 — 공식 예시 질의로 도메인당 1개

주최가 공개한 예시 질의를 그대로 써서 심사자가 대조하기 쉽게 한다. 각 담당이 **실제 서버 응답의 `think_trace` 를 옮겨** 단계별로 어느 온톨로지 요소가 먹혔는지 표기.

| 담당 | 질의 | 보여줄 요소 |
| :-- | :-- | :-- |
| 채권 | "판매 가능한 원화채권 중 AA- 이상" | CreditGrade closure 서열 · 판매가능 정의(만기 앵커) · 등급 결측 41% 모수 병기 |
| ETF | "캠브리콘이 편입된 중국 반도체 ETF" 또는 "에코프로 자회사 편입 ETF 중 순자산 큰 상품의 위험요인" | Security alias 합집합(캠브리콘 표기 6종) · `subsidiaryOf` 1단 전개(DART 근거 3사) · Region 계층 · holdings JOIN |
| 펀드 | "국민성장펀드의 구조와 투자전략" | `(or_co,mtco)` 합성키 · `feedsInto` 모펀드 · `ext_fund_page` 보강 · 없는 정보(운용역 등)는 ABSENT 로 답변에 명시 |
| 리드 | 답변불가 3종: "AAAA" · "Kimi" · "KODEX AI로봇" | 게이트 4분기 · Entity Resolution 실패 처리 · 정확일치/enum 소속 판정(부분일치 금지) — HCX 0회 |

흐름도 형식은 하나로 통일: `질의 → [Route] → [Ground] → [Gate] → [Plan/SQL] → [검증] → [조립]` 세로 상자에 오른쪽 주석으로 온톨로지 요소.

## 05. 기대효과 · 확장성 — 리드 논거 + 도메인 현업 지점 (배점표에 "5번 강조")

**확장성 논거 (리드):** 도메인 추가 = `enums/*.yaml` 1개 + `kg_entity` 포인터. 실증 2건 — ① 7/11 1차 → 8/24 2차 데이터 전환을 yaml 갱신으로 흡수, ② 9/2 온톨로지 확장(라벨 슬롯·국가/속성 노드·ABSENT 전수·등급 범위 선언)이 **4도메인 부작용 0** 으로 들어간 KG 구조 검증 35문항 실측. 값 사전과 검사기가 같은 원천이라 가능했다는 인과로 §01 차별화 3번과 닫는다.

**현업 적용 지점 (도메인당 1개, 각 1단락):**
- 채권: 등급 표준표가 코드북이라 신평사·등급 체계 교체가 파일 교체로 끝남. 결측 등급 41% 를 "없다"고 답하는 것 자체가 컴플라이언스 가치.
- ETF: 구상호·후계법인 슬롯(`formerName`·`successor`)으로 합병 운용사 질의 대응. 원천 지역 오분류를 규칙으로 보정하되 원본은 불변 → 데이터 품질 이슈를 **답변 근거로 노출**.
- 펀드: 클래스 도배·더미 키를 판정 규칙으로 격리해 "펀드 단위 집계"가 가능 — 현업 보고서 집계와 동일 기준.

**정직한 한계 절:** 해외 구성종목 커버리지 22.7% · 보고기준일 시차 · 지역 오분류 잔존 · 레버리지 경계 미확정 · Fund 두 뜻 · 비정형 문서 파싱(국민성장펀드류)의 범위. 한계 절이 오히려 신뢰를 준다(`README` 규칙 3).
