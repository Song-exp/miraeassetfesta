## 02. 제안 방법

### 2.1 특화 데이터 수집·정제 (3쪽) [ETF 통합]
- 2.1.1 무엇을 어디서 — 마스터 4테이블 / 외부 4테이블 / 코드북 13종(출처·기준일 ≤ 8/24). 수집 방법·적재 Flow 한 도해
- 2.1.2 정제·결측 원칙 — 값을 고치지 않는다: 센티넬·더미 키·0값·사모·ETN 을 "판정"하고, 외부 보강은 ext_* 에 태그로 병기
- 2.1.3 신뢰성 관리와 한계 — 커버리지 리포트, report_date 병기, 오분류 발견 사례, 해외 22.7%

### 2.2 온톨로지 엔지니어링 (12쪽) — 이 제안서의 본체
- 2.2.1 설계 원칙과 구조 [리드] (2쪽) — "값을 고치지 않고 의미를 선언한다". enums(컬럼층)·shared(개체층) 2층, 공유 개체 11종·관계·계층, holds 를 edge 로 두지 않은 결정. **그림 A 통합 온톨로지**
- 2.2.2 채권 [채권] (2.5쪽) — **그림 B-1** + 결함→선언 5건 압축(등급 서열 closure · 0등급 범위 · KR 상수 부재 · 할인율/영구채 규칙 · "가장 위험한" 되묻기) + 한계
- 2.2.3 ETF 국내·해외 [ETF] (3쪽) — **그림 B-2** + 6건(ETN disjoint · 해외 위험등급 부재 · 총보수 0 · 레버리지 부호 · Index 정본화 · Region 통합·Security 노드) + 한계
- 2.2.4 공모펀드 [리드] (3쪽) — **그림 B-3** + 6건(사모 혼입 모수 · 복합키 · 더미 키 · 순자산 MAX · 속성 토큰 alias · ABSENT 5) + 한계
- 2.2.5 합쳐지는 지점 [리드] (1.5쪽) — **표 C 도메인×개체 매트릭스**. Index 하나에 3도메인, Organization 구상호·후계, Region 삼중 표기 통합. 온톨로지가 하나라는 증거

### 2.3 검색 방법론 (3쪽) [리드]
- 2.3.1 왜 SQL 생성인가 — 관계형 마스터에서 그래프 탐색 대신 질의 생성을 택한 근거, 벡터 DB 비채택. 반 쪽
- 2.3.2 온톨로지가 개입하는 4지점 — 파이프라인 한 그림 위에 ① Route/Ground(값 접지) ② Gate(생성 전 기각, HCX 0회) ③ Plan(규칙 2층 주입) ④ 검증(값 검사기·0행 진단). 지점마다 반 쪽
- 2.3.3 교차질의와 하지 않은 것 — 조인키 4쌍(ISIN 폐기·grp 단독 금지), 0행 재시도·LIKE 완화를 안 한 이유, HCX 필수 2구간 준수

## 03. 시스템 구성도 (2쪽) [리드]
- 3.1 오프라인 빌드 도해 — 마스터·ext·코드북 → yaml → 검증 → ttl 5 + KG 4테이블
- 3.2 런타임 도해 + 배포 — 파이프라인 상자마다 읽는 온톨로지 층을 색으로. SQLite 단일 저장소·NCP·HTTPS 는 각주 수준

## 04. 주요 기능 흐름도 (3쪽) [채권 취합]
- 4.1 채권 — "판매 가능한 원화채권 중 AA- 이상": 등급 closure 서열이 SQL 에 들어가는 과정
- 4.2 ETF — "에코프로 자회사 편입 ETF 중 순자산 큰 상품": subsidiaryOf 전개 + holdings JOIN, 3-hop 이 값 접지로 풀리는 과정
- 4.3 펀드 — "국민성장펀드 구조·투자전략": 복합키·모펀드·ext_fund_page, 없는 정보는 ABSENT 로 답변에 명시
- 4.4 답변불가 — AAAA·Kimi·KODEX AI로봇 세 질의가 각각 enum·개체·정확일치 게이트에서 HCX 0회로 끝나는 과정

## 05. 기대효과·확장성 (2쪽) [채권]
- 5.1 효과 — 답변불가 방어·환각 0 경로 비중·평가셋 결과, KG 구조 검증 35문항 추이
- 5.2 확장성과 현업 적용 — yaml 1개 = 도메인 1개(실증 2건) + 도메인별 현업 지점 1개씩(등급 체계 교체 · 구상호/오분류 보정 · 펀드 단위 집계)
- 5.3 한계 — 해외 커버리지, 지역 오분류 잔존, 레버리지 경계, 비정형 파싱 범위
