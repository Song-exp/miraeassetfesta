# 설계 철학 — 그래프는 상품이 아니라 "상품을 고르는 조건의 값"을 담는다 (리드 확정 2026-09-03)

> 제안서 0·01·2.2.1·2.3 이 공유하는 서사. 도메인 절(04~06)은 이 파일을 참조만 하고 다시 정의하지 않는다.
> 논의 기록: 9/3 리드 세션. 이 문장들은 제안서에 그대로 옮겨도 된다.

## 1. 한 문장

**KG는 상품이 아니라 상품을 고르는 조건의 값을 담는다. 질문의 어휘를 값으로 접지하는 일은 그래프가, 그 값으로 행을 고르는 일은 SQL이 한다.**

편입 기준은 하나다 — **"질문의 어휘가 컬럼의 값으로 이어지는가."**
위험등급·자산군처럼 값이 7~9개인 닫힌 축도, 운용사·지수·종목처럼 수천 개인 열린 개체도 이 기준을 통과하면 노드가 된다. 수익률·순자산은 질문에 어휘로 나오지 않고 조건식으로만 나오니 그래프에 없다. 상품 행 자체도 없다.

## 2. 왜 이 분담인가

LLM이 테이블을 조회할 때 틀리는 곳은 "어느 행인가"가 아니라 "무슨 값인가"다.

| 간극 | 모델이 혼자서는 못 하는 것 | 우리 데이터에서 실제로 난 사고 |
| :-- | :-- | :-- |
| 어디를 볼지 | 질문 어휘 → 테이블·컬럼 | "채권형 ETF"를 채권 테이블로, 섹터 질의를 `pd_sect_cd`로 |
| 무슨 값으로 | 질문 어휘 → DB에 실재하는 리터럴 | `AA`(DB는 `AA0`), "삼성"이 삼성전기까지, 운용사 컬럼에 펀드명 99종 오염 |
| 데이터의 관행 | 0의 뜻, 행 단위, 단위, 기준일, 서열 | 총보수 0이 "가장 저렴", 클래스 행을 펀드 수로, "AA- 이상"을 `= 'AA-'` |
| 없는 걸 없다고 | 컬럼·개체·enum 값의 존재 | AAAA 등급, 해외ETF 위험등급, 설정유형코드 '10'을 "10좌" |

조건이 정해진 뒤 행을 고르는 것은 SQL이 원래 잘하는 일이다. 그러니 그래프는 조건 값의 사전이면 충분하고, 레코드는 관계형 그대로 둔다. 이것이 "값 사전 KG를 SQLite 매핑 테이블로 둔 Hybrid"의 뜻이다.

**운영 원칙: 모델은 복사만 하게 하라.** 추측·기억 대신, 질문 시점에 실재 값과 규칙을 놓아 주고 옮기게 하고, 옮긴 결과를 같은 사전으로 검사한다.

## 3. 사전이 되는 구조

- `kg_node` 정본 개체 하나 · `kg_alias` **(노드, 테이블, 컬럼, 실제 값, 매칭식)** · `kg_edge` 관계 4종만 · `kg_closure` 계층을 미리 펼친 조상-후손.
- alias는 예시가 아니라 **컬럼 distinct 전체를 규칙으로 돌린 전수**(66,592건 중 65,941건 `source=rule`). `crd_grd` 15/15, `cu_fund_mgmt_co` 99/100. 그래서 "사전에 없다 = DB에 없다"가 성립하고, 값 검사기가 같은 사전을 쓴다.
- 노드 하나를 잡으면 테이블별 alias가 같이 내려온다. 교차 질의(삼성전자 → 국내 티커·해외 cusip·펀드 ISIN)가 접지 한 번으로 세 조인키를 얻는 이유.
- 계층(Region·CreditGrade·Index)은 빌드 때 closure로 펼친다. "AA- 이상"은 값 4개 목록으로, "아시아"는 국가 목록으로 도착한다.
- 100만 행 구성종목 관계는 간선으로 옮기지 않는다. `ext_*` 테이블 자체가 간선이고 조인키만 프롬프트에 준다.

## 4. 빌드와 질의 — 두 줄

> **빌드 시점**: EDA → 공백과 예외를 컬럼층(enums yaml)에, 개체와 계층과 "어느 컬럼 값이 이 개체인가"를 개체층(shared yaml)에 선언 → 한 빌드(검증 7종)에서 ttl 5개와 값 사전 KG 4테이블 생성.
> **질의 시점**: 어휘를 값으로 접지 → 예외면 기각(HCX 0회) → 값과 규칙을 놓아 주고 SQL 생성 → 같은 사전으로 검사 → 실행과 조립.

접지가 예외 판정보다 앞이다. "위험등급 낮은 해외ETF"는 해외ETF로 라우팅된 뒤에야 부재가 서고, "AAAA"는 등급 토큰 접지를 시도한 뒤에야 표준표 밖으로 판정된다.

## 5. 이 관점에서의 강점 (제안서 1.2·5.1 소재)

1. 접지 결과가 곧 SQL 값이다 — 검색 결과를 다시 WHERE 값으로 바꾸는 단계가 없다.
2. 교차 질의가 접지 한 번으로 세 테이블에 닿는다.
3. 계층·서열이 값 목록으로 도착한다 — 런타임 탐색 0, 12초 예산 안.
4. 부재가 구조 안에 있어 없는 것을 찾으러 가지 않는다 — 답변불가가 검색 실패가 아니라 구조 판정.
5. 프롬프트에 준 사전과 검사하는 사전이 같다 — 도메인 추가가 yaml 하나.
6. 무거운 관계는 간선으로 옮기지 않았다 — 4만 노드로 가볍고, 홀딩스는 인덱스 있는 JOIN.

**정직한 약점**: alias가 없는 값은 접지하지 못한다(해외 구성종목 22.7%, Security TOP50 컷). 역할별 Organization 노드가 분리돼 있다(미래에셋 ETF 운용사 ≠ 채권 발행사 노드).

## 6. 이 철학이 아직 못 덮는 것 → `09_오답유형_구조해법.md`

15R 실측(231문항)에서 ❌ 30건의 절반이 "값은 맞는데 **축**이 틀림"(펀드↔클래스, 개수↔금액)이다. 사전이 필터 값은 접지하지만 **무엇을 세는지·무엇으로 정렬하는지·어디까지 포함하는지**는 접지하지 않기 때문이다. 다음 확장은 편입 기준을 한 줄 넓히는 것이다 — "질문의 어휘가 **지표·단위·범위**로 이어지는가."
