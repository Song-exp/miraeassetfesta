## 0. 한 줄 진단과 한 줄 처방

15R 보고서의 진단: **"질문이 축을 명시하지 않았을 때 결정층이 축을 확정하지 못한다."** ❌ 30건 중 16건이 값은 맞는데 축(펀드↔클래스, 개수↔금액, 기준가↔기준일자)이 틀렸고, 10건은 데이터가 있는데 문을 닫았다.

구조로 보면 원인은 하나다. **지금 사전은 필터 값(WHERE 리터럴)만 접지한다. 무엇을 세는지(measure), 어느 단위로(grain), 어디까지(scope)는 SQL 모양에 매달려 있다.** 펀드단위 가드가 `SELECT COUNT(*)` 모양일 때만 발동하고, 정렬 축은 HCX가 붙인 별칭을 답변기가 읽고, 지수명 확정식은 JOIN이 보이면 물러난다. 축이 값으로 접지돼 있지 않으니 SQL 모양이 조금만 달라져도 축이 흔들린다.

처방은 편입 기준을 한 줄 넓히는 것이다.

> **"질문의 어휘가 컬럼의 값으로 이어지는가"** → **"질문의 어휘가 값·지표·단위·범위로 이어지는가."**

지표(Measure)·단위(Grain)·범위(Scope)를 필터 값과 같은 방식으로 노드·alias·확정식으로 두고, 결정층이 SQL을 보기 전에 축을 확정한다. SL-1이 말하는 **runtime form**(YAML 데이터 모델 + 결정론적 컴파일러, 없는 measure 참조 시 에러)의 축소판이고, 우리는 이미 필터 값에 대해 그걸 갖고 있다.

## 1. 유형별 해법

### 1-1. 교차질의 "A와 B는 각각" — ❌ 16/30, 정답률 33%

**증상** `KG-025` 삼성자산운용 펀드 850(클래스 수)·ETF 240 / `X9` 미래에셋 2,066·230. 단일 상품군(`S8` KB 129개(클래스 625개))은 맞는데 "각각"이 붙으면 클래스 수가 펀드 수로 나간다.

**구조적 원인** 펀드단위 집계 교체 가드가 SQL 모양(`SELECT 목록 전체가 COUNT(*)`)에 묶여 있고, 교차 가지는 `SELECT '공모펀드' AS 구분, COUNT(*)`라 라벨 리터럴에 막힌다. **가드가 축이 아니라 SQL 형태를 본다.**

**해법 — 교차질의는 SQL 하나로 만들지 않는다. 가지별로 단일 도메인 질의를 돌리고 결정층이 합친다.**
1. 라우팅이 테이블 2개 이상 + "각각·비교·와" 문형이면 **분해**: "삼성자산운용 공모펀드 몇 개" / "삼성자산운용 국내 ETF 몇 개".
2. 각 가지를 기존 단일 도메인 경로로 실행 — 여기서는 펀드단위 가드가 정상 발동한다(S8이 증거).
3. 결정층이 가지 결과를 **템플릿으로 조립** — "공모펀드 207개(클래스 850개) · 국내 ETF 240개". 단위(KRW/USD)·기간(1y/1d) 불일치는 조립기가 병기.
4. UNION SQL은 "한 목록에 섞어 정렬"이 필요한 랭킹 교차(삼성전자 보유 ETF+펀드 TOP-N)에만 남기고, 그때도 각 가지의 measure는 아래 1-2의 축 사전에서 확정한다.

이미 P2 이월 큐에 **F5 교차 분기 기계 조립(N3+S7+R4)** 으로 잡혀 있는 항목이다. 15R 수치가 우선순위를 P0로 올린다.

**선행연구**
- 분해 자체: DIN-SQL(Pourreza & Rafiei 2023), MAC-SQL(Wang et al. 2023) — 복잡 질의를 하위 질문으로 나눠 푼다 `[미등급]`. 단 두 논문은 하위 결과를 **SQL로 재조립**하고, 우리는 **답변으로 재조립**한다 — SQL 재조립이 어렵다는 관찰("대부분의 복합 질의는 재조립 가능한 하위 질의로 분리되지 않는다", Semantic Decomposition of Question and SQL, arXiv 2310.13575 `[미등급]`)이 오히려 우리 쪽 근거다.
- 우리 등급 자료: `KGQA-1` "Federated Query Plan을 단일 저장소에 사상" 프레임(PROJECT §5) — 가지별 실행이 그 정의에 맞다. `SL-1` §5.4 ② "스냅샷을 시점 합산해 1000배" = 클래스 합산과 같은 grain 사고 (B).
- grain 원리: Kimball 차원 모델링의 "grain을 먼저 선언하라"(실무 표준) · Snowflake Cortex Analyst의 fan/chasm trap 검증 · SQLSure(fan-out 이중집계 검사기, BIRD/Spider에서 실제 버그 발견) `[미등급, 산업]`.

**검증** KG-025·X9·KG-031·CROSS-002 + 교차 형제 20문항 paired. 회귀선: S8·R1 유지, UNANS 9/9 유지.

### 1-2. 랭킹의 정렬 축 — 값은 맞는데 순서가 틀림

**증상** `KG-008` 수탁사 상위 3 — 개수를 물었는데 금액 순, 숫자는 클래스 수. SQL은 gold 순서인데 HCX 별칭 `COUNT(*) as 펀드수`를 답변기가 읽음. `FND-R03` 기준가 순 — 기준가가 아니라 **기준일자**로 정렬, "기준가는 비교 지표가 아니다" 규칙 미반영.

**구조적 원인** 정렬 축(measure)이 접지되지 않는다. 질문의 "가장 많이 수탁"·"규모"·"기준가 높은"이 어느 컬럼·어느 집계·어느 방향인지를 HCX가 정하고, 답변기는 HCX가 붙인 별칭을 믿는다. 필터 값에서 금지한 "모델의 추측"이 축에서는 허용돼 있다.

**해법 — Measure 노드.** shared yaml에 `measure.yaml`(개체층)을 두고 각 지표를 노드로 선언한다.

```yaml
# ontology/shared/measure.yaml (안)
entity: Measure
nodes:
  M_fund_count:
    label_ko: 펀드 수
    grain: fund            # (or_co, mtco) 단위
    sql: COUNT(DISTINCT or_co_xtn_itt_cd || zeropad(mtco_itm_no,7))
    aliases: [몇 개, 개수, 가장 많이 운용, 가장 많이 수탁]
    tables: [public_funds]
  M_class_count:
    label_ko: 클래스 수
    grain: class
    sql: COUNT(*)
    aliases: [클래스 몇 개]
    companion_of: M_fund_count   # 답변에 항상 병기
  M_nav:
    label_ko: 순자산
    column: fd_nast_suma
    grain: fund
    agg: MAX                     # 클래스 중복 기재 — SUM 금지
    aliases: [순자산, 규모, 큰 펀드, AUM]
    direction: desc
  M_nav_price:
    label_ko: 기준가
    column: bns_bpr
    comparable: false            # 펀드 간 비교 지표 아님 → 정렬 축으로 쓰면 게이트
    aliases: [기준가]
```

- **접지**: Ground가 필터 값과 같은 방식으로 질문 어휘 → Measure 노드를 잡는다. "가장 많이 수탁" → `M_fund_count` + 그룹 축 수탁사.
- **주입**: 프롬프트의 "실제 값" 블록 옆에 "정렬 축: 펀드 수 = COUNT(DISTINCT …) DESC" 를 확정식으로 준다(DK-1의 `'표현' refers to SQL조각` 형식).
- **검증**: 생성 SQL의 ORDER BY 표현식이 접지된 measure의 확정식과 다르면 재생성 1회, 그래도 다르면 결정층이 ORDER BY를 교체(값 검사기와 같은 자리).
- **조립**: 답변기가 HCX 별칭이 아니라 **접지된 measure의 label·grain**을 읽는다. `companion_of`가 있으면 병기.
- **게이트**: `comparable: false` measure가 정렬 축으로 접지되면 생성 전에 "기준가는 펀드 간 비교 지표가 아닙니다. 수익률·순자산 중 어느 기준으로 볼까요?" — 상수 컬럼 게이트와 같은 층.

**선행연구**
- `SL-1` §3.1 ② "지표와 공식", §5.4/§6.4 "잔여 실패는 메커니즘이 아니라 **named measure**를 문서에 더 적어 고칠 것", §3 runtime form 정의 — **B**(문서 전체 효과). 우리 것은 context form이 아니라 runtime form 쪽이다.
- `DK-1` 구조화 형식 우위(Table VI) — **A**.
- 산업: dbt MetricFlow(measure = grain + aggregation + dimensions), Cube semantic layer — "모델은 metric과 dimension을 고르기만 하면 잘못된 조인·집계를 만들 수 없다"(dbt 2026 벤치마크 블로그) `[미등급, 산업]`. Aggregation Consistency Errors in Semantic Layers(arXiv 2307.00417) — 집계 일관성 오류 분류 `[미등급]`.

**검증** KG-008·FND-R03 + 랭킹 36문항 전수 paired(정렬 축·단위 두 열로 채점).

### 1-3. 기준 없는 추천은 되묻고, 찾은 것은 답한다 — 되묻기의 양방향 오류

**증상** `FND-C01` "규모가 큰 펀드 추천" → 되물어야 하는데 순자산 TOP5(법인 MMF 일색)로 답함. `AA2` "KB중국본토A주 펀드 A클래스 기준가" → 되묻기 후보 첫 줄이 정답인데 "없다"고 답함.

**구조적 원인** 둘 다 "모호함"이 **유형화돼 있지 않다.** (a) "규모"는 measure가 둘(순자산/설정액)이고 모수가 둘(개인/법인)인데 어느 쪽이 기본값이고 어느 쪽이 되물을 것인지가 선언돼 있지 않다. (b) 상품명 매칭이 표기 변형(`[주식]` vs `(주식)`, 공백, 클래스 접미)을 정규화하지 않아 정확일치 실패 → 되묻기로 빠진다.

**해법**
- (a) **모호성 유형을 measure·모수 선언에 붙인다.** `M_nav.aliases: 규모` 에 `ambiguity: {axis: [순자산, 설정액], segment: [개인, 법인], policy: ask}` / `수익률` 은 `{axis: 기간 8종, policy: default 1y + 명시}` (리드 결정 08-31). 결정층은 접지된 measure의 policy로 되묻기·기본값을 결정하고, HCX가 정하지 않는다. AMBROSIA의 3분류(scope / attachment / vagueness)를 유형 축으로 쓰면 "각각"=scope, "규모"=vagueness, "A클래스 기준가"=attachment로 정리된다.
- (b) **상품명도 alias 원칙으로.** 정본 상품명 키를 빌드 때 정규화(괄호 종류·공백·클래스 접미 제거)해 두고, 질문 고유명도 같은 정규화로 **정확일치**한다. 유사도 매칭이 아니라 정규화 후 정확일치이므로 환각 경로가 아니다. 정규화 일치가 1건이면 답하고, 0건일 때만 유사 후보 되묻기.

**선행연구**
- `REF-1` §1·§3.1 답변가능성 정의(스키마 부재·제약 모호·개체 부재·범위 밖)와 부록 A 거절 9유형 — **A**(기준선). REF-1 Table 1: 언어적 모호성(AMBROSIA)은 어떤 방법도 70~80%에 머문다 → 카드 §5 결론 "모호 문항은 거절보다 기본 모수로 답하고 가정을 명시" — 이것이 (a)의 `policy: default` 근거.
- AMBROSIA(Saparina & Lapata, NeurIPS 2024) 3분류, AmbiQT(EMNLP 2023) 두 SQL 정답, AmbiSQL(arXiv 2508.15276) 객관식 되묻기 생성, PRACTIQ(arXiv 2410.11076) 모호·불가 대화형 셋 `[미등급]`.
- (b): 값 정규화 매칭은 CHESS(LSH+편집거리, `[미등급]`)·`VAL-1`의 값 후보 해소(B)와 방향이 같되, 우리는 **정규화 후 정확일치만** 쓴다(`KGG-1` verbatim 제약, B).

**검증** FND-C01·AA2 + 추천 문형 10·개별 조회 21(회귀 90% 유지) paired. `run_paired.py`의 CLARIFY 오발동 지표를 양방향(오발동·미발동)으로.

### 1-4. 답을 못 냄 — 접지가 SQL 모양에 양보한다

**증상** `CROSS-002` S&P500 국내·해외 총보수 비교 → "확인되지 않음". 국내 순수추종 24건 실재. 지수명 확정식이 JOIN이 있으면 즉시 반환하고, HCX가 쓴 `LIKE '%S&P500%'`(공백 없음)이 DB `'S&P 500 CR'`에 0행.

**구조적 원인** 둘. ① 접지 단계가 SQL 모양(JOIN 유무)을 보고 물러난다 — 철학상 접지는 SQL 이전에 끝나야 한다. ② Index alias 매칭 키가 공백·대소문자를 정규화하지 않는다(라벨에는 `_flex_match`가 있는데 Index alias 생성에는 없음).

**해법** ① 확정식 적용을 SQL 모양과 무관하게 — 접지된 Index 노드가 있으면 그 테이블의 alias 값 목록을 IN으로 주입하고, 검증기가 `ref_base_index` 리터럴을 사전과 대조한다(1-1로 가면 교차 가지가 단일 도메인이 되어 자동 해결). ② 빌드 시 alias에 정규화 키(공백·대소문자·기호 제거) 열을 추가하고 매칭은 정규화 키로, 주입은 원본 raw로. 1-3(b)와 같은 메커니즘.

**선행연구** `KGG-1` verbatim(B) · `VAL-1` 0행 진단(B) — 진단이 "ref_base_index 조건이 0행, 정규화 변형은 24행"을 잡으면 거절 대신 재접지. 값 정규화는 CHESS/BRIDGE 계열 `[미등급]`.

**검증** CROSS-002 + 지수 표기 변형 문항(S&P500/S&P 500/SP500, KOSPI200/코스피 200) 10건.

### 1-5. 원시 덤프 — 조립기가 SQL 모양에 양보한다

**증상** `Z18` "ETF로 자산배분하는 펀드" → 30행 원시 덤프(`대표_itm_no`, 종목명 `ㅊ`), SQL은 주식형 전수.

**구조적 원인** 둘. ① "ETF로 자산배분"이라는 개념이 어느 축에도 접지되지 않았는데 HCX가 주식형으로 대체했다 — 필터 값 접지 실패가 거절 대신 추측으로 흘렀다. ② 조립기가 예상 SQL 모양이 아니면 통째로 건너뛰어 컬럼명·내부 ID가 노출된다.

**해법** ① **접지 0인 개념 게이트**: 질문의 조건 어휘 중 어떤 노드·attribute token·규칙 트리거에도 걸리지 않은 것이 있으면, HCX가 대체 컬럼을 고르게 두지 않고 "이 조건은 데이터에서 판별할 축이 없습니다"로 부재 응답(ABSENT와 같은 층). 실제로 재간접·ETF 편입 여부가 `prfd_attr_cds`나 `ext_fund_holdings`로 판별 가능하면 그 alias를 추가하는 것이 정답이고, 그건 사전 확장이다. ② **표시 스키마를 온톨로지에**: 컬럼마다 `display: {label, role: id|label|measure|hidden}` 를 선언(해외ETF yaml의 `column_korean_names` 확장). 조립기는 SQL 모양이 아니라 결과 컬럼의 role로 렌더링하므로 어떤 SQL이 와도 ID는 숨고 라벨은 한글이 된다.

**선행연구** `SL-1` runtime form "없는 measure 참조 시 에러"(B) · `REF-1` §3.1 스키마 요소 부재(A) · `ENT-1` WRONG_FILTER 54.6%(C) — 접지 실패를 추측으로 메우는 것이 최대 오답원.

**검증** Z18 + 목록·서술 76문항 중 원시 덤프 판정 건 전수.

### 1-6. 포함/제외 범위 — "역외펀드까지 포함하면"

**증상** `KG-031` 피델리티 역외 포함 → 제외하고 제외했다고 고지. 형제 `X12`(슈로더)는 합산 정답. 같은 문형에 답이 두 가지.

**구조적 원인** 범위(scope)가 개체 계층에 없다. 피델리티 온쇼어 운용사와 역외 법인이 별개 Organization 노드이고 둘을 묶는 상위 노드가 없어서 "포함하면"이 closure로 풀리지 않고 HCX 재량이 된다.

**해법** Region·CreditGrade와 같은 메커니즘 — **Organization 그룹 노드** + `skos:broader`. `Org_group_fidelity ⊃ {Org_fidelity_kr, Org_fidelity_offshore}`. 기본은 온쇼어(모수 명시), "포함·전체·계열" 어휘가 있으면 closure 후손 전부. 미래에셋 ETF 운용사/채권 발행사 분리 노드도 같은 그룹 노드로 묶으면 08 §5의 약점이 닫힌다.

**선행연구** 우리 closure(KGQA-1 계층은 "질문 어휘가 상위 개념일 때 값을 펴 주는 용도"로만, 종합 §1-1) · AMBROSIA scope ambiguity `[미등급]`.

**검증** KG-031·X12 + 그룹 운용사 5곳 × 포함/미포함 문형.

| 축 | 지금 | 확장 | 어느 층 | 닫히는 오답 |
| :-- | :-- | :-- | :-- | :-- |
| 필터 값 | kg_alias 전수 | (유지) + 정규화 키 열 | 1층 | 1-4 지수 표기, 1-3(b) 상품명 |
| **지표 Measure** | HCX 재량 | `measure.yaml` 노드: column·agg·grain·direction·comparable·aliases·ambiguity policy | 1층(접지) + 3층(ORDER BY 검증·comparable 게이트) + 조립(label·grain) | 1-2 정렬 축, 1-3(a) 추천 기준, 1-1 펀드 수 |

| **범위 Scope** | 없음 | Organization 그룹 노드 + closure, "포함" 어휘 트리거 | 1층 | 1-6 역외 포함 |

| 표시 | 조립기 SQL 모양 의존 | 컬럼 role 선언 | 조립 | 1-5 원시 덤프 |
| 접지 0 개념 | HCX 대체 | 부재 게이트 | 3층 | 1-5 주식형 대체 |

전부 **같은 원리의 반복**이다 — 모델이 정하던 것을 선언으로 옮기고, 질의 시점엔 접지·주입·검사만 한다. 제안서 2.3.3 "다음"에는 이 표 한 장과 "편입 기준 한 줄 확장"으로 쓰면 된다.

## 3. 정직하게 적을 것

- Measure 노드는 SL-1이 정의만 하고 실험하지 않은 runtime form이다. 우리 수치가 나오기 전엔 "SL-1의 정식화를 measure에 적용"으로만 쓴다.
- 분해→조립은 DIN-SQL/MAC-SQL과 반대 방향(SQL 재조립이 아니라 답변 재조립). 논문 수치를 옮기지 않는다.
- AMBROSIA 계열은 카드가 없다. 제안서에 쓰려면 카드 먼저(REF-1 카드가 AMBROSIA를 데이터셋으로 언급하므로 그 경유 인용은 가능).
- 모호성은 어떤 방법도 80%대(REF-1 Table 1) — "되묻기로 다 잡는다"고 쓰지 않는다. 기본값+명시가 감점 위험이 낮다는 정책을 함께 쓴다.
