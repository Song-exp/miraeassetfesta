## 0. 요약

본 시스템은 국내채권·국내ETF·해외ETF·공모펀드 마스터 데이터 4종(53,375행 ▶)과 외부 수집 구성종목·설명서 데이터 위에서, 자연어 질의를 HyperCLOVA X(HCX-005)가 SQL로 옮기고 그 결과로 답하는 금융상품 에이전트다. 설계의 출발점은 단순하다. **LLM이 테이블을 조회할 때 틀리는 곳은 "어느 행"이 아니라 "무슨 값, 무슨 축"이다.** 행을 고르는 일은 SQL이 원래 잘한다. 그래서 온톨로지와 지식그래프를 탐색 장치가 아니라 **조건의 값을 미리 접지해 두는 사전**으로 설계했고, 모델이 하는 일을 "놓아 준 값과 규칙을 SQL로 복사하는 것"으로 줄였다.

온톨로지는 네 형태로 존재한다. 제출 규격의 ttl 5분할(선언), SQLite 4테이블로 적재된 값 사전 KG(접지), 프롬프트에 실리는 규칙 문서(관행), 생성 전후를 막는 게이트와 검증기(부재·강제). 넷은 같은 yaml 선언에서 한 빌드로 생성되며 손으로 쓴 ttl이나 KG는 없다. 이 구조에서 답변불가 질의는 검색 실패가 아니라 구조 판정으로 처리되어, 15R 실측 231문항에서 환각 방지 문항 9/9, 개별 조회 90%를 기록했다 ▶. 남은 약점은 교차·랭킹 질의에서 "무엇을 세는가"의 축이 흔들리는 것이며, 이를 값 사전과 같은 방식으로 지표·단위·범위까지 선언하는 축 사전으로 확장하는 작업이 진행 중이다.

## 01. 전체 아키텍처 및 특화기능

### 1.1 문제를 어디에 두었나

주최가 제공한 데이터는 관계형 마스터 4개와, 마스터에 없는 정보(구성종목·설명서)를 외부에서 채워 넣은 테이블이다. 질의는 단일 턴이고, 35문항 중 5문항은 답변을 생성하면 감점되는 답변불가 문항이다. 이 조건에서 우리는 "무엇을 검색할 것인가"가 아니라 "LLM이 이 데이터에서 무엇을 틀리는가"를 먼저 물었다. 선행연구의 관찰과 우리 실측이 같은 다섯 곳을 가리켰다.

| 간극 | 모델이 혼자서는 못 하는 것 | 우리 데이터에서 난 사고 |
| :-- | :-- | :-- |
| 어디를 볼지 | 어휘 → 테이블·컬럼 | "채권형 ETF"를 채권 테이블로 |
| 무슨 값으로 | 어휘 → DB에 실재하는 리터럴 | `AA`(DB 표기는 `AA0`), 운용사 컬럼에 펀드명이 99종 섞인 오염 |
| 데이터의 관행 | 0의 뜻, 행 단위, 단위, 기준일, 서열 | 총보수 0이 "가장 저렴", 클래스 행을 펀드 수로 |
| 없는 것 | 컬럼·개체·enum 값의 부재 | AAAA 등급, 해외ETF 위험등급 |
| 축 | 무엇을 세고 어느 단위로 어디까지 | 펀드↔클래스, 개수↔금액, 역외 포함 여부 |

기업 데이터 Text-to-SQL 실패의 절반 이상이 WHERE 값·enum 오류라는 관찰(ENT-1)과, 스키마만 주면 정답률이 10%대에 머물다 업무 규칙·용어집 문서를 더하면 78%로 뛴다는 주최 인용 논문(JAMIA-1)의 결과는 같은 말이다. 좌우하는 것은 스키마가 아니라 "데이터가 실제로 어떻게 생겼는지"의 명시적 문서화다. 우리 온톨로지는 그 문서화를 값·규칙·검사 세 형태로 나눠 구현한 것이다.

### 1.2 구조 한 장

```
[빌드]  EDA → enums yaml(컬럼층: 결측 판정·규칙·부재) + shared yaml(개체층: 개체·계층·어느 컬럼 값이 이 개체인가)
        → build_ontology.py (검증 V1~V7) → ttl 5분할 + KG 4테이블(node·alias·edge·closure) + 범주값 어휘
[질의]  Route(온톨로지 값으로 만든 어휘) → Ground(어휘→노드→테이블별 실제 값, closure 전개)
        → Gate(부재·enum·범위·상수: HCX 0회 기각) → Plan(HCX: 실제 값 블록 + 조인키 + 선별 규칙 + 스키마)
        → 검증(validate_sql · 값 검사기 · 규칙 강제 · 사후조건) → 실행 → 조립(목록형은 HCX 0회)
```
[그림 1: `08_설계철학.md` 그림 4]

KG는 별도 그래프 엔진이 아니라 SQLite 매핑 테이블이다. 주최 기술세션의 정의("Hybrid는 한 소스 내 결합")에 따라 이 구조는 **값 사전 KG를 관계형 저장소에 사상한 Hybrid Retrieval**이다. 런타임에서 그래프를 걷는 일은 없다. 계층과 서열은 빌드 시점에 이행폐포로 펼쳐 두고, 질의 시점에는 접지·주입·검사 세 가지만 한다.

### 1.3 특화기능 셋

**① 손으로 쓴 ttl·KG가 없다.** 사람이 쓰는 것은 yaml 두 층뿐이다. 빌더 하나가 ttl 5개, KG 4테이블, 게이트 상수, 프롬프트 규칙을 같은 선언에서 생성하고, 검증 7종(죽은 alias, 값 충돌, 미완 포인터, 코드북 출처·기준일, 미지 컬럼, 부재 선언 대상, alias 확장 대상)에 걸리면 산출물을 만들지 않는다. 프롬프트에 주는 값과 검사하는 값이 같은 테이블(`kg_alias`)에서 나오므로 어긋날 수 없고, 도메인 추가는 yaml 하나로 끝난다. 2차 데이터 전환(7/11→8/24)과 9/2 온톨로지 확장(라벨 슬롯·국가/속성 노드·부재 선언 전수·등급 범위 선언)이 4도메인 부작용 0으로 들어간 것이 이 구조의 실측이다 ▶.

**② 테이블 축과 상품종류 축을 분리했다.** 국내ETF 마스터에는 ETN 545건, 해외ETF 마스터에는 65건이 섞여 있다 ▶. `DomesticETF`를 `ETF`의 하위 클래스로 두면 ETN 행까지 ETF로 단정해 `owl:disjointWith`와 모순이 된다. 그래서 테이블 클래스 4개(데이터 출처)와 상품종류 클래스(ETF⟂ETN, 실제 분류)를 다른 축에 두고 `pd_grp_no`·`cu_etn_yn` 컬럼이 판별하게 했다. 이 결정이 온톨로지 전체의 뼈대이고, "ETF 중 총보수 낮은 것"에 ETN이 섞이지 않는 실제 필터다.

**③ 축을 접지하고 선언을 강제한다.** 필터 값은 사전에서 오지만 "무엇을 세는가"는 모델 재량이었고, 규칙은 프롬프트 문서로만 전달돼 "실려도 무시되는" 경우 코드로 새어 나갔다. 15R 오답 30건 중 16건이 그 자리에서 났다 ▶. 규칙에 `text`(프롬프트)와 `enforce`(적용기 강제) 두 형태를 주고, 지표·단위·범위를 노드와 관계 속성으로 선언하는 확장이 진행 중이다(2.3.2 ④, 5.3).

### 1.4 주최 필수 구성요소 대응

| 구성요소 | 우리 대응 |
| :-- | :-- |
| 정형·비정형 분석·정제 [Parsing / Ontology] | 투자설명서·펀드페이지 수집 → `ext_fund_holdings`·`ext_fund_page` / enums yaml 컬럼층 = 상품별 LLM 가이드라인 |
| KnowledgeBase [Extraction / EntityResolution] | shared 개체층 + 코드북 13종 → KG. ER: 펀드 더미 키 49%, 운용사 표기 99종, 센티넬 문자열, 동일 키만 병합(이름만 같으면 병합 금지) |
| Intent·Retrieval [NL2SQL / Retrieval] | Route·Ground·Gate·Plan. 인텐트는 규칙 라우터 + 미특정 시 HCX |

용어: 이 문서에서 **부재 선언(ABSENT)** 은 컬럼 자체가 없는 것, **결측** 은 값이 비어 있는 것이다. **펀드** 는 운용단위 `(or_co, mtco)` 와 KG Fund 노드(`rptt` 묶음) 두 뜻이 있어 절마다 표기한다. 기준일은 2026-08-22, 외부 자료는 2026-08-24 발행분까지다.

## 2.2.1 온톨로지 설계 원칙과 구조

### 값은 사전에서 온다

이 그래프의 노드는 개체 하나이고, 간선은 그 개체가 각 테이블에 존재하는 실제 값이다. `kg_node` 41,580 · `kg_alias` 66,592 · `kg_edge` 7,414 · `kg_closure` 9,965 ▶. alias는 손으로 고른 예시가 아니라 컬럼 distinct 전체를 규칙으로 돌린 전수(66,592건 중 65,941건이 `source=rule`)라서 "사전에 없다"가 곧 "DB에 없다"다. 채권 `crd_grd`는 15/15, 국내ETF `cu_fund_mgmt_co`는 99/100이 사전에 걸려 있다 ▶.

미래에셋 노드 하나를 보면 구조가 보인다. 국내ETF 운용사 컬럼에는 `'미래에셋'`, `'TIGER'`, `'미래에셋TIGER200IT증권상장지수투자신탁(주식)'`처럼 펀드 이름이 통째로 들어간 표기 99종이 있다. 모델이 이 컬럼을 직접 보면 `= '미래에셋자산운용'`을 쓰고 0건이 된다. 사전은 99종을 노드 하나에 걸어 두고, 질문에 "미래에셋"이 나오면 그 테이블의 alias 값 목록을 IN 절로 넘긴다. 모델은 오염을 보지 않고 복사만 한다. [그림 2: `08` 그림 1]

계층은 빌드 때 펼친다. Region(국가⊂권역⊂글로벌), CreditGrade(등급⊂투자/투기 밴드, rank 1~20), Index(변형⊂정본)를 `skos:broader`로 선언하고 `kg_closure`에 조상-후손 쌍으로 적재한다. "AA- 이상"은 표준표 rank로 등급 4개를 고르고 각 노드의 alias에서 DB 표기(`AA0`)를 꺼내 `IN ('AAA','AA+','AA0','AA-')`가 된다. 8/31 실측에서 "A등급 이상 회사채"가 `= 'A-'` 단일 등급으로 나가 모수의 8%만 조회됐던 사고가 이 구조로 닫혔다 ▶.

### 공유 개체 11종과 관계 4종

허브에는 닫힌 분류축 여섯(AssetClass 9 · RiskGrade 7 · CreditGrade 21 · Currency 8 · Region 60 · Country 17)과 열린 개체 다섯(Organization 2,527 · Index 3,172 · Security 27,996 · Fund 7,584 · FundAttribute 179)이 있다 ▶. 관계는 질의가 요구하는 네 종류만 둔다. `hasAssetClass`·`coversRegion`(지수로 자산군·지역을 찾는다), `feedsInto`(자펀드→모펀드), `subsidiaryOf`(에코프로→자회사 3사, DART 사업보고서 근거). 역관계 세 쌍(`manages↔hasManager`, `issues↔hasIssuer`, `holds↔isHeldBy`)은 규격 작성 팁에 따라 선언했다.

구성종목 관계(`holds`)는 간선으로 옮기지 않았다. 국내 75,859행, 해외 906,848행, 펀드 59,206행이라 KG가 24배로 불어난다. 대신 `ext_*` 테이블 자체를 간선으로 간주하고 조인키 4쌍을 프롬프트에 준다. 관계형·집계형 KG에서는 질의 생성이 트리플 검색이나 홉 탐색을 압도한다는 결과(KGQA-1, Northwind 55.3 vs 0.7·3.4)가 이 결정의 근거이고, 관계 종류를 늘리면 정확도가 오른다는 근거는 우리가 검토한 어느 논행연구에도 없었다.

### 편입 기준과 두 층

편입 기준은 하나다. **질문의 어휘가 컬럼의 값으로 이어지는가.** 위험등급처럼 값이 7개인 닫힌 축도, 종목처럼 2만 8천 개인 열린 개체도 이 기준을 통과하면 노드가 된다. 수익률·순자산은 질문에 어휘로 나오지 않고 조건식으로만 나오니 그래프에 없다. 상품 행 자체도 없다. 마스터 4테이블 280개 컬럼 중 약 20개 컬럼의 값만 노드에 걸려 있고, 나머지는 SQL이 다룬다.

선언은 두 층이다. `enums/*.yaml`(컬럼층)은 담당자별로 컬럼마다 결측 판정(`missing_reason`·`zero_is_value`·`value_semantics`), 조회 규칙, 부재 선언, 되묻기, 답변불가 사유를 적는다. 4도메인 컬럼 판정은 58/58 · 62/62 · 35/37 · 66/68이다 ▶. `shared/*.yaml`(개체층)은 개체·계층·"어느 컬럼의 값이 이 개체인가"를 적는다. 둘을 잇는 것은 컬럼층의 `kg_entity` 포인터 한 줄이다. 빌더가 둘을 같이 읽어 ttl과 KG를 동시에 뱉으며, 검증 7종에 걸리면 산출물을 만들지 않는다.

### 부재도 선언한다

값을 고치지 않고 의미를 선언한다는 원칙(주최 공지 "0·결측은 의도된 값")의 귀결로, 컬럼 자체가 없는 속성 14건을 ABSENT로 선언했다. 채권의 자산군·지수·투자지역·등급이력, ETF의 신용등급·시계열, 해외ETF의 위험등급, 펀드의 신용등급·좌수·운용역·시계열이다. 이 선언은 ttl의 주석이자 게이트의 어휘다. "위험등급 낮은 해외ETF"는 HCX를 부르기 전에 기각된다. 답변불가 5문항은 검색 실패가 아니라 구조 판정으로 처리되며, 그래서 부분일치로 그럴듯한 것을 찾아 답을 만드는 경로가 없다.

### 규칙 12종

컬럼층의 판정은 규칙 12종으로 정리된다. 지칭정리·결측방어·외부병합·행 단위·기본모수·파생유도·배타분리·단위스케일·금지규칙·부재선언·계층·기준일. 규칙마다 "데이터가 이랬다 → 그래서 이렇게 정했다 → 전수 인벤토리 → 실측 근거 → 안 지키면"의 문서가 yaml에서 생성되며(`docs/ontology_rules/`), 다음 절의 도메인별 서술은 이 번호를 인용한다.

## 2.2.5 합쳐지는 지점

도메인 절이 셋이어도 온톨로지는 하나다. 표 C(도메인×공유 개체 매트릭스, `03_구성도_설계.md` §4)를 열로 읽으면 도메인 그림이 되고 행으로 읽으면 한 개체를 몇 도메인이 공유하는지가 보인다. Organization과 Currency는 네 테이블 전부, Index·Region·AssetClass는 세 테이블, Fund·FundAttribute·Country는 펀드만 닿는다.

증거 셋. **첫째, 지수.** `Idx_MSCI_ACWI` 노드 하나에 국내ETF `ref_base_index`, 해외ETF `cu_base_index`, 펀드 `bmrk_nm`의 표기 변형이 전부 걸려 있다. 교차 질의는 이 구조의 직접 수혜자다. "삼성전자를 보유한 국내ETF·해외ETF·펀드"에서 삼성전자 노드 하나에 국내 holdings의 티커, 해외 holdings의 cusip, 펀드 holdings의 ISIN이 alias로 달려 있어, 접지 한 번으로 조인키 세 개가 내려오고 UNION ALL 템플릿에 들어간다. 도메인별 그래프였다면 접지가 세 번 일어나고 표기를 모델이 알아야 했다. `[실측 붙일 곳: CROSS-001 think_trace — Ground 매핑 블록 3테이블]`

라벨 충돌은 구조로 막는다. '중국', 'ETF', '국내' 같은 라벨이 상품군 명사나 Region을 가로채던 회귀(3R·5R)를, 이름을 하드코딩하지 않고 빌더가 라우터 어휘와 KG 라벨을 대조해 충돌 노드 8개를 매칭 키에서 제외하는 방식으로 닫았다 ▶.

## 2.3 검색 방법론

### 2.3.1 왜 SQL 생성인가

데이터가 관계형 마스터이고 답은 항상 SQL 한 문장으로 표현된다. 문제는 검색이 아니라 조건 조립이다. 벡터 검색은 "비슷한 것"을 돌려주고 그래프 탐색은 "노드"를 돌려주는데, 둘 다 모델이 그것을 다시 WHERE 값으로 바꿔야 하고 그 변환에서 틀린다. 게다가 환각이 감점인 대회에서 "유사한 것을 찾아 주는" 검색은 그 자체가 오답 경로다. 호출당 예산이 12초(권장 60초 안의 절대 방어선)라 런타임 탐색은 빌드 시점 전처리로 옮겨야 했다. 그래서 벡터 DB는 채택하지 않았고(안건 A-5), 그래프는 값 사전으로만 쓴다.

### 2.3.2 온톨로지가 개입하는 네 지점

[그림 4: 파이프라인 한 장, 상자마다 읽는 층을 색으로 — `08` 그림 4]

**① 접지 (Route·Ground).** 라우팅에 사람이 쓴 단어 목록이 없다. KG alias의 실제 값(가중치 3), 범주 컬럼의 distinct(2), ETF 약어명, yaml 동의어로 어휘를 자동 생성하고 길이 보정 점수로 테이블을 고른다. 한국어 수식 구조에서 마지막 상품명사가 머리라는 규칙이 얹혀 "채권형 ETF"가 ETF로 간다. Ground는 질문 어휘를 노드로 접지하되 **대상 테이블에 alias가 없는 노드는 버린다.** "한국전력 채권"에 주식 노드의 ETF 구성종목 alias가 실려 엉뚱한 조인을 만들던 회귀의 처방이다. 접지된 노드는 closure 후손과(자회사 질의면) `subsidiaryOf` 1단까지 펼쳐 대상 테이블의 실제 값만 컬럼당 60개까지 프롬프트에 놓는다. 노드 ID는 넘기지 않는다. 넘기면 모델이 `= 'Org_issuer_97e46…'`을 쓴다.

**② 게이트 (생성 전 기각).** 부재 속성, enum 밖의 값, 범위 밖의 등급, 상수 컬럼 위반이면 HCX를 부르지 않고 끝낸다. 등급 판정은 목록이 아니라 표준표의 형태(`^([A-D])\1{0,3}[+\-0]?$`)에서 온 규칙으로 `not_grade / unknown / no_data / ok` 네 갈래를 가른다. "AAAA"는 `unknown`, "BB+"는 표에는 있으나 데이터에 없는 `no_data`다. 생성 전·실행 없는 답변가능성 게이트의 정식화(REF-1)를 따랐고, 프롬프트 기반 거절만으로도 금융 도메인에서 F1 97.2를 보인 그 논문의 기준선이 우리 방식의 하한이다.

**③ 규칙 주입 (Plan).** 프롬프트는 KG 개체 매핑(실제 값), 상품 고유명 슬롯, 조인키 4쌍, 도메인 규칙, 되묻기·답변불가 규칙, 스키마 순이다. 규칙은 두 층이다. 항상 싣는 것(모수·센티넬·단위·기준일)과 질문 어휘가 있을 때만 싣는 것. 전부 주입보다 선별 주입이 낫다는 결과(DK-1 39.0→47.5)를 따랐고, 8/31 paired 실험(87문항)에서 선별이 전부 주입을 3건 이기고 0건 졌다 ▶. 규칙은 산문이 아니라 SQL 조각 형식(`보수유효: cu_charge_rt > 0 AND pd_grp_no='ETF'`)으로 쓴다.

**④ 검증 (생성 후).** `validate_sql`이 허용 테이블·SELECT·LIMIT를 보고, 값 검사기가 WHERE 리터럴을 ①과 같은 사전과 대조한다. 사전이 그 컬럼 distinct의 98% 이상을 덮는 컬럼만 검사 대상이다(부분 사전은 정상 값을 기각한다). 실패 시 재생성 1회. 0행이면 조건을 하나씩 떼어 Sub-SQL로 어느 조건이 비웠는지 진단하고 그 진단을 거절 답변의 근거로 쓴다. 자동 재시도나 LIKE 완화는 하지 않는다. 거절이 정답인 문항에서 환각 경로가 되기 때문이다.

여기에 9/3부터 **규칙 강제**가 들어간다. 15R 실측에서 코드로 강제된 펀드 규칙 30개 중 20개가 "규칙이 프롬프트에 실려도 재현되지 않는다"는 이유로 생겼고, 코드 규칙은 SQL 모양에 묶여 UNION 가지에서 침묵했다(교차 오답 16건). 규칙 전달 감사(9/3)는 그 "무시" 중 일부가 트리거 미일치로 아예 실리지 않은 것(공식 예시 #2의 설명서 조인 규칙)과 모순 규칙의 동시 주입(행 단위 vs 펀드 단위)임을 확인했고, 형식만 바꾸는 개입은 효과가 없었다(A 42.9% vs B 39.3%, p=1.0, 검정력 낮음) ▶. 그래서 규칙에 `text`(프롬프트)와 `enforce`(적용기가 SQL에 강제, 표식 + 체인 끝 사후조건) 두 형태를 주었다. 인벤토리 결과 20개 중 9개는 확장 없이 슬롯으로, 8개는 스키마 확장 후, 3개는 코드 잔류다 ▶. 프리즈 전 전환 3개(기본모수·펀드단위·지수 정본)의 효과는 5.1에 `[실측 붙일 곳: 17R]`.

### 2.3.3 교차 질의와 하지 않은 것

조인키는 네 쌍이다. 국내ETF `etf_code = pd_itm_no`, 해외ETF `etf_ticker = replace(pd_itm_no, '.K'/'.O')`, 펀드 `(grp, or_co) = (mtco_itm_no, or_co_xtn_itt_cd)`, 펀드페이지 `itm_no`. 해외 ISIN 조인은 폐기했다. `pd_isin_cd`가 두 상품에 걸린 63종에서 오배정 8건이 실증됐다. 펀드 `grp` 단독 조인도 금지했다. `mtco_itm_no`는 운용사 안에서만 유일해 179,333쌍 중 5,099쌍(2.84%)이 남의 펀드에 붙었다 ▶. 교차 질의는 한 SQL에 욱여넣지 않고, 개수·속성 문형은 가지별로 단일 도메인 경로를 돌린 뒤 결정층이 조립한다(진행 중). 단위(KRW/USD)·기간(1y/1d) 불일치는 답변에 명시한다.

하지 않은 것과 이유. 0행 자동 재시도·LIKE 완화(거절 문항의 환각 경로), 그래프 탐색·간선 확장(근거 없음), 파생 컬럼(값을 고치면 "왜 없는지"를 답할 근거가 사라진다. 이름 규약은 조건식으로), 컬럼 프루닝(병목이 아니다. 라우팅은 재현율 우선), 모델 교체(문서 유무 +17~23pp vs 모델 차 5pp). HCX 필수 구간(인텐트·답변 생성)은 준수하며 런타임 `src/`에 타사·유료 LLM 사용은 0건이다.

## 펀드 §B.2 결함 → 선언 (→ 2.2.4)

도입은 06 §B.0 그대로. 여기서는 6건.

### B.2-1. 행이 펀드가 아니라 클래스이고, 묶음 키로 보이는 컬럼은 묶음 키가 아니다 → 행 단위 선언 + 복합키 (2층·기수)

- **데이터가 이랬다**: 23,676행은 클래스 단위다. 묶음 키처럼 보이는 `std_itm_no`는 distinct 18,948 중 18,909가 `itm_no`와 1:1이고, 2개 이상을 가리키는 값이 39개뿐이다. 결측 515 + 12자 패딩 위장결측 145 = 660행은 전부 판매완료다 ▶.
- **그래서 이렇게**: `row_grain`을 "행 = 클래스"로 선언하고 펀드 단위 키를 `(or_co_xtn_itt_cd, mtco_itm_no)` 복합키로 못 박았다. `mtco` 단독은 415종이 2개 이상 운용사에 걸친다. 순자산은 클래스별 중복 기재라 SUM 금지·펀드 단위 MAX(`fp:navTotal` 주석). 관계 기수(행 → Fund, N:1)를 선언에 두는 확장이 진행 중이다.
- **런타임에서**: Plan이 `펀드단위` 규칙을 싣고, 규칙 강제가 `COUNT(*)`를 `COUNT(DISTINCT 펀드키)` + 클래스 수 병기로 교체한다. 조립이 "펀드 N개(클래스 M개)"를 병기한다.
- **실측 사례**: `S8` "KB자산운용이 운용하는 공모펀드는 몇 개야" → 129개(클래스 625개) ✅. 같은 규칙이 교차 문형 `KG-025`에서는 코드 가드의 SQL 모양 의존으로 발동하지 않아 850(클래스 수)이 나갔다 — 규칙 강제로 옮기는 이유 ▶.
- **안 지키면**: `GROUP BY mtco_itm_no` 단독 → `grp='00'`이 운용사 34곳에 걸려 남남 펀드가 합산.

### B.2-2. 사모 8,960행 혼입 → 기본 모수 선언 (2층)

- 2차 데이터에 사모 8,960행이 들어왔다(1차 168). 기본 모수를 `sale_yn='판매중' AND prvo_pbff_desc='공모'`로 못 박았다. 8,969행 / 3,040펀드 ▶. 모든 답변이 모수를 명시한다. 규칙 강제 P0-1이 이 절이다. 안 지키면 "펀드 몇 개"가 2.6배 부풀고, 랭킹에 판매완료 상품이 오른다.

### B.2-3. 더미 키를 값으로 취급하면 한 값에 1만 행이 뭉친다 → 더미 판정 (2층)

- `rptt_ksd_itm_no` 더미 6,970행(`KR0000000000` 5,308), `fss_itm_no` 더미 11,611행(49.2%) ▶. `normalization.dummy_as_missing`으로 조인·개체 키에서 제외했다. KG Fund 노드는 더미를 뺀 rptt 묶음 6,867 + 모펀드 717이다. 안 지키면 5,308 클래스가 한 펀드가 된다.

### B.2-4. 속성이 한 컬럼에 압축돼 있다 → token 노드 (1층)

- `prfd_attr_cds`는 코드 210종 15축이 콤마로 이어진 다중값이다. LIKE로 풀면 '10'이 '110'에 걸린다. 속성 코드 179개를 FundAttribute 노드로 만들고 alias에 `match_kind='token'`과 확정식 `','||col||',' LIKE '%,raw,%'`를 붙였다. 코드북(`fund_attr_code.csv`)으로 20종 유일 확정. 모델은 "연금저축 가능한 ESG 펀드"에서 태그 두 개의 확정식을 AND로 복사할 뿐 컬럼 형식을 추측하지 않는다. 같은 컬럼의 국가 태그 17종은 Country 노드다. 유형 축 6개와 `or_attr_desc`(자산군·운용구조·파생활용 3축 압축)는 `axis_mapping`으로 분리하고, 펀드 유형은 개체가 아니라 하위 클래스로 둔다(FIBO 원칙).

### B.2-5. 좌수·운용역·시계열이 없다 → 부재 선언 5건 (3층)

- KG-027 실측: 설정유형코드 '10'을 "10좌"로 6펀드에 단언한 사고가 계기다. `hasUnitsOutstanding`·`hasFundManager`·`hasNavHistory`·`hasHoldingsHistory`·`hasCreditGrade`를 ABSENT로 선언하고 대체 안내(`fd_nast_suma`·`bns_bpr`·`ext_fund_holdings`)를 붙였다. 게이트가 생성 전에 기각한다.

### B.2-6. 운용사·수탁사가 코드뿐이고 약칭 라벨은 매칭 하한에 걸린다 → 코드북 + 공식 라벨 슬롯 (1층)

- 마스터에 운용사 이름 컬럼이 없다. `asset_manager.csv` 275종, `trustee.csv` 50종 코드북으로 Organization 노드를 만들고, `organization.yaml`의 약칭(`'삼성'` 2자)이 라벨 길이 하한에 걸려 "삼성자산운용 펀드"가 Ground 0이던 FND-034를 `label_official` 슬롯 분리로 닫았다. 브랜드 하나가 법인 코드 여럿에 걸리는 경우(삼성자산운용·삼성액티브)는 같은 공식 라벨의 형제 코드를 IN으로 묶는다.

### B.3 한계

**Fund의 두 뜻**을 분리하지 않았다. 운용단위 `(or_co, mtco)` 14,467과 KG Fund 노드(`rptt` 묶음) 7,584가 공존한다. 집계·순자산은 복합키, 개체 조회는 rptt로 갈라 쓰고 있으며, 분리하지 않은 이유는 ttl 클래스명과 도해가 함께 바뀌는 데 비해 현재 오답을 만들지 않아서다. FundClass 노드 0·`belongsToFund` 간선 0은 결함이 아니라 컬럼이 이미 담고 있어 23,676 노드 중복 생성을 피한 설계이나, 관계 기수를 선언하지 않은 대가가 교차 문형의 클래스↔펀드 오답으로 나타났고 그 확장이 진행 중이다. 비정형 설명서 파싱은 구성종목·페이지 항목까지이며 "투자전략 동향" 류 서술은 범위 밖이다. 위험등급 NULL 14,987(63%)은 보완 불가다 ▶.

## 펀드 §C 흐름도 — "국민성장펀드의 구조와 투자전략 동향" (→ 4.3)

| 단계 | 일어나는 일 | 읽는 온톨로지 |
| :-- | :-- | :-- |
| Route | "펀드" 머리명사 → `public_funds` | 라우팅 어휘 |
| Ground | "국민성장펀드" → 상품 고유명 슬롯(residual_name_token) + Fund 노드(rptt 묶음). 모펀드면 `feedsInto` 후손 | 1층 Fund · feedsInto |
| Gate | "구조·투자전략·동향" 중 부재 항목(운용역 등) 판정 | 3층 ABSENT |
| Plan | `펀드단위` 복합키 GROUP BY, `설명서항목` → `ext_fund_page` JOIN(`itm_no`, 컬럼 전부 한정), 기본모수 | 2층 + 조인키 |
| 검증 | JOIN 템플릿·별칭 한정, 값 사전 대조, 규칙 강제 | 3층 |
| 실행 | 클래스 목록 → 펀드 단위 요약 + 설정일·환매조건 | — |
| 조립 | 구조(모/자·클래스 수·운용사·수탁사) + 페이지 항목 + **"투자전략 동향은 제공 데이터에 없음"** 명시 | answer_rules · ABSENT 안내 |

이 문항은 규칙 전달 감사에서 **`설명서항목` 규칙이 트리거 미일치로 프롬프트에 실리지 않은** 유일한 확정 사례였다. 처방은 트리거 낱말 추가(yaml 한 줄)이며 9/3 적용. `[실측 붙일 곳: 수정 후 think_trace — Plan 줄에 ext_fund_page 등장, answer 첫 3줄]`

## 펀드 §D 현업 적용 지점 (→ 5.2)

클래스 도배와 더미 키를 판정 규칙으로 격리했기 때문에 "펀드 단위 순자산·클래스 수·운용사별 집계"가 현업 보고서와 같은 기준으로 나온다. 속성 태그 15축을 token alias로 열어 두어 "연금저축 가능한 ESG 해외 펀드" 같은 다축 필터가 상품명 검색 없이 성립한다. 판매 현장에서는 위험등급이 없는 클래스에 대해 유추하지 않고 "등급 없음"으로 답하는 것이 적합성·설명의무 관점의 가치다. 없는 등급을 만들어 내는 챗봇은 창구에서 쓸 수 없다.
