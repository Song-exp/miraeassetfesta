# 온톨로지·KG 구축 과정 — ETF (2026-09-04 · 병철)

> "EDA → 뜻 정리 → yaml → 빌드 → KG·ttl" 이 실제로 어떤 손순서였는지의 기록.
> 모든 판정은 같은 여섯 걸음을 밟았고, 아래 실례 3개가 세 층(값 사전 / 규칙 / 게이트)을 하나씩 대표한다.

---

## 0. 여섯 걸음 — 판정 하나의 일생

```
① 발견(EDA)      데이터를 쿼리로 뜯어보다 이상한 것을 만난다
② 뜻 정리(판정)   "이 값은 무슨 뜻인가"를 실측으로 확정한다 — 추측 금지, 반례 탐색 포함
③ 기록(yaml)     판정을 기계가 읽는 자리에 적는다 — 문서에 적으면 챗봇은 모른다
④ 생성(빌드)     build_ontology.py 가 yaml → ttl 5개 + kg_* 4테이블을 만든다 (V1~V7 검증 통과 시에만)
⑤ 사용(런타임)   Route·Ground·Gate·Plan 이 매 질문마다 그 판정을 읽는다
⑥ 검증(회귀)     실측 질문을 평가 문항으로 승격 — 이후 모든 수정에서 자동 재검사
```

핵심 규율 둘. **값을 고치지 않는다**(주최 8/24 — 판정만 기록) · **수치는 전부 실측**(추측으로 적은 규칙은 반드시 실전에서 뚫렸다).

## 1. 기록의 자리 — 무엇을 어디에 적나

| 자리 | 담는 것 | ETF 실측 규모 |
| :-- | :-- | :-- |
| `enums/domestic_etfs.yaml` `columns:` | 컬럼별 뜻 — 결측 사유, 0의 의미, 함정, answer_policy | 98컬럼 판정 |
| 〃 `query_rules:` | 질의 조립 규칙 — 조건식 + 근거 + 반례 + 실측 사례 | 44개 (해외 23) |

| 〃 `synonyms:` `clarify:` `derivation_rules:` `external_join:` | 통칭, 되묻기, 파생 판정, 조인 계약 | 61 / 5 / 1 / 1 |

## 2. 실례 ① — 총보수 0 (2층 규칙이 된 판정)

- **① 발견** — 총보수 오름차순을 돌려보니 0% 상품이 상위를 도배. distinct 를 세니 0·NULL 이 1,713행, 값이 있는 건 **67건뿐**.
- **② 뜻 정리** — 0이 "무료"인가 "미입력"인가? 반례 탐색: 무료 ETF는 실재하지 않고, ETN 545건은 전건 NULL(보수 개념이 다름). 주최 8/25 답변("값 0인 행은 포함하지 않는 게 맞다")으로 확정: **0 = 미입력**.
- **③ 기록** — `columns.cu_charge_rt` 에 뜻을, `query_rules.보수유효` 에 조건식을: `cu_charge_rt > 0 AND pd_grp_no='ETF'` + "답변에 모수 67건을 밝힌다".
- **④~⑤** — 규칙은 빌드를 거치지 않고 그대로 Plan 프롬프트에 실린다. 개별 조회는 `NULLIF(cu_charge_rt,0)` 로 감싸 답변기가 0을 아예 못 보게 했다 — 말로 "0이면 미수록이라 말하라"고 적었을 땐 무시당했다(서버 실측). **말로 하는 규칙은 무시된다 → 기계적 차단**이 이 판정에서 나온 교훈이다.
- **⑥ 검증** — 서버 오답 2회("총보수 0.0%입니다" · 집계에 과잉 적용돼 삼성 227→18개)가 각각 회귀 문항이 됐고, 적용 범위("보수를 묻지 않은 질의에는 걸지 않는다")까지 규칙에 박혔다.

## 3. 실례 ② — 캠브리콘 (1층 값 사전이 된 판정)

- **① 발견** — 공식 예시 #3 이 0건. 구성종목이 마스터에 없어 외부 수집했는데, 수집물 안에서 같은 회사가 **표기 6종**(본토 티커 `688256 C1` · 영문 사명 2형 · ISIN · CUSIP …)으로 흩어져 있고, 그마저 국내 티커 칸이 비어 있었다.
- **② 뜻 정리** — 6종이 같은 회사인지 하나씩 실측 대조(ISIN↔티커↔사명). 원칙 확정: 키 우선순위 티커>CUSIP>LEI>이름, **이름만 같으면 병합 금지**(삼성전자↔삼성전기 오병합 방지).
- **③ 기록** — `codebooks/security_alias_manual.csv` 에 종목 9개의 국내 티커를 수기 등재(852행 분).
- **④ 생성** — 빌드가 `Sec_m_cambricon` 노드 1개 + alias 6종 + closure 를 DB 에 생성. **KG는 DB 안에 살므로 코드 배포와 별개로 DB 배포가 필요하다** — 이걸 놓쳐 한 번 더 실패했다.
- **⑤ 사용** — Ground(접지)가 질문의 '캠브리콘'을 노드로 찾아 표기 6종을 전부 프롬프트에 내려준다. HCX 는 그 값을 WHERE 에 복사할 뿐, 문자열을 추측하지 않는다.
- **⑥ 검증** — 0건(9/1) → 접지 실패 → 복구 후 14건·1위 비중 13.25% 정답 일치(9/4). 실패 3회가 각각 규칙·사전·배포 경로의 수리가 됐다.

## 4. 실례 ③ — 해외 위험등급 (3층 게이트가 된 판정)

- **① 발견** — 해외 테이블 49컬럼을 훑어도 위험등급이 없다. 국내에는 있다.
- **② 뜻 정리** — 결측이 아니라 **구조적 부재**. 위험한 건 LLM 이 국내 기준으로 유추해 지어내는 것 — 평가에 "답변불가 질의에 답을 생성하면 감점"이 있다.
- **③ 기록** — 해외 yaml 에 부재 선언. 빌드가 `etf_gl.ttl` 의 ABSENT 와 게이트 상수를 **한 선언에서** 만든다(이원화 방지).
- **⑤ 사용** — "위험등급 낮은 해외 ETF" → Gate 가 **HCX 호출 0회**로 기각 + 대체 안내. 점수 방어이자 비용 방어다.

```bash

git add … && git commit && git push       # main

#   shared·codebooks 를 고쳤으면 --db-only  # KG 는 DB 안에 산다
```

## 6. 왜 이 구조인가 — 한 단락

EDA 보고서를 아무리 잘 써도 챗봇은 그걸 읽지 않는다. 이 구조의 요점은 **판정의 저장 위치를 "사람이 읽는 문서"에서 "챗봇이 매 질문마다 읽는 자리"로 옮긴 것**이다. 그러자 유지보수가 단순해졌다 — 오답의 원인을 찾으면 고칠 자리가 세 층 중 하나로 정해지고, 고치면 행동이 바뀌고, 회귀 문항이 재발을 지킨다. ETF 트랙에서 이 루프를 스물아홉 번 돌았다.
