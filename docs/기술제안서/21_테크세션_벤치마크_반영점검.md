## C. 결정이 필요한 2건

### C-1. SHACL 을 어떻게 처리할 것인가 (A-3)

주최 자료는 검증층에 SHACL 을 둔다. 우리는 **같은 일을 코드 게이트로 한다** — `range_by_table`(0~6)·`absent_in`(속성 부재)·enum·상수 컬럼이 전부 SHACL 제약과 1:1로 대응된다. 선택지:

1. **서술로 정면 대응(권장 · 비용 0)** — 부록 A 머리에 한 단락: *"검증 선언은 yaml 한 곳에서 나오고, 집행은 런타임 코드가 한다(레이턴시 예산 때문). `sh:minCount`·범위·`sh:in`·shape 부재에 각각 대응하는 우리 장치는 …"* + 대응표 4행. **정직하고 심사자가 찾는 항목에 걸린다.**
2. ttl 에 실제 `sh:NodeShape` 을 병기 — 빌더 수정이 필요하고 코드 프리즈(9/6)가 임박. **비권장**.

→ 기본값 1번으로 진행하되, ttl 생성기는 리드 소관이라 확인 요청.

### C-2. §5 정량화 재료 (B)

우리가 이미 가진 숫자 중 사업성 서술로 쓸 수 있는 것:
- **환각 방지 9/9** · 게이트 기각 10건이 전부 HCX 0회 → **비용**: 답변불가 질의는 LLM 비용 0원
- 규칙 주입 선별로 프롬프트 11,760자 → 5,800자(**51% 절감**) → 질의당 토큰 비용 절반
- 오답 → 회귀 승격 **79건**(ETF 29 · 채권 50)이 자동 재검사 → **유지보수 인건비** 대체
- 코드북 교체 한 번으로 등급 체계 개편 대응(채권) · yaml 한 줄로 규칙 변경 → **신상품·규제 변경 대응 시간**
- 상품군 확장: 새 테이블을 붙이는 비용 = yaml 1개 + 코드북 (개체 11종은 재사용)

→ 이 재료로 "질의 1건당 비용 · 규칙 변경 리드타임 · 유지보수 공수" 세 축을 숫자로 쓰면 대상작의 정량화에 대응된다.
