# 🧩 확장성 — 이 구조가 다른 데이터에도 그대로 가는가 (2026-09-04 · 병철)

> 질문: *"EDA → 온톨로지·KG → SQL → 답변 이 흐름이 다른 데이터에도 똑같이 적용되나?"*
> 답: **구조는 그대로 가고, 판정은 새로 해야 한다.** 아래는 그 경계를 실측으로 나눈 것이다 — §5(기대효과·확장성) 서술 재료.
> 🔴 원칙: "확장 가능하다"는 주장 대신 **이미 4번 한 실적**과 **재사용되지 않는 부분**을 함께 적는다. 한계를 적는 쪽이 신뢰를 준다.

## 0. 한 줄

**우리는 이미 4개 상품군(채권·국내ETF·해외ETF·펀드)을 같은 구조 위에 올렸다.** 확장성은 계획이 아니라 반복된 사실이고, 반복하며 드러난 비용도 측정돼 있다.

## 1. 세 갈래로 나눈 재사용 경계

### ① 그대로 가는 것 — 도메인 무관 (코드 수정 0)

| 자산 | 왜 재사용되나 |
| :-- | :-- |
| **방법 6걸음** — 발견(EDA) → 뜻 정리(판정) → 기록(yaml) → 생성(빌드) → 사용(런타임) → 검증(회귀) | 데이터 종류와 무관한 절차다 |
| **공유 개체 11종** — Organization · Security · Index · Region · Country · Currency · RiskGrade · CreditGrade · AssetClass · Fund · FundAttribute | "세상에 실재하는 것"이라 상품군에 속하지 않는다. 지수 하나(`Idx_MSCI_ACWI`)에 국내ETF·해외ETF·펀드가 동시에 매달리는 것이 증거 |
| **빌드 파이프라인** `build_ontology.py` | yaml 을 읽어 ttl·KG 를 만든다. 테이블이 늘어도 코드는 그대로 |
| **런타임 8단계** Route→Ground→Gate→Plan→Guard→Execute→Answer | 전부 yaml 이 주는 사전·규칙으로 돈다 |
| **결함 유형 분류** 미입력 0 · 센티넬 · 더미 코드 · 구조적 부재 | 새 데이터에서도 같은 네 유형이 나온다 → **무엇부터 찾을지의 체크리스트** |
| **함정 목록** 고정폭 패딩 · 약칭 · 이름 두 벌 · 언어 분단(한글 이름 vs 영문 코드) | 금융 데이터에서 반복되는 패턴 |

### ② 새로 해야 하는 것 — 자동화되지 않는다 (정직한 비용)

컬럼마다 "이 값이 무슨 뜻인가"를 사람이 판정해야 한다. 이것이 이 방식의 **본질적 비용**이고, 팔란티어가 금융 온톨로지에 전문가 50명·6개월을 넣는 이유와 같은 지점이다(테크세션).

| 도메인 | 판정한 컬럼 | 만든 질의 규칙 | yaml 줄 수 |
| :-- | --: | --: | --: |
| 국내채권 | 58 | 41 | 933 |
| 국내ETF | 62 | 45 | 1,285 |
| 해외ETF | 37 | 24 | 779 |
| 공모펀드 | 68 | 31 | 1,411 |

여기에 도메인 특유의 외부 지식이 코드북으로 붙는다(채권 신용등급 서열표 · ETF 종목 티커 · 펀드 운용사 정식명). **데이터에 없는 지식은 사람이 가져와야 한다.**

### ③ 🔴 정직한 한계 — 결정층에는 도메인 코드가 있다

런타임 함수 **239개 중 도메인 특수 가드가 39개**다 (펀드 29 · ETF 6 · 채권 4). 오답을 급히 막느라 규칙이 아니라 코드로 들어간 자리다.

→ 따라서 정확한 서술은 이것이다: **선언층(값 사전·규칙·게이트)은 100% 재사용, 결정층은 그 도메인의 결함만큼 코드가 붙는다.**
→ 확장 비용 = `yaml 1개 + 코드북(필요시) + 그 도메인의 결함 수만큼의 가드`. 가드를 규칙으로 되돌리는 것(enforce 슬롯화)이 진행 중인 다음 단계다.

## 2. 실적 — 이미 흡수한 변화 3건

| 사건 | 변화 폭 | 흡수 방법 | 코드 수정 |
| :-- | :-- | :-- | :-- |
| **2차 데이터 전환** (8/24) | 채권 42,394행×40컬럼 → 21,882×58 · 컬럼명 전면 소문자화 · PK 복합화 · 국내ETF 73→98컬럼 | yaml 재작성 + 재빌드 | 없음 |
| **1차 판정 4건 뒤집힘** | 추적오차·괴리율·분배수익률이 "전부 0, 못 쓰는 컬럼" → 실제 값 수록으로 반전 | 재실측 후 판정 갱신, 규칙 신설 | 없음 |
| **개체 확장** (9/2) | 라벨 슬롯·국가/속성 노드·ABSENT 전수·등급 범위 테이블별 선언 | shared yaml 선언 추가 | 없음 |

세 번 모두 **데이터가 바뀌었지 코드가 바뀌지 않았다.** 이것이 "yaml 단일 원천"의 실효다.

## 3. 새 상품군을 붙인다면 — 구체 시나리오

**예: 파생결합증권(ELS/DLS)**

| 필요한 것 | 이미 있는가 |
| :-- | :-- |
| 발행사(증권사) | ✅ Organization 재사용 |
| 기초자산(지수·종목) | ✅ Index · Security 재사용 |
| 통화·투자지역·위험등급 | ✅ 재사용 |
| **조기상환 조건·낙인 배리어** | ❌ 신규 개체 1~2종 + 그 판정 |

즉 **개체 11종 중 9종이 그대로 쓰이고 새로 정의할 것은 1~2종**이다. 랩·연금·예적금도 같은 비율이다. 확장의 실제 부담은 개체가 아니라 **그 상품군 데이터의 결함을 읽는 EDA 시간**이다.

## 4. §5 에 쓸 문장 (초안)

> 이 구조의 확장 단위는 코드가 아니라 선언이다. 새 상품군을 붙이는 데 필요한 것은 `enums/<table>.yaml` 하나와, 그 도메인에만 있는 개체 선언이다 — 공유 개체 11종·빌드·런타임 8단계는 그대로 재사용된다. 실제로 4개 상품군이 같은 구조 위에 있고, 2차 데이터 전면 교체(컬럼명 소문자화·PK 복합화·컬럼 25개 증가)를 코드 수정 없이 yaml 재작성만으로 흡수했다.
> 재사용되지 않는 것도 분명하다. **컬럼의 뜻을 판정하는 일은 자동화되지 않는다** — 도메인당 37~68개 컬럼을 사람이 읽었고, 그 산물이 yaml 779~1,411줄이다. 결정층에는 아직 도메인 특수 가드가 39개 남아 있어, 이를 선언으로 되돌리는 것이 다음 단계다.
