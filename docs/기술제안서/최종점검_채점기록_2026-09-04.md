## FIN-06 — 운용사별 ETF 개수 (수치 오답)

### 서버가 낸 SQL
```sql
SELECT ref_fund_mgmt_co, COUNT(*) as cnt FROM domestic_etfs
WHERE pd_grp_no = 'ETF' AND pd_sale_yn = 1
GROUP BY cu_fund_mgmt_co ORDER BY cnt DESC LIMIT 5
```

### 왜 틀렸나
SELECT 는 정본 컬럼(`ref_fund_mgmt_co`)인데 **GROUP BY 는 오염 컬럼**(`cu_fund_mgmt_co`)이다.
`cu_fund_mgmt_co` 에는 운용사·판매사·브랜드·상품명이 섞여 있어서, 같은 운용사가 브랜드별로 쪼개진다.
SQLite 는 이런 문장을 오류 없이 실행하고 각 그룹에서 아무 행의 정본 이름을 하나 집어 온다 — **조용히 틀린다.**

로컬 재현(판매중 ETF):

| 운용사 | 서버 답 (오염 컬럼 기준) | 실제 (정본 기준) |
|---|---|---|
| 삼성자산운용 | 224 | **240** |
| 미래에셋자산운용 | 188 | **230** |
| KB자산운용 | 142 | 142 |
| 한국투자신탁운용 | 110 | 110 |
| 한화자산운용 | 81 | **85** |

집계 그룹 수 자체가 다르다 — 오염 컬럼 **84그룹** vs 정본 **28그룹**. 1·2위가 각각 16개·42개씩 적게 세어졌다.

### 고친 곳
`src/runtime/pipeline.py` 의 `ensure_etf_mgmt_canon()` — 지금까지 FROM 앞(SELECT 목록)만 치환했다.
GROUP BY·ORDER BY·HAVING 절도 같이 정본으로 바꾸도록 확장했다.

```python
_MGMT_TAIL_SEG = re.compile(
    r"((?<![A-Za-z_])(?:GROUP\s+BY|ORDER\s+BY|HAVING)(?![A-Za-z_]))"
    r"(.*?)(?=(?<![A-Za-z_])(?:GROUP\s+BY|ORDER\s+BY|HAVING|LIMIT|UNION)(?![A-Za-z_])|$)", re.I | re.S)
```

### 확인
같은 SQL 을 가드에 통과시키면 `GROUP BY ref_fund_mgmt_co` 로 바뀌고, 실행 결과가 240 / 230 / 142 / 110 / 85 로 정본과 일치한다.
운용사 절이 없는 일반 조회문은 그대로 통과한다(회귀 확인).

## FIN-05 — 삼성전자 편입 ETF·펀드 개수 (답변 실패)

### 무슨 일이 있었나
질문은 국내 ETF 와 공모펀드 두 상품군인데, 근거문서 **첫 줄**에 해외 ETF 구성종목 테이블
(`ext_ovs_etf_holdings.holding_name`)의 영문 표기 6종이 실렸다. 이 표기가 가장 눈에 띄는 자리에 있으니
SQL 생성기가 그 값들로 서브쿼리를 짰고, 검사기가 "라우팅 대상 밖 테이블" 로 기각했다.
재생성한 SQL 은 이번엔 `SELECT pd_itm_no FROM ext_etf_holdings` 를 썼는데 — 그 테이블의 ETF 식별자는
`etf_code` 이지 `pd_itm_no` 가 아니다. 두 번째도 기각되면서 답변이 끊겼다.

원인이 둘이다.
1. **라우팅 대상 밖 테이블의 개체 매핑이 근거문서에 실렸다.** 근거가 아니라 오답 유도였다.
2. **ext_ 테이블에 마스터 컬럼 이름을 갖다 썼다.** 조인 키 목록은 줬는데, 개수 세기를 JOIN 이 아니라
   서브쿼리로 풀면서 컬럼 이름을 헷갈렸다.

### 고친 곳
`src/runtime/pipeline.py` `build_grounding()`

1. 교차질의일 때 **짝이 맞는 ext_ 테이블만** 근거문서에 싣는다. 검사기가 허용하는 집합과 같은 규칙이다
   (`_EXT_PAIR` 재사용). 국내ETF·펀드 질의에 해외 구성종목 매핑이 실리지 않는다.
2. 조인 키 안내에 두 문장을 더했다 — **ext_ 테이블에는 마스터 컬럼 이름이 없다**(`etf_code` 이지 `pd_itm_no` 가 아니다),
   그리고 **개수를 세는 교차질의도 JOIN 형식으로** 쓰라는 완성형 예시(UNION ALL 두 가지 + 모든 컬럼 별칭 한정).

### 확인
같은 질문의 근거문서를 다시 만들면 `ext_ovs_etf_holdings` 언급이 사라지고, 개수 세기 JOIN 예시와
ambiguous 경고가 실린다.

## FIN-08 — 퇴직연금 ETF (오답)

### 서버가 낸 SQL
```sql
SELECT DISTINCT pd_abrv_nm, pd_nm FROM domestic_etfs
WHERE pd_sale_yn = 1 AND pd_grp_no = 'ETF' LIMIT 30
```

### 왜 틀렸나
**연금 조건이 한 글자도 없다.** 그냥 "판매중인 ETF" 30건을 뽑아 놓고 "퇴직연금으로 살 수 있는 ETF" 라고 답했다.
연금 계좌 편입 가능 여부는 `pd_pen_tr_yn` 이라는 **별도 컬럼에 있는 사실**이지 판매 여부가 아니다.
답에 나열된 상품이 우연히 연금 가능일 수는 있어도, 조건이 없으니 불가능한 상품이 섞여도 알 수 없다.

### 고친 곳
`ontology/enums/domestic_etfs.yaml` 에 `연금질의` 규칙 신설 (트리거: 퇴직연금·연금·IRP·개인연금·DC·노후).
`pd_pen_tr_yn = 'Y'` 를 걸고(ETF 1,022건), 연금 실무에 맞게 `pd_pen_risk_nm`(안전자산 218건 / 위험자산)을
함께 밝히도록 했다. 답변에 모수를 명시한다.

## FIN-07 — 변동성 낮은 ETF 5개 (정답, 다만)

Top 5 는 로컬 재현과 **정확히 일치**한다(RISE CD금리 0.084 → HANARO 머니마켓 0.402).

### 잠재 위험 — 0값 3건이 우연히 가려져 있었다
SQL 은 `du_vlty_1y IS NOT NULL` 만 걸었다. 그런데 변동성이 **0인 ETF 가 3건** 있다
(TIGER 금속선물(H) · ACE 러시아MSCI(합성) · ACE 글로벌메타버스테크액티브 — 전부 미산출).
이번에 안 나온 건 **세 건 모두 판매완료라서** 가드가 넣은 `pd_sale_yn = 1` 에 걸렸기 때문이다.
조건이 하나만 바뀌면 "변동성 0%" 상품이 1~3위를 통째로 차지한다. 총보수 0값 도배와 같은 부류다.

### 표기 문제 둘
- **단위 누락** — 0.084 는 0.08**%** 다(연환산 변동성).
- **일반론 꼬리** — "투자 전 충분한 검토가 필요합니다". 9/2 월배당 답변의 "투자 목표와 리스크 허용 범위 확인" 과 같은 문형이다.

### 고친 곳
`ontology/enums/domestic_etfs.yaml`
- `변동성질의` 규칙 신설 — `du_vlty_1y > 0` 을 함께 걸고, 답변에 **단위(%)와 기준일**을 밝힌다.
  변동성 기준일은 마스터 기준일이 아니라 `du_vlty_base_dt`(1,584건이 2026-08-21)다.
- 답변 규칙에 일반론 꼬리 금지 항목 추가 — 실측으로 새어 나온 문형 2종을 그대로 적었다.
  데이터에 근거한 주의(레버리지 혼입·선물 롤오버·모수 한정)는 붙이되, 누구에게나 해당하는 조언은 붙이지 않는다.

세 건이 서로 다른 층에서 났다. 같은 실수의 반복이 아니다.

| 층 | 문항 | 성격 |
|---|---|---|
| 근거문서 조립 | FIN-05 | 실을 것을 **덜 실어야** 했다 — 무관한 매핑이 오답을 유도했다 |
| 가드 코드 | FIN-06 | 치환 범위가 절반이었다 — SELECT 만 고치고 GROUP BY 를 놓쳤다 |
| yaml 규칙 | FIN-07·08 | 컬럼은 있는데 **판정이 규칙 본문에 없었다** |

FIN-08 은 우리가 계속 마주쳐 온 뿌리와 같다 — **컬럼 설명에만 적힌 판정은 프롬프트에 실리지 않는다.**
`pd_pen_tr_yn` 은 스키마 줄에 "연금거래가능여부" 로 나와 있었지만, "연금을 물으면 이 컬럼을 걸어라" 는
문장이 `query_rules` 본문에 없었기 때문에 생성기가 그냥 지나쳤다.

FIN-06 은 새로운 종류의 경고다 — **가드가 반쯤 고치면 안 고친 것보다 나쁠 수 있다.**
SELECT 만 정본으로 바뀐 덕에 답변에는 정확한 회사 이름이 찍혔고, 그래서 숫자가 틀렸다는 걸 알아채기 더 어려웠다.
컬럼을 정본으로 바꿀 때는 그 컬럼이 쓰이는 **모든 자리**(SELECT·WHERE·GROUP BY·ORDER BY·HAVING)를 한 번에 바꿔야 한다.

## 가장 나빴던 것 — 3배 레버리지 환각

```sql
SELECT DISTINCT pd_abrv_nm, pd_nm FROM domestic_etfs
WHERE (wu_inv_rgn = '미국' OR ref_geo_focus = 'United States of America') LIMIT 30
```

**배수 조건이 없다.** 미국 투자 494건 중 30건을 뽑았고, 답변이 그중 이름에 '레버리지' 가 든 둘을 골라
"미국 3배 레버리지 ETF" 라고 단정했다 — `PLUS 삼성전자단일종목레버리지`(미국이 아니고 2배)와
`PLUS 200커버드콜액티브`(레버리지도 아님). **데이터에 없는 것을 이름만 보고 만들어 낸 것**이라
지금까지 나온 결함 중 성격이 가장 나쁘다.

같은 부류가 하나 더 있다. 원자재 ETN 답변이 "은 선물의 가격 변동을 **2배수로** 추종합니다" 라고 썼는데
SQL 은 `cu_lev_fector` 를 SELECT 하지 않았다. 상품명에서 추론한 서술이지 조회한 값이 아니다.

## 축이 답을 뒤집는다 — 거래 활발

실측 2026-09-04, 상위 5개가 **거의 겹치지 않는다**.

| 순위 | 거래대금(`du_val_1d`) 기준 | 거래량(`du_vol_1d`) 기준 |
|:--:|---|---|
| 1 | KODEX 200 (3.6조원) | KODEX 200선물인버스2X (87.9억주) |
| 2 | KODEX 레버리지 | KODEX 인버스 |
| 3 | TIGER 200 | TIGER 200선물인버스2X |

겹치는 건 `KODEX 인버스` **1건뿐**이다. 단가가 낮은 상품이 거래량 순위를 독식하기 때문이다.
서버는 거래대금으로 뽑아 놓고 답변 끝문장에서 "거래량이 높은 TOP5" 라고 축을 뒤집었고,
`du_val_1d` 를 "하루 **가치 변동액**" 이라고 읽었다(실제는 일거래대금).

## 없는 값을 만든다 — 두 갈래

**① 범주값 창작.** `cu_inverse_short_yn = 'N'` 이 나갔는데 그 컬럼의 실제 값은 **'Y'(183건)와 NULL(5,854건)뿐이고 'N' 은 0건**이다.
값 사전 대조를 통과한 이유는 그 컬럼이 저카디널리티 어휘 생성 대상에서 빠져 있어서다.

**② KG 매핑 확대 해석.** 근거문서가 "한 개체에 값이 여럿이면 IN 으로 모두 넣는다" 고 안내하는데,
'삼성전자' 매핑은 `constituent = '삼성전자'` 하나뿐인데도 SQL 이 `'삼성전자우'`·`'삼성전자 (우)'`·`'삼성전자 (WTS)'` 등
**17종을 창작**해 IN 에 넣었다. 우선주가 섞여 239개가 **259개**로 나갔다.

| `상품설명_창작금지` (신설) | **SELECT 하지 않은 값을 설명하지 않는다** | 모든 컬럼 |
| 해외 `질문에_없는_필터금지` (이식) | 국내에만 있던 규칙을 해외로 + `'N'` 은 0건 명시 | 해외 전 질의 |
| 해외 `목록조회_별칭` (신설) | 45컬럼 나열 = `SELECT *` 금지 | 해외 목록 질의 |
| KG 매핑 창작 금지 (**코드**) | 근거문서에 "목록에 없는 표기를 지어내지 않는다" | 모든 도메인·모든 개체 |

## 2차 라운드가 말해 주는 것

**이미 고친 자리는 안 틀렸다.** 회귀 문항 185개가 전부 통과했고, 1차에서 고친 운용사·연금·변동성도 재현된다.
틀린 10문항은 **전부 오늘 처음 던져 본 축**이다 — 환헤지·추적오차·배수·거래축·전체개수는 어제까지 한 번도 묻지 않았다.

그러니 "자꾸 틀린다" 보다 **"새 서랍을 열 때마다 그 서랍의 첫 먼지가 나온다"** 에 가깝다.
컬럼 62개와 질문 유형을 곱하면 수백 가지인데 실측한 건 그중 50가지쯤이다.

다만 아픈 신호가 하나 있다 — **금 ETF 의 `cu_charge_rt > 0` 이 세 번째 재발**이다.
규칙 본문에 굵은 빨간 글씨로 "묻지 않았으면 걸지 마라" 가 적혀 있는데도 또 붙었다.
이미 아는 결론을 다시 확인해 준 셈이다: **말로 하는 규칙은 확률적으로만 지켜지고, 확실한 것은 코드 가드뿐이다.**
그래서 이번 라운드에서도 가장 일반적인 수리 3건(운용사 GROUP BY · 교차질의 짝 필터 · KG 창작 금지)은 규칙이 아니라 **코드**로 넣었다.
