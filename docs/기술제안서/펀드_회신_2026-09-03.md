## 6. 🔴 브랜치 — 오늘부로 `main` 하나로 간다

`eda/domestic_etfs` 를 `main` 에 병합했다(`7f41ed5`, 충돌 0 · 삭제 0). 제출 마감(9/6)까지 남은 문서 작업은 서로 다른 파일을 만지므로 브랜치를 나눌 이유가 없다. **앞으로 커밋·push 는 전원 `main`.**

```bash
git pull --rebase        # 🔴 항상 먼저. 남의 커밋을 당겨와 내 커밋을 그 위에 얹는다
git add <파일> && git commit
git push
```

- **`--rebase` 를 붙인다.** 그냥 `git pull` 하면 사람 수만큼 병합 커밋이 쌓여 이력이 엉킨다.
- push 가 `rejected` 로 튕기면 그 사이 누가 올린 것이다 — `git pull --rebase` 하고 다시 push 하면 된다.
- 충돌이 나면 그 파일만 고치고 `git add <파일>` → `git rebase --continue`.
- **`git push --force` 는 쓰지 않는다.** 공유 브랜치라 남의 커밋이 사라진다.

### 아직 옛 브랜치에 있다면

```bash
git checkout main && git pull --rebase
# 옛 브랜치에 안 올린 작업이 남아 있으면 먼저: git checkout <옛브랜치> && git merge main
```

`eda/domestic_etfs` · `eda/domestic_bonds` · `data/v2-20260824` 는 병합했거나 역할이 끝났다. 새로 커밋하지 말 것 — 거기 올린 건 서버에 안 간다.

### 왜 `main` 인지 — 배포 경로가 `main` 만 본다

서버는 내 PC 를 보지 않는다. **GitHub `origin/main` 을 `git pull --ff-only` 로 당겨온다**(`DEPLOY.md` §0-B).

```
내 PC  ──push──▶  GitHub(main)  ──pull──▶  NCP 서버      (코드·yaml·문서)
```

즉 **`main` 에 push 안 한 수정은 서버에 없다.** "고쳤는데 왜 그대로지" 의 1순위 원인이다. 다른 브랜치에 올린 것도 마찬가지로 서버에 안 간다.
